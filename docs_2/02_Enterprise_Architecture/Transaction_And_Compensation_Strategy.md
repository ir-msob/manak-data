# سند استراتژی تراکنش و جبران (Transaction & Compensation Strategy)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.0

**وضعیت:** جدید

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف استراتژی واحد برای مدیریت تراکنش‌های توزیع‌شده (Distributed Transactions) و عملیات جبرانی (Compensation) در پلتفرم تدوین شده است. این سند مرجع اصلی برای تمام دامنه‌ها در زمینه طراحی و پیاده‌سازی گردش‌کارهای چندمرحله‌ای، مدیریت خطا و بازگردانی وضعیت در صورت شکست است.

این سند مکمل اسناد `Workflow_Domain_Architecture` و `Tool_Domain_Architecture` است و الگوی Orchestrated Saga را به‌عنوان راهکار اصلی مدیریت تراکنش‌های توزیع‌شده تعریف می‌کند.

---

## ۲. دامنه سند

این سند موارد زیر را پوشش می‌دهد:

- **مرز تراکنش (Transaction Boundary):** تعریف محدوده هر تراکنش در سطح گردش‌کار
- **الگوی Orchestrated Saga:** نقش Orchestrator در شروع، پیگیری و جبران
- **مدیریت وضعیت جبران (Compensation State Management):** ثبت و رهگیری وضعیت جبران در State Manager
- **رفتار در زمان شکست جبران (Compensation Failure):** Dead Letter Queue، Retry Policy، هشدار
- **الزامات Toolها برای پشتیبانی از عملیات جبرانی:** Idempotency، Compensation Action
- **سناریوهای Toolهای غیرقابل جبران (Non-Compensable):** رفتارهای تعریف‌شده
- **مداخله دستی (Manual Intervention):** رابط مدیریتی برای گردش‌کارهای COMPENSATION_FAILED

جزئیات پیاده‌سازی فنی در اسناد سطح پایین‌تر تدوین می‌شوند. این سند صرفاً **استراتژی سطح بالا و اصول طراحی** را تعریف می‌کند.

---

## ۳. اصول طراحی

| اصل | توضیح |
| :--- | :--- |
| **Orchestrated Saga** | یک Orchestrator مرکزی (Workflow Engine) توالی گام‌ها را کنترل می‌کند و در صورت شکست، خودش مسئول شروع عملیات جبرانی به‌صورت معکوس است. |
| **Eventual Consistency** | سیستم از مدل سازگاری نهایی (Eventual Consistency) پیروی می‌کند و هر Tool مسئول Atomicity عملیات داخلی خود است. |
| **Idempotency** | تمام عملیات (اعم از اصلی و جبرانی) باید Idempotent باشند تا اجرای مجدد آن‌ها عوارض جانبی جدید ایجاد نکند. |
| **جداسازی مسئولیت** | Workflow Engine مسئول توالی و جبران است؛ Toolها مسئول عملیات اتمی و جبران‌کننده‌های خود هستند. |
| **شفافیت و قابلیت رهگیری** | تمام مراحل اجرا و جبران باید در State Manager و Audit Log ثبت شوند. |
| **تاب‌آوری در برابر شکست جبران** | شکست در عملیات جبرانی نباید باعث از دست رفتن اطلاعات شود؛ درخواست‌ها در Dead Letter Queue نگهداری می‌شوند. |

---

## ۴. مرز تراکنش (Transaction Boundary)

هر تراکنش در سطح یک گردش‌کار (Workflow) تعریف می‌شود. مرز تراکنش به‌صورت زیر مشخص می‌شود:

| عنصر | توضیح |
| :--- | :--- |
| **شروع تراکنش** | شروع اجرای یک نمونه گردش‌کار (Workflow Instance) |
| **پایان تراکنش** | تکمیل موفق تمام گام‌ها یا جبران کامل گام‌های موفق قبلی |
| **گام‌های تراکنش** | هر گام گردش‌کار که از طریق Tool Execution Engine اجرا می‌شود |
| **Atomicity** | هر Tool به‌تنهایی مسئول Atomicity عملیات خود است؛ Workflow Engine فقط ترتیب و جبران را مدیریت می‌کند. |

---

## ۵. الگوی Orchestrated Saga

### ۵.۱. نقش Orchestrator

Workflow Engine به‌عنوان Orchestrator مرکزی عمل می‌کند و مسئولیت‌های زیر را بر عهده دارد:

| مسئولیت | توضیح |
| :--- | :--- |
| **مدیریت توالی** | اجرای گام‌ها به‌صورت ترتیبی، موازی یا شرطی بر اساس تعریف گردش‌کار |
| **ثبت وضعیت** | ذخیره وضعیت هر گام (موفق، ناموفق، در انتظار) در State Manager |
| **تشخیص شکست** | شناسایی خطا در هر گام بر اساس کد خطای بازگشتی یا Timeout |
| **شروع جبران** | در صورت شکست غیرقابل بازیابی، شروع فرایند جبران به‌صورت معکوس |
| **مدیریت Retry** | اعمال سیاست یکپارچه Retry (طبق `Non_Functional_Requirements_And_SLA`) برای خطاهای موقت |
| **ثبت رویداد** | انتشار رویدادهای `WorkflowStarted`، `WorkflowStepCompleted`، `WorkflowStepFailed`، `WorkflowCompleted`، `WorkflowFailed`، `CompensationFailed` |

### ۵.۲. جریان جبران (Compensation Flow)

```text
Step 1: Execute → موفق
        │
        ▼
Step 2: Execute → موفق
        │
        ▼
Step 3: Execute → شکست (غیرقابل Retry)
        │
        ▼
شروع جبران (Reverse Saga):
        │
        ├── جبران Step 2: فراخوانی compensation_action
        │       │
        │       ├── موفق → ادامه
        │       │
        │       └── ناموفق → Dead Letter Queue + هشدار Critical
        │
        ├── جبران Step 1: فراخوانی compensation_action
        │       │
        │       └── (ادامه فرآیند مشابه)
        │
        ▼
وضعیت نهایی: Compensated / COMPENSATION_FAILED
```

## ۶. مدیریت وضعیت جبران (Compensation State Management)

### ۶.۱. فیلدهای وضعیت جبران در State Manager

| فیلد | توضیح |
| :--- | :--- |
| `compensation_status` | وضعیت جبران (`NotStarted`, `InProgress`, `Completed`, `Failed`) |
| `compensation_started_at` | زمان شروع جبران |
| `compensation_completed_at` | زمان اتمام جبران (در صورت موفقیت) |
| `compensation_failed_step_id` | شناسه گامی که جبران آن با شکست مواجه شده است |
| `compensation_retry_count` | تعداد Retry برای عملیات جبرانی جاری |
| `dlq_reference` | ارجاع به درخواست در Dead Letter Queue (در صورت شکست) |

### ۶.۲. ثبت رویدادهای جبران

تمامی رویدادهای مرتبط با جبران باید در `event_log` State Manager ثبت شوند:

| رویداد | توضیح |
| :--- | :--- |
| `CompensationStarted(workflow_instance_id, timestamp)` | شروع فرایند جبران |
| `StepCompensated(step_id, compensation_result, timestamp)` | تکمیل موفق جبران یک گام |
| `CompensationFailed(step_id, error, timestamp)` | شکست در جبران یک گام |
| `CompensationCompleted(workflow_instance_id, timestamp)` | اتمام موفق تمام جبران‌ها |
| `CompensationAborted(workflow_instance_id, reason, timestamp)` | لغو دستی جبران توسط اپراتور |

---

## ۷. رفتار در زمان شکست جبران (Compensation Failure)

### ۷.۱. Dead Letter Queue (DLQ)

در صورت شکست عملیات جبرانی یک گام، Orchestrator باید:

۱. درخواست جبرانی ناموفق را در **Dead Letter Queue (DLQ)** قرار دهد.
۲. یک **Scheduler مجزا** برای Retry با Backoff طولانی‌تر (هر ۱ ساعت) راه‌اندازی کند.
۳. یک **هشدار Critical** به تیم عملیات ارسال کند.
۴. گردش‌کار را به وضعیت **`COMPENSATION_FAILED`** تغییر دهد.

### ۷.۲. سیاست Retry برای DLQ

| پارامتر | مقدار پیش‌فرض | توضیح |
| :--- | :--- | :--- |
| **حداکثر تعداد Retry** | ۵ بار | تعداد تلاش‌های مجدد برای عملیات جبرانی از DLQ |
| **فاصله زمانی اولیه** | ۱ ساعت | فاصله زمانی قبل از اولین Retry از DLQ |
| **ضریب افزایش** | ۲ | ضریب افزایش فاصله زمانی در هر Retry |
| **حداکثر فاصله زمانی** | ۲۴ ساعت | حداکثر فاصله زمانی بین Retryها |
| **رفتار پس از اتمام Retry** | `HUMAN_ESCALATION` | ارجاع به اپراتور برای مداخله دستی |

### ۷.۳. وضعیت‌های گردش‌کار مرتبط با جبران

| وضعیت | توضیح |
| :--- | :--- |
| **Compensating** | فرایند جبران در حال اجراست. |
| **Compensated** | عملیات جبرانی با موفقیت انجام شده و گردش‌کار به پایان رسیده است. |
| **COMPENSATION_FAILED** | عملیات جبرانی با شکست مواجه شده و نیاز به مداخله دستی دارد. |
| **WAITING_MANUAL_INTERVENTION** | گردش‌کار در انتظار مداخله دستی (برای Toolهای غیرقابل جبران یا شکست جبران). |

---

## ۸. الزامات Toolها برای پشتیبانی از عملیات جبرانی

### ۸.۱. فیلدهای الزامی در Tool Registry

| فیلد | نوع | الزامی | توضیح |
| :--- | :--- | :--- | :--- |
| `compensable` | boolean | بله | آیا ابزار قابلیت جبران (Compensation) دارد؟ |
| `compensation_action` | string | در صورت `compensable: true` | نام عملیات جبرانی (مثلاً `tool_name.compensate`) |
| `compensation_params_mapping` | JSON object | در صورت `compensable: true` | نگاشت پارامترهای عملیات جبرانی از خروجی عملیات اصلی یا ورودی‌های اولیه |
| `is_compensation_idempotent` | boolean | خیر (پیش‌فرض: `true`) | آیا عملیات جبرانی Idempotent است؟ |
| `compensation_timeout_seconds` | integer | خیر (پیش‌فرض: ۳۰) | Timeout اختصاصی برای عملیات جبرانی |

### ۸.۲. الزامات پیاده‌سازی عملیات جبرانی

| الزام | توضیح |
| :--- | :--- |
| **Idempotency** | عملیات جبرانی باید Idempotent باشد؛ اجرای مجدد آن نباید عوارض جانبی جدید ایجاد کند. |
| **عدم وابستگی به وضعیت جلسه** | عملیات جبرانی نباید به Context یا Session Memory جاری وابسته باشد. |
| **ثبت کامل** | تمام فراخوانی‌های عملیات جبرانی (موفق و ناموفق) باید در Audit Log ثبت شوند. |
| **مدیریت خطا** | در صورت خطا در عملیات جبرانی، Tool باید خطای مشخصی بازگرداند تا Orchestrator بتواند تصمیم‌گیری کند. |

---

## ۹. سناریوهای Toolهای غیرقابل جبران (Non-Compensable Tools)

### ۹.۱. تعریف

Toolهایی که امکان بازگردانی وضعیت قبلی را ندارند (مانند ارسال ایمیل، ایجاد تیکت در سیستم خارجی بدون قابلیت حذف، یا عملیات‌های صرفاً خواندنی).

### ۹.۲. سیاست‌های رفتاری

| سیاست | توضیح | کاربرد |
| :--- | :--- | :--- |
| **ABORT_WORKFLOW** | گردش‌کار بدون شروع جبران، با وضعیت `FAILED` پایان می‌یابد و خطا ثبت می‌شود. | عملیات‌هایی که شکست آن‌ها به‌معنای شکست کل فرایند است. |
| **CONTINUE_WITH_WARNING** | گردش‌کار با وضعیت `COMPLETED_WITH_WARNINGS` ادامه می‌یابد و خطا در Audit Log ثبت می‌شود. | عملیات‌هایی که شکست آن‌ها حیاتی نیست. |
| **HUMAN_ESCALATION** | گردش‌کار به وضعیت `WAITING_MANUAL_INTERVENTION` می‌رود و هشدار برای مداخله دستی ارسال می‌شود. | عملیات‌هایی که نیاز به تصمیم‌گیری انسانی دارند. |

### ۹.۳. معیارهای انتخاب سیاست

| معیار | توصیه |
| :--- | :--- |
| **تأثیر کسب‌وکاری** | اگر شکست Tool به‌معنای شکست کل فرایند است، از `ABORT_WORKFLOW` استفاده کنید. |
| **قابلیت جبران دستی** | اگر امکان جبران دستی وجود دارد، از `HUMAN_ESCALATION` استفاده کنید. |
| **اهمیت عملیات** | اگر عملیات کم‌اهمیت است و شکست آن تأثیر چندانی ندارد، از `CONTINUE_WITH_WARNING` استفاده کنید. |

## ۱۰. مداخله دستی (Manual Intervention)

### ۱۰.۱. رابط مدیریتی (Admin UI)

برای گردش‌کارهایی که به وضعیت `COMPENSATION_FAILED` یا `WAITING_MANUAL_INTERVENTION` رسیده‌اند، یک رابط مدیریتی با قابلیت‌های زیر فراهم می‌شود:

| قابلیت | توضیح |
| :--- | :--- |
| **مشاهده درخواست‌های DLQ** | نمایش لیست درخواست‌های جبرانی ناموفق با جزئیات کامل (شناسه گردش‌کار، گام، Tool، پیام خطا، تعداد Retry). |
| **Retry دستی** | امکان اجرای مجدد عملیات جبرانی برای یک گام خاص. |
| **لغو دستی گردش‌کار** | امکان خاتمه گردش‌کار با ثبت دلیل در Audit Log. |
| **ادامه گردش‌کار** | در صورت امکان، ادامه گردش‌کار از نقطه شکست (با تأیید اپراتور). |

### ۱۰.۲. الزامات امنیتی

| الزام | توضیح |
| :--- | :--- |
| **احراز هویت** | فقط کاربران با نقش `Admin` یا `Operator` به رابط مدیریتی دسترسی دارند. |
| **ثبت کامل** | تمام عملیات انجام‌شده از طریق رابط مدیریتی در Audit Log با شناسه اپراتور ثبت می‌شود. |
| **تأیید دوگانه** | برای عملیات حساس (مانند لغو گردش‌کار)، تأیید دوگانه (Two-Person Rule) الزامی است. |

## ۱۳. نتیجه‌گیری

این سند استراتژی واحد برای مدیریت تراکنش‌های توزیع‌شده و عملیات جبرانی در پلتفرم تعریف می‌کند. با استفاده از الگوی Orchestrated Saga، تفکیک واضح مسئولیت‌ها بین Workflow Engine و Toolها، و مکانیزم‌های مقاوم‌سازی مانند Dead Letter Queue و مداخله دستی، پلتفرم قادر خواهد بود گردش‌کارهای چندمرحله‌ای را به‌صورت قابل اعتماد و با حفظ یکپارچگی داده اجرا کند.

**مسئولیت به‌روزرسانی:** تیم معماری به همراه تیم‌های Workflow و Tool مسئول بازبینی دوره‌ای این سند و به‌روزرسانی آن بر اساس تغییرات نیازمندی‌ها و درس‌آموخته‌های عملیاتی هستند.
