# معماری دامنه اتصال‌دهنده (Connector Domain Architecture)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.0

**وضعیت:** پیش‌نویس

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف معماری دامنه **اتصال‌دهنده** (Connector Domain) تدوین شده است. این دامنه مسئول اتصال به منابع داده و سیستم‌های خارجی با پروتکل‌های مختلف (پایگاه‌های داده، فایل‌ها، APIهای سازمانی، سامانه‌های پیام‌رسان و غیره) است. هدف آن ایجاد چارچوبی استاندارد، توسعه‌پذیر و امن برای دریافت داده از منابع خارجی و تبدیل آن به فرمت قابل استفاده توسط پلتفرم است.

این سند به‌عنوان مرجع اصلی برای تیم‌های توسعه، معماری، یکپارچه‌سازی و مهندسی داده در زمینه طراحی و پیاده‌سازی اتصال‌دهنده‌های مختلف به منابع داده و سیستم‌های سازمانی عمل می‌کند.

---

## ۲. دامنه سند

این سند تمام جنبه‌های مرتبط با دامنه اتصال‌دهنده را پوشش می‌دهد و شامل موارد زیر است:

- **Connector Registry:** ثبت، مدیریت و نگهداری اتصال‌دهنده‌های موجود
- **Data Ingestion Framework:** چارچوب دریافت داده از منابع خارجی
- **پروتکل‌های پشتیبانی‌شده:** پایگاه‌های داده، فایل‌ها، APIها، پیام‌رسان‌ها، مخزن‌های کد
- **الگوهای دریافت داده:** Batch، Streaming، Event-Driven، Incremental
- **تبدیل و نگاشت داده (Mapping & Transformation):** تبدیل داده به فرمت استاندارد داخلی
- **مدیریت اعتبارنامه (Credential Management):** ذخیره و استفاده امن از اعتبارنامه‌ها
- **پایش و مشاهده‌پذیری:** پایش وضعیت، عملکرد و خطاهای اتصال‌دهنده‌ها
- **مدیریت خطا و Retry:** مدیریت خطاهای اتصال، زمان‌بندی مجدد و تلاش مجدد
- **همگام‌سازی و زمان‌بندی (Scheduling):** زمان‌بندی دریافت دوره‌ای داده

جزئیات پیاده‌سازی فنی و کدنویسی در اسناد سطح پایین‌تر تدوین می‌شوند. این سند صرفاً **معماری سطح بالا و اصول طراحی** دامنه را تعریف می‌کند.

## ۳. اصول طراحی دامنه

| اصل | توضیح |
| :--- | :--- |
| **توسعه‌پذیری (Extensibility)** | افزودن اتصال‌دهنده جدید (نوع منبع یا پروتکل جدید) باید بدون تغییر در هسته سیستم امکان‌پذیر باشد. |
| **امنیت پیش‌فرض (Security by Default)** | تمام اتصال‌دهنده‌ها باید با احراز هویت، رمزنگاری و مدیریت امن اعتبارنامه‌ها کار کنند. |
| **جداسازی (Decoupling)** | منطق دریافت داده از منطق پردازش و ذخیره‌سازی جدا است تا تغییر در یک بخش تأثیری بر سایر بخش‌ها نداشته باشد. |
| **مقاوم در برابر خطا (Fault Tolerance)** | اتصال‌دهنده‌ها باید در برابر قطعی شبکه، خطای منبع و تغییرات ناگهانی مقاوم باشند و با Retry و Recovery مدیریت شوند. |
| **مقیاس‌پذیری (Scalability)** | اتصال‌دهنده‌ها باید توانایی پردازش حجم‌های بزرگ داده (میلیون‌ها رکورد) را در زمان‌های مشخص داشته باشند. |
| **قابلیت رهگیری (Traceability)** | تمام داده‌های دریافت‌شده باید قابل ردیابی به منبع، زمان دریافت و نسخه باشند. |
| **حداقل تأثیر بر منبع (Minimal Source Impact)** | دریافت داده باید با حداقل بار روی منبع داده (منبع اصلی) انجام شود تا عملکرد سیستم منبع تحت تأثیر قرار نگیرد. |
| **انعطاف‌پذیری در زمان‌بندی (Flexible Scheduling)** | پشتیبانی از زمان‌بندی‌های مختلف (Real-Time، Scheduled، On-Demand، Event-Driven) |
| **استقلال از منبع (Source Agnostic)** | اتصال‌دهنده‌ها نباید وابسته به یک محصول یا فروشنده خاص باشند و باید امکان جایگزینی یا افزودن منابع مشابه بدون تغییر در معماری فراهم باشد. |
| **قابلیت ادامه اجرا (Resumability)** | در صورت قطع ارتباط یا توقف پردازش، اتصال‌دهنده باید بتواند از آخرین نقطه موفق ادامه دهد و از دریافت مجدد داده‌های تکراری جلوگیری کند. |
| **Idempotency (تکرارپذیری ایمن)** | اجرای مجدد عملیات دریافت داده نباید باعث ایجاد داده‌های تکراری یا ناسازگاری در سیستم شود. |
| **سازگاری با چند مستأجر (Multi-Tenancy)** | تمام اتصال‌دهنده‌ها باید داده‌ها، تنظیمات و اعتبارنامه‌های هر مستأجر را به‌صورت کامل از سایر مستأجران جدا نگه دارند. |
| **قابلیت مشاهده کامل (Full Observability)** | تمام مراحل دریافت داده، خطاها، زمان اجرا، حجم داده و وضعیت اتصال باید به‌صورت کامل ثبت و قابل پایش باشند. |

## ۴. مؤلفه‌های اصلی دامنه

### ۴.۱. Connector Registry (ثبت اتصال‌دهنده)

**مسئولیت:** ثبت، نگهداری و مدیریت اتصال‌دهنده‌های موجود در پلتفرم.

**وظایف کلیدی:**

- **ثبت اتصال‌دهنده:** ثبت نوع، پروتکل، تنظیمات و Metadata اتصال‌دهنده
- **مدیریت چرخه حیات:** فعال/غیرفعال‌سازی، به‌روزرسانی، حذف اتصال‌دهنده
- **کشف قابلیت (Capability Discovery):** ارائه اطلاعات درباره قابلیت‌های هر اتصال‌دهنده (انواع داده، پروتکل‌ها، الگوهای دریافت)
- **مدیریت نسخه:** نگهداری نسخه‌های مختلف اتصال‌دهنده
- **مدیریت وضعیت:** نمایش وضعیت (فعال، غیرفعال، خطا، در حال همگام‌سازی)

**اطلاعات تکمیلی هر اتصال‌دهنده:**

- نسخه API یا پروتکل منبع
- نسخه اتصال‌دهنده
- وضعیت سلامت (Health Status)
- آخرین زمان اجرای موفق
- آخرین زمان اجرای ناموفق
- آخرین زمان همگام‌سازی
- حجم متوسط داده دریافت‌شده
- مالک اتصال‌دهنده
- برچسب‌ها (Tags)
- سطح حساسیت داده

**فیلدهای کلیدی Connector Registry:**

| فیلد | توضیح |
| :--- | :--- |
| `connector_id` | شناسه یکتای اتصال‌دهنده |
| `tenant_id` | شناسه مستأجر |
| `name` | نام اتصال‌دهنده |
| `type` | نوع منبع (Database, File, API, Messaging, Repository, ...) |
| `protocol` | پروتکل (JDBC, REST, GraphQL, Kafka, Git, ...) |
| `config_schema` | طرحواره پیکربندی (JSON Schema) |
| `capabilities` | قابلیت‌ها (Batch, Streaming, Incremental, ...) |
| `status` | وضعیت (Active, Inactive, Error, Syncing) |
| `auth_method` | روش احراز هویت (Basic, OAuth2, API Key, Certificate) |
| `schedule` | زمان‌بندی همگام‌سازی (Cron Expression) |
| `created_at` | زمان ثبت |
| `updated_at` | زمان آخرین به‌روزرسانی |

### ۴.۲. Data Ingestion Framework (چارچوب دریافت داده)

**مسئولیت:** دریافت داده از منابع خارجی و تبدیل آن به فرمت استاندارد داخلی.

**قابلیت‌های تکمیلی چارچوب دریافت داده:**

- پشتیبانی از دریافت موازی (Parallel Ingestion)
- کنترل نرخ دریافت (Throttling)
- محدودسازی مصرف منابع
- مدیریت Backpressure
- ادامه دریافت از آخرین Checkpoint
- تشخیص داده‌های تکراری
- مدیریت Chunkهای بزرگ داده

**وظایف کلیدی:**

- **اتصال به منبع:** برقراری ارتباط با منبع داده با استفاده از پروتکل مناسب
- **دریافت داده:** دریافت داده بر اساس الگوی تعیین‌شده (Batch، Streaming، Incremental)
- **اعتبارسنجی:** اعتبارسنجی داده‌های دریافت‌شده از نظر فرمت، کامل بودن و صحت
- **تبدیل (Transformation):** تبدیل داده به فرمت استاندارد داخلی (JSON، Avro، Parquet)
- **نگاشت (Mapping):** نگاشت فیلدهای منبع به فیلدهای هدف (Schema Mapping)
- **غنی‌سازی:** افزودن Metadata (زمان دریافت، منبع، نسخه)
- **انتقال به لایه داده:** ارسال داده به لایه مهندسی داده برای ذخیره‌سازی و پردازش بیشتر

**جریان دریافت داده (Ingestion Flow):**
```text
Source System
        │
        ▼
Connector Instance
        │
        ├── Authentication (Credential Validation)
        │
        ├── Data Extraction (Query, API Call, File Read, ...)
        │
        ├── Validation (Schema, Format, Completeness)
        │
        ├── Transformation (Normalize, Enrich, Map)
        │
        ├── Add Metadata (source, timestamp, version, tenant_id)
        │
        ▼
Data Pipeline (مهندسی داده)
        │
        ▼
Storage (Data Lake, Warehouse, Vector DB)
```

### ۴.۴. الگوهای دریافت داده (Ingestion Patterns)

| الگو | توضیح | کاربرد | مزایا | معایب |
| :--- | :--- | :--- | :--- | :--- |
| **Batch (دسته‌ای)** | دریافت دوره‌ای حجم‌های بزرگ داده در زمان‌های مشخص | همگام‌سازی اسناد، پایگاه‌های داده، فایل‌ها | سادگی، کارایی بالا، مدیریت آسان | تأخیر در دریافت داده‌های جدید |
| **Streaming (جاری)** | دریافت مداوم داده‌های جاری با تأخیر کم | رویدادها، لاگ‌ها، تغییرات Repository | تأخیر کم، داده‌های به‌روز | پیچیدگی بیشتر، نیاز به زیرساخت پیشرفته |
| **Incremental (افزایشی)** | دریافت فقط داده‌های جدید یا تغییرکرده | پایگاه‌های داده با Change Data Capture | کاهش حجم داده، کارایی بالا | نیاز به شناسایی تغییرات |
| **Event-Driven (رویدادمحور)** | واکنش به رویدادها و دریافت داده در لحظه وقوع | اعلان‌ها، وب‌هوک‌ها | واکنش فوری، کاهش بار اضافی | وابستگی به رویدادهای منبع |
| **Scheduled (زمان‌بندی‌شده)** | دریافت بر اساس زمان‌بندی (Cron) | گزارش‌های دوره‌ای، همگام‌سازی شبانه | کنترل کامل بر زمان دریافت | تأخیر ذاتی |

**معیار انتخاب الگوی دریافت داده**

انتخاب الگوی مناسب دریافت داده بر اساس معیارهای زیر انجام می‌شود:

- حجم داده
- نرخ تغییرات داده
- حساسیت زمانی
- محدودیت‌های منبع
- هزینه انتقال
- SLA مورد انتظار
- قابلیت پشتیبانی منبع
- الزامات کسب‌وکار

### ۴.۵. تبدیل و نگاشت داده (Mapping & Transformation)

**مسئولیت:** تبدیل داده از فرمت منبع به فرمت استاندارد داخلی و نگاشت فیلدها.

**وظایف کلیدی:**

- **نگاشت Schema:** تعیین ارتباط بین فیلدهای منبع و فیلدهای هدف
- **تبدیل نوع داده:** تبدیل انواع داده (Date، Number، Boolean، ...)
- **نرمال‌سازی:** نرمال‌سازی مقادیر (Trim، تبدیل حروف، فرمت تاریخ)
- **غنی‌سازی:** افزودن فیلدهای محاسباتی یا Metadata
- **اعتبارسنجی:** اعتبارسنجی داده‌های تبدیل‌شده

**نمونه نگاشت (Mapping):**

```json
{
  "source": {
    "table": "employees",
    "fields": {
      "id": "INTEGER",
      "full_name": "VARCHAR",
      "hire_date": "DATE",
      "department": "VARCHAR",
      "salary": "DECIMAL"
    }
  },
  "target": {
    "schema": "person",
    "mapping": {
      "employee_id": "id",
      "name": "full_name",
      "joined_at": "hire_date",
      "dept": "department",
      "annual_salary": "salary * 12"
    },
    "transformations": {
      "hire_date": "to_iso_date(hire_date)",
      "full_name": "trim(full_name)"
    }
  }
}
```

**قابلیت‌های پیشرفته نگاشت**

- تبدیل شرطی داده
- نگاشت مبتنی بر Rule
- نگاشت چند منبع به یک مقصد
- نگاشت یک منبع به چند مقصد
- اعتبارسنجی Ruleهای نگاشت
- نسخه‌بندی Mappingها

### ۴.۶. مدیریت اعتبارنامه (Credential Management)

**مسئولیت:** ذخیره، مدیریت و استفاده امن از اعتبارنامه‌های دسترسی به منابع خارجی.

**وظایف کلیدی:**

- **ذخیره‌سازی امن:** ذخیره اعتبارنامه‌ها در Secret Management Service (HashiCorp Vault، AWS Secrets Manager)
- **چرخش (Rotation):** چرخش دوره‌ای اعتبارنامه‌ها برای افزایش امنیت
- **دسترسی محدود:** دسترسی به اعتبارنامه‌ها فقط برای اتصال‌دهنده‌های مجاز
- **ثبت ممیزی:** ثبت تمام دسترسی‌ها و استفاده از اعتبارنامه‌ها
- **رمزنگاری:** رمزنگاری اعتبارنامه‌ها در حالت ذخیره و انتقال

**الزامات امنیتی تکمیلی**

- پشتیبانی از Secret Rotation خودکار
- جلوگیری از نمایش Credential در Log
- استفاده از Tokenهای کوتاه‌عمر
- پشتیبانی از OAuth2 Refresh Token
- ثبت کامل تمام دسترسی‌ها
- پشتیبانی از Certificate Based Authentication

---

### ۴.۷. پایش و مشاهده‌پذیری (Observability)

**مسئولیت:** پایش وضعیت، عملکرد و خطاهای اتصال‌دهنده‌ها.

**متریک‌های کلیدی:**

| متریک | توضیح |
| :--- | :--- |
| **Ingestion Success Rate** | درصد دریافت‌های موفق |
| **Ingestion Failure Rate** | درصد دریافت‌های ناموفق |
| **Data Volume** | حجم داده دریافت‌شده (رکورد/بایت) |
| **Ingestion Latency** | زمان بین درخواست دریافت و تکمیل |
| **Sync Duration** | مدت زمان هر همگام‌سازی |
| **Error Count** | تعداد خطاهای رخ‌داده |
| **Pending Queue Size** | تعداد داده‌های در انتظار پردازش |

**لاگ‌گیری:**

- تمام تلاش‌های دریافت داده (موفق و ناموفق) با جزئیات کامل
- شامل: `connector_id`, `source`, `records_processed`, `duration_ms`, `status`, `error_message`

**هشداردهی (Alerting):**

- هشدار در صورت کاهش نرخ موفقیت (Success Rate) زیر آستانه
- هشدار در صورت افزایش تأخیر (Latency)
- هشدار در صورت تکرار خطای احراز هویت

---

### ۴.۸ مدیریت وضعیت همگام‌سازی (Synchronization State Management)

برای هر اتصال‌دهنده وضعیت آخرین همگام‌سازی نگهداری می‌شود.

اطلاعات قابل نگهداری شامل:

- آخرین زمان اجرای موفق
- آخرین Checkpoint
- آخرین Offset
- آخرین Version
- آخرین Cursor
- وضعیت فعلی
- تعداد Retry
- علت آخرین خطا
- حجم آخرین داده دریافت‌شده

این اطلاعات امکان ادامه دریافت داده بدون پردازش مجدد اطلاعات قبلی را فراهم می‌کند.

## ۵. جریان دریافت داده (Data Ingestion Flow)

جریان کامل دریافت داده از منبع تا ذخیره‌سازی:

```text
Source System
        │
        ▼
Connector Instance (Scheduler)
        │
        ├── Credential Retrieval (از Secret Management)
        │
        ├── Authentication (به منبع)
        │
        ├── Data Extraction (بر اساس الگوی Ingestion)
        │
        ├── Validation (اعتبارسنجی داده)
        │
        ├── Transformation & Mapping (تبدیل و نگاشت)
        │
        ├── Enrichment (افزودن Metadata)
        │
        ▼
Data Pipeline (مهندسی داده)
        │
        ├── Storage (Data Lake / Warehouse)
        │
        ├── Indexing (Knowledge & Context Engine)
        │
        └── Event Publishing (اعلان به سایر دامنه‌ها)
        │
        ▼
Logging & Observability
```

### ۵.۱ مدیریت خطاهای دریافت داده

در هنگام دریافت داده، اتصال‌دهنده باید انواع خطاهای زیر را مدیریت کند.

| نوع خطا | رفتار سیستم |
| :--- | :--- |
| خطای شبکه | Retry با Backoff |
| Timeout | Retry محدود |
| Authentication Failure | توقف و هشدار |
| Authorization Failure | توقف عملیات |
| Schema Change | ارسال هشدار و توقف Mapping |
| Data Validation Failure | ثبت خطا و رد داده |
| Rate Limit | انتظار و تلاش مجدد |
| Source Unavailable | Retry زمان‌بندی‌شده |

## ۱۰. نتیجه‌گیری

دامنه **اتصال‌دهنده** به‌عنوان **دروازه ورود داده به پلتفرم**، نقش حیاتی در یکپارچه‌سازی با منابع داده و سیستم‌های سازمانی ایفا می‌کند. معماری تعریف‌شده در این سند، چارچوبی استاندارد، توسعه‌پذیر، امن و مقیاس‌پذیر برای دریافت داده از منابع متنوع و تبدیل آن به فرمت قابل استفاده توسط پلتفرم فراهم می‌آورد.

رعایت اصول طراحی (Extensibility، Security by Default، Fault Tolerance، Scalability) و پیاده‌سازی مؤلفه‌های کلیدی (Connector Registry، Data Ingestion Framework، Credential Management، Observability) تضمین می‌کند که پلتفرم بتواند به‌صورت مؤثر با هر نوع منبع داده‌ای یکپارچه شود، داده‌ها را با قابلیت اطمینان بالا دریافت کند و در عین حال امنیت، عملکرد و قابلیت نگهداری بلندمدت را حفظ کند.

**مسئولیت به‌روزرسانی:** تیم معماری به همراه تیم‌های توسعه، یکپارچه‌سازی و مهندسی داده مسئول بازبینی دوره‌ای این سند، به‌روزرسانی آن بر اساس تغییرات نیازمندی‌های یکپارچه‌سازی، پروتکل‌های جدید و بازخورد تیم‌های پیاده‌سازی هستند.

**ثبات سند:** این سند باید با تغییرات در معماری کلان، پروتکل‌های یکپارچه‌سازی و نیازمندی‌های دریافت داده هم‌گام باشد. هر تغییر در اتصال‌دهنده‌ها یا سیاست‌های دریافت داده باید در این سند منعکس شود تا سایر اسناد معماری و طراحی نیز به‌روزرسانی شوند.
