# نقشه کانتکست دامنه‌ها (Context Map)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.0

**وضعیت:** پیش‌نویس

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف ترسیم **نقشه کانتکست** (Context Map) دامنه‌های پلتفرم تدوین شده است. نقشه کانتکست، ارتباطات، مرزها و الگوهای تعامل بین دامنه‌های مختلف (Bounded Contextها) را مشخص می‌کند و نشان می‌دهد که هر دامنه با کدام دامنه‌های دیگر در تعامل است، چه نوع رابطه‌ای بین آن‌ها برقرار است و چه قراردادها و انتظاراتی بین آن‌ها وجود دارد.

این سند با بهره‌گیری از مفاهیم **طراحی مبتنی بر دامنه** (Domain-Driven Design — DDD)، به شفاف‌سازی مرزهای حوزه‌های مختلف، مدیریت وابستگی‌ها و جلوگیری از نشت مفاهیم بین دامنه‌ها کمک می‌کند. این سند به‌عنوان مرجع اصلی برای تیم‌های معماری، توسعه و محصول در زمینه درک تعاملات بین دامنه‌ها و طراحی رابط‌های بین آن‌ها عمل می‌کند.

---

## ۲. دامنه سند

این سند تمام دامنه‌های تعریف‌شده در سند `Domain Landscape` را پوشش می‌دهد و شامل موارد زیر است:

- **نقشه ارتباطات:** نمایش گرافیکی و توصیفی روابط بین دامنه‌ها
- **الگوهای یکپارچه‌سازی:** الگوهای تعامل (مشتری-تأمین‌کننده، مشارکت، هسته مشترک و غیره)
- **قراردادها و انتظارات:** خروجی‌ها، رویدادها و APIهای مورد انتظار بین دامنه‌ها
- **مرزهای معنایی:** مشخص کردن اینکه چه مفاهیمی در کدام دامنه تعریف و مدیریت می‌شوند

جزئیات پیاده‌سازی فنی و مشخصات دقیق APIها در اسناد تخصصی هر دامنه و سند `API_Contract_Overview` تدوین می‌شوند. این سند صرفاً **الگوهای تعامل سطح بالا** را تعریف می‌کند.

## ۳. مفاهیم کلیدی نقشه کانتکست

| مفهوم | توضیح |
| :--- | :--- |
| **Bounded Context (کانتکست محدود)** | مرز مشخصی که در آن یک مدل دامنه تعریف و معنا دارد. هر دامنه یک Bounded Context مستقل است. |
| **Upstream / Downstream** | جهت وابستگی: دامنه Upstream تأمین‌کننده خدمات یا داده است و دامنه Downstream مصرف‌کننده آن. |
| **Contract (قرارداد)** | مجموعه انتظارات، خروجی‌ها، رویدادها و APIهایی که یک دامنه در اختیار سایر دامنه‌ها قرار می‌دهد. |
| **Anticorruption Layer (لایه ضدفساد)** | لایه‌ای که از نشت مفاهیم و مدل‌های خارجی به دامنه داخلی جلوگیری می‌کند. |
| **Shared Kernel (هسته مشترک)** | مجموعه‌ای از مفاهیم و مدل‌ها که بین دو یا چند دامنه به‌اشتراک گذاشته می‌شوند. |
| **Conformist (پیرو)** | دامنه‌ای که مدل خود را با مدل دامنه Upstream هم‌راستا می‌کند (زمانی که تغییر در Upstream دشوار است). |
| **Open Host Service (سرویس میزبان باز)** | سرویسی که با ارائه یک رابط استاندارد و عمومی، امکان تعامل با دامنه‌های مختلف را فراهم می‌کند. |
| **Published Language (زبان منتشرشده)** | زبان مشترک و استانداردی که برای ارتباط بین دامنه‌ها استفاده می‌شود (معمولاً به‌صورت JSON Schema، ProtoBuf و غیره). |

## ۴. اصول طراحی نقشه کانتکست

| اصل | توضیح |
| :--- | :--- |
| **مرزهای واضح (Clear Boundaries)** | هر دامنه مرز مشخصی دارد و مفاهیم آن نباید به‌طور مستقیم به سایر دامنه‌ها نشت کنند. |
| **وابستگی حداقلی (Minimal Coupling)** | دامنه‌ها باید حداقل وابستگی مستقیم به یکدیگر داشته باشند و از طریق رابط‌های استاندارد تعامل کنند. |
| **استقلال تکاملی (Evolutionary Independence)** | هر دامنه باید قابلیت تکامل مستقل از سایر دامنه‌ها را داشته باشد. تغییرات در یک دامنه نباید مستقیماً سایر دامنه‌ها را تحت تأثیر قرار دهد. |
| **انتقال رویدادمحور (Event-Driven Communication)** | ارتباط بین دامنه‌ها تا حد امکان از طریق رویدادها انجام می‌شود تا وابستگی زمانی و مستقیم کاهش یابد. |
| **قراردادهای صریح (Explicit Contracts)** | تمام تعاملات بین دامنه‌ها باید دارای قراردادهای مشخص، مستند و نسخه‌بندی‌شده باشند. |
| **حفظ یکپارچگی معنایی (Semantic Integrity)** | هر مفهوم باید در یک دامنه تعریف و مدیریت شود و سایر دامنه‌ها از طریق رابط‌های استاندارد به آن دسترسی داشته باشند. |

## ۶. الگوهای تعامل بین دامنه‌ها

### ۶.۱. لایه دسترسی و تعامل

| دامنه مبدأ | دامنه مقصد | الگوی تعامل | جهت وابستگی | قراردادهای کلیدی |
| :--- | :--- | :--- | :--- | :--- |
| **یکپارچه‌سازی و API** | **عامل‌ها و هماهنگی** | **Open Host Service** | Upstream → Downstream | درخواست‌های REST، WebSocket، گراف‌QL |
| **Webhook و رویداد** | **یکپارچه‌سازی و API** | **Conformist** | Upstream → Downstream | رویدادهای استاندارد، Webhook Callback |
| **اتصال‌دهنده‌ها** | **یکپارچه‌سازی و API** | **Anticorruption Layer** | Upstream → Downstream | داده‌های نرمال‌شده، Metadata |
| **یکپارچه‌سازی و API** | **هویت و دسترسی** | **Open Host Service** | Downstream → Upstream | توکن JWT، درخواست احراز هویت |
| **یکپارچه‌سازی و API** | **حاکمیت و انطباق** | **Conformist** | Downstream → Upstream | سیاست‌های دسترسی، Rate Limiting |

### ۷.۳. زبان مشترک (Published Language)

| مفهوم | تعریف | دامنه مالک |
| :--- | :--- | :--- |

| **Agent** | واحد اجرایی هوشمند | عامل‌ها و هماهنگی |
| **Knowledge** | واحد دانش قابل استفاده | دانش و زمینه |

| **Memory** | اطلاعات ذخیره‌شده از تعاملات | حافظه و تجربه |

| **Task** | واحد کار قابل انجام توسط Agent | عامل‌ها و هماهنگی |
| **Workflow** | دنباله‌ای از گام‌های از پیش تعریف‌شده | مدیریت جریان کار |
| **Model** | مدل هوش مصنوعی قابل استفاده | مدیریت مدل‌ها |
| **Policy** | قانون یا محدودیت قابل اعمال | حاکمیت و انطباق |

## ۱۰. نتیجه‌گیری

این سند نقشه کانتکست دامنه‌های پلتفرم را ترسیم می‌کند و شفافیت کاملی در مورد مرزها، ارتباطات، الگوهای تعامل و قراردادهای بین دامنه‌ها فراهم می‌آورد. با رعایت اصول و الگوهای تعریف‌شده در این سند، تیم‌های توسعه می‌توانند دامنه‌ها را به‌صورت مستقل تکامل دهند، از نشت مفاهیم بین دامنه‌ها جلوگیری کنند و تعاملات بین آن‌ها را به‌صورت استاندارد و قابل اطمینان مدیریت کنند.

نقشه کانتکست به‌عنوان **مرجع اصلی برای طراحی رابط‌های بین دامنه‌ها** عمل می‌کند و تضمین می‌کند که تمامی تعاملات بین دامنه‌ها با قراردادهای مشخص، شفاف و قابل رهگیری انجام می‌شود. این امر به کاهش پیچیدگی، افزایش سرعت توسعه و بهبود نگهداری بلندمدت سیستم کمک می‌کند.

**مسئولیت به‌روزرسانی:** تیم معماری به همراه تیم‌های محصول و توسعه مسئول بازبینی دوره‌ای این سند، به‌روزرسانی نقشه ارتباطات بر اساس تغییرات در دامنه‌ها، اضافه شدن دامنه‌های جدید یا تغییر در الگوهای تعامل هستند.

**ثبات سند:** این سند باید با تغییرات در دامنه‌ها، معماری کلان و نیازمندی‌های یکپارچه‌سازی هم‌گام باشد. هر تغییر در ارتباطات بین دامنه‌ها باید در این سند منعکس شود تا سایر اسناد معماری و طراحی نیز به‌روزرسانی شوند.
