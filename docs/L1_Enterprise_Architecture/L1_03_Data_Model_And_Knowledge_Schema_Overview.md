# ۱. مقدمه و هدف سند

این سند ساختار مفهومی داده، فراداده (Metadata)، گراف دانش (Knowledge Graph)، زمینه (Context) و حافظه (Memory) را در پلتفرم تعریف می‌کند. هدف آن ایجاد یک زبان مشترک برای مدل‌سازی داده است تا موتور دانش و زمینه (Knowledge & Context Engine) و موتور مدیریت حافظه (Memory Management Engine) بر مبنای یک ساختار یکسان پیاده‌سازی شوند.

این سند در سطح **مدل مفهومی داده** (Conceptual Data Model، مستقل از پایگاه داده یا فناوری پیاده‌سازی) تهیه شده است؛ طرحواره فیزیکی، نوع پایگاه داده و ساختار جدول‌ها در اسناد طراحی سطح پایین‌تر مشخص می‌شوند.

# ۲. اصول طراحی (Design Principles)

| اصل | توضیح |
| :--- | :--- |
| **Domain Agnostic** | مدل داده به یک حوزه کسب‌وکار خاص وابسته نیست و برای هر دستیار هوش مصنوعی حوزه‌ای (Domain AI Assistant) قابل استفاده است. |
| **Knowledge First** | داده خام ارزش مستقیم ندارد؛ هدف نهایی تبدیل آن به دانش قابل استفاده برای استدلال (Reasoning) است. |
| **Metadata Driven** | رفتار سیستم (دسترسی، بازیابی، اعتماد) بر اساس فراداده هر شیء تعیین می‌شود، نه نوع فایل یا منبع آن. |
| **Graph Friendly** | ساختار داده به‌گونه‌ای طراحی شده که روابط بین موجودیت‌ها (نه فقط خود موجودیت‌ها) قابل نگهداری و پرس‌وجو باشد. |
| **Multi-Source** | یک موجودیت دانش می‌تواند از چند منبع مختلف تغذیه شود؛ مدل باید این ترکیب را پشتیبانی کند. |
| **Traceable** | هر دانش (Knowledge) و هر زمینه (Context) باید تا منبع اصلی خود (Source) قابل ردیابی باشد. |
| **Data Lineage** | تمام تغییرات و تبدیل‌های اعمال‌شده روی داده (از منبع تا دانش) باید ثبت و قابل پیگیری باشد تا شفافیت و حسابرسی کامل میسر شود. |
| **Lifecycle Management** | داده‌ها و دانش باید دارای چرخه عمر مشخص شامل ایجاد، نگهداری، بایگانی و حذف باشند. |

# ۳. موجودیت‌های اصلی (Core Entities)

جریان تبدیل داده خام به دانش قابل استفاده از شش موجودیت اصلی عبور می‌کند:

```text
Source → Resource → Content → Knowledge → Context → Memory
```

| موجودیت | تعریف | نمونه |
| :--- | :--- | :--- |
| **Source** | منبع اصلی داده که پلتفرم از طریق اتصال‌دهنده (Connector) به آن متصل می‌شود. شامل اطلاعاتی مانند نوع منبع، آدرس اتصال، اعتبارنامه و سیاست همگام‌سازی است. | مخزن Git، ویکی، پایگاه داده، حافظه فایل |
| **Resource** | نماینده یک شیء مشخص در دل یک Source؛ واحد آدرس‌دهی و همگام‌سازی. هر Resource به یک Source تعلق دارد و دارای شناسه منحصربه‌فرد در آن منبع است. | یک فایل، یک صفحه ویکی، یک رکورد پایگاه داده |
| **Content** | محتوای خام استخراج‌شده از یک Resource، پیش از پردازش معنایی. شامل داده باینری یا متنی و فراداده اولیه است. | متن یک سند، خروجی یک پرس‌وجو |
| **Knowledge** | واحد دانش قابل استفاده که از Content پس از تقسیم‌بندی (Chunking)، استخراج فراداده و تولید نمایش عددی (Embedding) تولید می‌شود. | یک بخش نمایه‌شده، یک گزاره استخراج‌شده |
| **Context** | زیرمجموعه‌ای از Knowledgeها و Memoryها که برای یک درخواست مشخص انتخاب و به مدل ارسال می‌شود. | نتیجه جستجوی معنایی برای یک سؤال کاربر |
| **Memory** | اطلاعات ذخیره‌شده از تعاملات گذشته برای استفاده در درخواست‌های آینده (شرح کامل انواع Memory در بخش ۸). | خلاصه یک جلسه قبلی، یک تصمیم ثبت‌شده |

> **مرز مهم:** Knowledge دانشی است که از منابع سازمانی استخراج شده (مالکیت Knowledge & Context Engine)؛ Memory دانشی است که از تعامل سیستم با کاربر یا محیط تولید شده (مالکیت Memory Management Engine). این دو موجودیت منبع تولید متفاوت دارند اما هر دو می‌توانند وارد Context شوند.

**روابط بین موجودیت‌ها:**

```text
Source (1) ───< (0..*) Resource
Resource (1) ───< (0..*) Content
Content (1) ───< (0..*) Knowledge
Knowledge (0..*) ───> (1) Context (ترکیب)
Memory (0..*) ───> (1) Context (ترکیب)
```

# ۴. فراداده استاندارد (Standard Metadata)

هر موجودیت (Resource، Content، Knowledge) دارای مجموعه‌ای از فیلدهای فراداده مشترک است:

| فیلد | توضیح |
| :--- | :--- |
| **ID** | شناسه یکتای موجودیت در سطح پلتفرم (UUID) |
| **Type** | نوع موجودیت (سند، کد، رکورد پایگاه داده، پیام و...) |
| **Title / Description** | عنوان و توضیح کوتاه برای شناسایی موجودیت |
| **Owner** | مالک یا واحد سازمانی مسئول محتوا (ارجاع به هویت کاربر یا گروه) |
| **Source ID** | شناسه Source اصلی که این موجودیت از آن استخراج شده (برای ردیابی و نسبت‌شناسی داده) |
| **Resource ID** | شناسه Resource مبدأ در صورت وجود |
| **Created Time / Updated Time** | زمان ایجاد و آخرین به‌روزرسانی |
| **Version** | نسخه محتوا؛ برای تشخیص تغییرات و همگام‌سازی افزایشی (Incremental Sync) |
| **Tags** | برچسب‌های دسته‌بندی برای جستجو و فیلتر |
| **Security Classification** | سطح حساسیت داده (عمومی، داخلی، محرمانه، بسیار محرمانه) |
| **Permission** | مجوزهای دسترسی مرتبط (لیست نقش‌ها یا کاربران مجاز)؛ ورودی تصمیم‌گیری کنترل دسترسی به زمینه هوش مصنوعی |
| **Confidence Score** | میزان اطمینان به صحت یا کیفیت استخراج (عدد بین ۰ تا ۱)؛ برای Knowledgeهای تولیدشده از منابع غیررسمی یا تحلیل‌شده توسط مدل محاسبه می‌شود. روش محاسبه در سند `Component_Design_Knowledge_Context_Engine` مشخص شده است. |
| **Data Quality Metrics** | مجموعه معیارهای کیفیت داده شامل کامل بودن، صحت، به‌روزبودن و سازگاری که به‌صورت دوره‌ای محاسبه و به‌روز می‌شوند. |
| **Retention Policy** | سیاست نگهداری داده شامل مدت زمان نگهداری، تاریخ انقضا و اقدام پس از انقضا (بایگانی یا حذف). |
| **Lineage** | ثبت زنجیره تبدیل‌ها و پردازش‌های اعمال‌شده بر روی داده از منبع تا وضعیت فعلی. |

# ۵. طرحواره دانش (Knowledge Schema)

هر واحد Knowledge از چهار بخش ساختاریافته تشکیل می‌شود:

| بخش | محتوا |
| :--- | :--- |
| **Identity** | شناسه، نوع، منبع و نسخه؛ برای ردیابی و ارجاع یکتا به Knowledge |
| **Content** | متن یا داده اصلی به همراه نمایش عددی (Embedding) برای جستجوی معنایی |
| **Semantic Information** | موجودیت‌ها (Entities)، روابط (Relations) و برچسب‌های معنایی استخراج‌شده از محتوا؛ ورودی اصلی گراف دانش (Knowledge Graph) — روش استخراج در سند `Component_Design_Knowledge_Context_Engine` تشریح شده است. |
| **Governance** | طبقه‌بندی امنیتی، مجوزها و امتیاز اطمینان؛ تعیین‌کننده این‌که Knowledge در چه شرایطی و برای چه کاربری قابل استفاده است |

**مدیریت نسخه‌گذاری (Versioning):** هر بار که محتوای یک Resource تغییر کند، یک نسخه جدید از Knowledge تولید می‌شود. نسخه‌های قدیمی تا پایان دوره نگهداری (Retention Period) قابل بازیابی هستند و تغییرات بین نسخه‌ها قابل ردیابی می‌باشند.

# ۶. گراف دانش (Knowledge Graph) — Shared Kernel رسمی

> **مالکیت رسمی:** طرحواره تعریف‌شده در این بخش (انواع Node، انواع Relation، فیلدهای مشترک) **Shared Kernel رسمی** بین دامنه دانش و زمینه (`Knowledge_&_Context_Domain_Architecture`) و دامنه مدیریت دانش (`Knowledge_Management_Domain_Architecture`) است. پیاده‌سازی کامل موتور گراف (ذخیره‌سازی، پرس‌وجو، استخراج موجودیت/رابطه، Ontology Management) به‌طور انحصاری در دامنه مدیریت دانش انجام می‌شود. دامنه دانش و زمینه صرفاً مصرف‌کننده است و از طریق Graph Query Service به این طرحواره دسترسی دارد. هرگونه تغییر در Node Types یا Relation Types زیر، باید ابتدا در همین سند ثبت شود و سپس هر دو دامنه به آن ارجاع دهند؛ هیچ‌کدام مجاز به تعریف مستقل Entity/Relation Type جدید نیستند.

گراف دانش روابط بین موجودیت‌های سازمان را نگهداری می‌کند تا بازیابی اطلاعات فراتر از جستجوی متنی، بر اساس رابطه بین موجودیت‌ها نیز ممکن باشد. این گراف در دامنه مدیریت دانش پیاده‌سازی می‌شود و توسط موتور دانش و زمینه (Knowledge & Context Engine) برای بازیابی ترکیبی (Hybrid Retrieval) و تولید زمینه غنی‌تر مصرف می‌شود.

## ۶.۱ گره‌ها (Nodes)

| گره | توضیح |
| :--- | :--- |
| **Person** | افراد سازمان (کاربر، مالک محتوا، تصمیم‌گیرنده) |
| **Organization** | واحد سازمانی یا تیم |
| **Document** | سند یا محتوای دانشی |
| **Service** | سرویس یا سیستم سازمانی |
| **Process** | فرآیند یا گردش‌کار سازمانی |
| **Rule** | قانون، سیاست یا محدودیت |

## ۶.۲ روابط (Relations)

| رابطه | معنا |
| :--- | :--- |
| **references** | یک موجودیت به موجودیت دیگر ارجاع می‌دهد |
| **depends_on** | یک موجودیت برای عملکرد صحیح به موجودیت دیگر وابسته است |
| **owns** | یک Person یا Organization مالک موجودیت دیگر است |
| **generated_by** | یک Knowledge یا Memory توسط یک فرآیند یا Agent تولید شده است |
| **related_to** | ارتباط معنایی عمومی بین دو موجودیت، بدون نوع رابطه مشخص‌تر |

**کاربرد در بازیابی:** هنگام جستجو، علاوه بر تطابق متنی، پلتفرم از گراف دانش برای یافتن موجودیت‌های مرتبط با درخواست کاربر و گسترش دامنه جستجو استفاده می‌کند. به‌عنوان مثال، برای پرسش درباره یک سرویس خاص، تمام مستنداتی که به آن سرویس ارجاع داده‌اند یا توسط تیم مالک آن تولید شده‌اند، بازیابی می‌شوند.

# ۷. مدل زمینه (Context Model)

Context برای هر درخواست به‌صورت پویا و بر اساس این زنجیره ساخته می‌شود:

```text
User Request → Task → Relevant Knowledge → Memory → Policies → Tools → Model Context
```

| مرحله | توضیح |
| :--- | :--- |
| **User Request** | درخواست ورودی که از لایه تعامل و یکپارچه‌سازی (Interface & Integration Layer) دریافت شده |
| **Task** | هدف (Intent) و نوع کار تشخیص‌داده‌شده توسط موتور هماهنگی و ارکستراسیون Agent (Agent Orchestration Engine) |
| **Relevant Knowledge** | نتیجه جستجوی معنایی/ترکیبی (Semantic / Hybrid Retrieval) از موتور دانش و زمینه، متناسب با Task |
| **Memory** | تاریخچه و تجربیات مرتبط بازیابی‌شده از موتور مدیریت حافظه (Memory Management Engine) |
| **Policies** | محدودیت‌های سرویس‌های حاکمیت و پلتفرم (Governance & Platform Services) روی داده قابل استفاده (مثلاً پنهان‌سازی اطلاعات حساس) |
| **Tools** | فهرست ابزارهای در دسترس برای این Task، جهت آگاهی مدل از قابلیت‌های اجرایی |
| **Model Context** | خروجی نهایی؛ بسته‌ای ساختاریافته (معمولاً به فرمت JSON) که به موتور مدیریت مدل (Model Management Engine) جهت فراخوانی مدل ارسال می‌شود. این بسته شامل ترکیبی از متن، فراداده، دستورالعمل‌های سیستم و اطلاعات ابزارها است. |

# ۸. مدل حافظه (Memory Model)

انواع Memory در این سند، تفصیل ساختار داده‌ای همان مؤلفه‌های موتور مدیریت حافظه (Memory Management Engine — بخش ۴.۶ سند `Architecture_Overview_Enterprise_AI_Platform`) هستند:

| نوع Memory | تعریف | ساختار داده‌ای نمونه | متناظر با |
| :--- | :--- | :--- | :--- |
| **Session Memory** | تاریخچه و Context تعامل جاری کاربر با سیستم | لیست پیام‌های تبادل‌شده، وضعیت Task جاری، متغیرهای جلسه | Session Memory (کامپوننت اصلی) |
| **Working Memory** | زیرمجموعه فعال Session Memory که در لحظه پردازش یک Task در اختیار Agent قرار دارد | بخشی از Session Memory که برای Task فعلی انتخاب شده است | بخشی از Session Memory |
| **Long-Term Memory** | تصمیم‌ها، الگوها و دانش تولیدشده از تعاملات گذشته که فراتر از یک Session نگهداری می‌شود | پایگاه داده از تجربیات ثبت‌شده با قابلیت جستجوی معنایی | Long-Term Memory (کامپوننت اصلی) |
| **Semantic Memory** | دانش کلی و پایدار استخراج‌شده از تجربیات (حقایق و الگوهای تکرارشونده) | گراف دانش شخصی یا جدول حقایق با امتیاز اطمینان | بخشی از Long-Term Memory |
| **Procedural Memory** | الگوهای «چگونگی انجام کار» (توالی تصمیم یا اجرای موفق قبلی) که برای Taskهای مشابه آینده قابل استفاده‌اند | ثبت توالی گام‌های موفق در اجرای یک نوع Task خاص | بخشی از Long-Term Memory |
| **Episodic Memory** | ثبت رویدادمحور یک تعامل یا اجرای مشخص (چه اتفاقی، چه زمانی، با چه نتیجه‌ای) | رکورد شامل زمان، نوع رویداد، شرکت‌کنندگان، نتیجه و فراداده | Episodic Memory (کامپوننت اصلی) |

**مدیریت چرخه عمر حافظه:** داده‌های حافظه بر اساس سیاست نگهداری (Retention Policy) تعریف‌شده در فراداده، به‌صورت خودکار بایگانی یا حذف می‌شوند. مدت نگهداری برای Session Memory معمولاً کوتاه‌مدت (چند روز تا چند هفته) و برای Long-Term Memory بلندمدت (چند ماه تا چند سال) است.

# ۹. چرخه عمر اطلاعات (Information Lifecycle)

```text
Raw Data → Ingestion → Processing → Metadata → Knowledge → Graph → Embedding → Retrieval → Context → Reasoning → Memory Update
```

| مرحله | توضیح | مالک |
| :--- | :--- | :--- |
| **Raw Data → Ingestion** | دریافت داده خام از Source از طریق Connector (کششی یا فشاری) | Knowledge & Context Engine |
| **Processing → Metadata** | تقسیم‌بندی (Chunking)، استخراج فراداده و موجودیت‌ها از Content | Knowledge & Context Engine |
| **Knowledge → Graph → Embedding** | تولید واحد Knowledge، ثبت روابط در گراف دانش و تولید نمایش عددی (Embedding) برای جستجوی معنایی | Knowledge & Context Engine |
| **Retrieval → Context** | بازیابی Knowledge مرتبط و ترکیب آن با Memory و Policy برای ساخت Context (بخش ۷) | Knowledge & Context Engine / Memory Management Engine |
| **Reasoning** | استفاده از Context توسط مدل، Agent و Tool برای تصمیم‌گیری و اجرا | Agent Orchestration Engine |
| **Memory Update** | ثبت نتیجه، تصمیم و تجربه جدید برای چرخه‌های بعدی | Memory Management Engine |

# ۱۱. نتیجه‌گیری

این سند مدل مفهومی داده، فراداده، گراف دانش، زمینه و حافظه را به‌صورت یکپارچه تعریف می‌کند و زبان مشترکی برای تمام Componentهای مرتبط با داده فراهم می‌سازد. با رعایت اصول مطرح‌شده (مانند نسبت‌شناسی داده، مدیریت چرخه عمر و حاکمیت مبتنی بر فراداده)، پلتفرم قادر خواهد بود دانش سازمانی را به‌صورت ساختاریافته، قابل ردیابی و امن مدیریت کرده و زمینه‌های دقیق و قابل اعتمادی برای مدل‌های هوش مصنوعی تولید کند.
