# مرور نظارت و مشاهده‌پذیری (Monitoring and Observability Overview)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.1

**وضعیت:** پیش‌نویس بازبینی‌شده

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف معماری نظارت (Monitoring) و مشاهده‌پذیری (Observability) پلتفرم تدوین شده است تا وضعیت سلامت، عملکرد، پایداری و کیفیت سرویس‌ها به‌صورت مستمر قابل مشاهده، اندازه‌گیری و تحلیل باشد. این سند چارچوبی برای جمع‌آوری، تحلیل و نمایش داده‌های عملیاتی فراهم می‌کند تا مشکلات سیستم پیش از تأثیر بر کاربران شناسایی و برطرف شوند و تصمیم‌گیری‌های مرتبط با مقیاس‌پذیری، ظرفیت‌سنجی و بهبود عملکرد بر اساس داده‌های واقعی انجام شود.

این سند به‌عنوان مرجع اصلی برای تمام تیم‌های توسعه، عملیات، SRE و DevOps در زمینه پیاده‌سازی و بهره‌برداری از قابلیت‌های مشاهده‌پذیری پلتفرم عمل می‌کند.

---

## ۲. دامنه سند

این سند راهبردهای نظارت بر تمامی اجزای پلتفرم را پوشش می‌دهد:

- **سرویس‌های اصلی (Core Services):** لایه تعامل و یکپارچه‌سازی، موتور هماهنگی و ارکستراسیون Agent، موتور دانش و Context، موتور مدیریت مدل، موتور اجرای عملیات و ابزار، موتور مدیریت حافظه
- **سرویس‌های مشترک (Shared Services):** هویت، Policy، Audit، Logging، Monitoring، Configuration، Secret Management، Notification، محدودیت نرخ
- **زیرساخت (Infrastructure):** Kubernetes Cluster، پایگاه‌های داده (رابطه‌ای، برداری، کش)، میانجی پیام، ذخیره‌سازی اشیاء
- **لایه هوش مصنوعی:** مدل‌های زبانی بزرگ (LLM)، مدل‌های Embedding، Agentها، Toolها و Workflowها
- **APIها و نقاط ورود:** دروازه API، Webhook، SDK، دریافت رویداد

جزئیات پیاده‌سازی ابزارهای خاص (مانند Prometheus، Grafana، ELK، Jaeger) در اسناد سطح پایین‌تر (مانند `Monitoring_Implementation_Guide`) تدوین می‌شوند.

## ۴. اصول معماری

| اصل | توضیح |
| :--- | :--- |
| **مشاهده‌پذیری از ابتدای طراحی (Observability by Design)** | تمام Componentها باید از ابتدا با قابلیت تولید لاگ (Log)، شاخص (Metric) و ردیابی (Trace) طراحی شوند. مشاهده‌پذیری یک ویژگی الحاقی نیست. |
| **ثبت استاندارد لاگ‌ها** | تمام لاگ‌ها باید به‌صورت ساخت‌یافته (Structured Logging) با فرمت JSON و شامل فیلدهای استاندارد (زمان، سرویس، شناسه درخواست، سطح، پیام) باشند. |
| **استفاده از Trace برای ردیابی درخواست‌های توزیع‌شده** | هر درخواست باید با یک شناسه همبستگی (Correlation‑ID) قابل ردیابی در تمام Componentها باشد تا مسیر کامل اجرا قابل مشاهده باشد — مطابق با الگوی تعریف‌شده در سند `Multi_Agent_Collaboration_Model`. |
| **جمع‌آوری شاخص‌ها (Metrics) در سطح مناسب** | شاخص‌های کلیدی (تأخیر، توان عملیاتی، نرخ خطا، اشباع) برای هر Component و منبع جمع‌آوری شوند. |
| **هشدارهای هوشمند و قابل اجرا** | هشدارها باید بر اساس آستانه‌های معنادار تعریف شوند، از هشدارهای بی‌رویه (Alert Fatigue) جلوگیری شود و هر هشدار دارای اقدام مشخص باشد. |
| **داشبوردهای استاندارد و هدفمند** | داشبوردها برای مخاطبان مختلف (مدیریت، عملیات، توسعه، امنیت) طراحی شوند و اطلاعات موردنیاز هر گروه را به‌وضوح نمایش دهند. |
| **حفاظت از داده‌های حساس در لاگ‌ها** | اطلاعات حساس (مانند رمز عبور، توکن‌ها، داده‌های شخصی، Promptهای حساس) نباید در لاگ‌ها ثبت شوند یا باید پنهان (Mask) شوند — مطابق با سند `Security_and_Privacy_Architecture`. |

## ۵. اجزای اصلی معماری مشاهده‌پذیری

معماری مشاهده‌پذیری بر اساس سه رکن اصلی لاگ‌نویسی (Logging)، شاخص‌ها (Metrics) و ردیابی (Tracing) استوار است که هرکدام نقش مشخصی در درک وضعیت سیستم ایفا می‌کنند.

### ۵.۱. ثبت لاگ (Logging)

**هدف:** ثبت رویدادهای مهم سیستم به‌صورت ساخت‌یافته برای عیب‌یابی، ممیزی و تحلیل.

**الزامات:**
- **ساختار:** تمام لاگ‌ها به‌صورت JSON با فیلدهای اجباری: `timestamp`، `service`، `level` (INFO، WARN، ERROR، DEBUG)، `correlation_id`، `user_id` (در صورت وجود)، `tenant_id`، `message`
- **سطوح لاگ:** DEBUG (برای توسعه)، INFO (رویدادهای عادی)، WARN (شرایط غیرعادی اما غیربحرانی)، ERROR (خطاهایی که نیاز به بررسی دارند)
- **چرخش و نگهداری:** لاگ‌ها با سیاست چرخش (Rotation) و دوره نگهداری مشخص (حداقل ۳۰ روز برای لاگ‌های عملیاتی، ۱ سال برای لاگ‌های امنیتی) ذخیره می‌شوند.
- **جمع‌آوری متمرکز:** تمام لاگ‌ها به یک سیستم جمع‌آوری متمرکز (مانند Elasticsearch، Loki) ارسال می‌شوند تا قابل جستجو و تحلیل باشند.

**نمونه لاگ ساخت‌یافته:**
```json
{
  "timestamp": "2026-07-24T10:30:45.123Z",
  "service": "agent-orchestration",
  "level": "ERROR",
  "correlation_id": "req-abc123",
  "user_id": "user-456",
  "tenant_id": "tenant-789",
  "message": "Failed to execute tool: timeout after 30s",
  "tool_name": "github-create-issue",
  "error_code": "TOOL_TIMEOUT"
}
```

---

### ۵.۲. شاخص‌ها (Metrics)

**هدف:** جمع‌آوری شاخص‌های کمی برای پایش عملکرد، ظرفیت و سلامت سیستم.

**دسته‌بندی شاخص‌ها:**

| دسته | شاخص‌های نمونه |
| :--- | :--- |
| **زیرساخت** | مصرف CPU، حافظه، دیسک، شبکه، تعداد Podها، وضعیت Nodeها |
| **سرویس‌ها** | نرخ درخواست (Request Rate)، زمان پاسخ (Latency P50/P95/P99)، نرخ خطا (Error Rate) |
| **API** | تعداد درخواست‌ها بر اساس Endpoint، کد وضعیت HTTP، تأخیر، نرخ محدودشده (Rate Limited) |
| **دانش و Context** | تعداد اسناد پردازش‌شده، زمان نمایه‌سازی (Indexing)، زمان جستجو، تعداد نتایج بازیابی‌شده |
| **مدل‌های هوش مصنوعی** | زمان پاسخ مدل، تعداد توکن مصرفی (ورودی/خروجی)، هزینه، نرخ موفقیت، نرخ جایگزین (Fallback) |
| **Agent و Tool** | تعداد اجرای Agent، تعداد فراخوانی Tool، نرخ موفقیت Tool، زمان اجرا |
| **حافظه** | اندازه حافظه جلسه (Session Memory)، تعداد عملیات خواندن/نوشتن، زمان پاسخ |
| **صف‌های پیام** | طول صف، نرخ تولید/مصرف، تأخیر پیام |

**فرمت شاخص‌ها:** شاخص‌ها در قالبی استاندارد مانند Prometheus Exposition Format با برچسب‌های (Labels) مناسب مانند `service`، `endpoint`، `tenant_id`، `model_provider` جمع‌آوری می‌شوند.

### ۵.۳. ردیابی (Tracing)

**هدف:** ردیابی کامل مسیر اجرای یک درخواست در میان سرویس‌های مختلف برای شناسایی گلوگاه‌ها، خطاها و تأخیرها.

**الزامات:**
- **پشتیبانی از ردیابی توزیع‌شده (Distributed Tracing):** هر درخواست با یک `Trace-ID` و `Span-ID` مشخص در تمام Componentها دنبال می‌شود.
- **ثبت Spanها:** هر Component باید Spanهای مربوط به عملیات خود را (شامل زمان شروع، پایان، مدت زمان، Metadata) ثبت کند.
- **ارتباط با Log و Metrics:** امکان اتصال Traceها به Logها و Metricsهای مرتبط برای مشاهده یکپارچه.
- **پشتیبانی از استانداردها:** پیاده‌سازی بر اساس استاندارد OpenTelemetry برای قابلیت حمل و یکپارچگی با ابزارهای مختلف.

**نمونه مسیر ردیابی:**
```
User Request → API Gateway → Agent Orchestration → Knowledge & Context → Model Management → Agent Orchestration → Action & Tool → Response
```

---

### ۵.۴. داشبوردها (Dashboards)

**هدف:** نمایش بصری وضعیت لحظه‌ای سیستم، سرویس‌ها، منابع، مدل‌ها و Agentها برای تیم‌های عملیاتی و مدیریتی.

**داشبوردهای پیشنهادی:**

| داشبورد | مخاطب | محتوای کلیدی |
| :--- | :--- | :--- |
| **سلامت کل پلتفرم** | مدیریت، عملیات | وضعیت کلی سرویس‌ها، تعداد خطاهای فعال، در دسترس‌پذیری، هشدارهای بحرانی |
| **وضعیت Microserviceها** | تیم عملیات، SRE | تأخیر، نرخ خطا، توان عملیاتی، مصرف منابع برای هر سرویس |
| **وضعیت Agentها و مدل‌ها** | تیم AI، محصول | نرخ موفقیت Agent، زمان پاسخ مدل، هزینه، تعداد درخواست‌ها، جایگزین‌ها |
| **وضعیت زیرساخت داده** | تیم داده، عملیات | وضعیت پایگاه‌های داده، طول صف‌ها، سرعت نمایه‌سازی، حجم داده |
| **امنیت و ممیزی** | تیم امنیت، مدیریت | رویدادهای امنیتی، تلاش‌های دسترسی ناموفق، تغییرات Policy، فعالیت‌های مشکوک |
| **تجربه کاربری** | مدیریت محصول، UX | زمان پاسخ سرتاسری (End‑to‑End)، نرخ رضایت، خطاهای کاربری، درخواست‌های تکراری |

---

### ۵.۵. هشدار (Alerting)

**هدف:** ارسال هشدار هنگام عبور شاخص‌ها از آستانه‌های تعریف‌شده یا وقوع رخدادهای غیرعادی برای اقدام سریع.

**دسته‌بندی هشدارها بر اساس شدت:**

| سطح | توضیح | زمان پاسخ | نمونه |
| :--- | :--- | :--- | :--- |
| **بحرانی (Critical)** | سرویس از کار افتاده یا داده‌ها در خطر هستند | ≤ ۱۵ دقیقه | سرویس اصلی پاسخگو نیست، پایگاه داده از دسترس خارج شده |
| **بالا (High)** | اختلال جدی در عملکرد یا تجربه کاربر | ≤ ۱ ساعت | تأخیر از آستانه عبور کرده، نرخ خطا بالا رفته |
| **متوسط (Medium)** | شرایط غیرعادی که ممکن است به مشکل تبدیل شود | ≤ ۴ ساعت | مصرف CPU بالا، طول صف در حال افزایش |
| **اطلاعاتی (Info)** | رویدادهای مهم اما غیربحرانی | بدون نیاز به اقدام فوری | استقرار جدید، تغییر پیکربندی، شروع/پایان عملیات طولانی |

**الزامات هشدار:**
- هر هشدار باید دارای **مالک مشخص** (تیم یا فرد) برای رسیدگی باشد.
- روش اطلاع‌رسانی (Email، Slack، PagerDuty، SMS) بر اساس شدت تعیین می‌شود.
- از هشدارهای تکراری و بی‌رویه (Alert Fatigue) با استفاده از مکانیزم‌هایی مانند گروه‌بندی (Grouping)، حذف تکراری (Deduplication) و دوره‌های سکوت (Silence Periods) جلوگیری شود.
- هشدارها باید شامل اطلاعات کافی (Correlation‑ID، پیام خطا، زمان، Component) برای شروع سریع عیب‌یابی باشند.

| :--- | :--- | :--- | :--- |

| **تأخیر API (صدک ۹۵)** | زمان پاسخ ۹۵٪ درخواست‌های API | ≤ ۵۰۰ ms | سند `Non_Functional_Requirements_And_SLA` |
| **نرخ خطای API** | درصد درخواست‌های ناموفق (خطای سرور) | ≤ ۰.۵٪ | سند `Non_Functional_Requirements_And_SLA` |
| **زمان پاسخ جستجو** | زمان پاسخ جستجوی معنایی | ≤ ۲ ثانیه | سند `Non_Functional_Requirements_And_SLA` |
| **زمان هماهنگی درخواست AI** | زمان پردازش Orchestration (بدون مدل) | ≤ ۵ ثانیه | سند `Non_Functional_Requirements_And_SLA` |
| **زمان پاسخ مدل** | زمان پاسخ مدل هوش مصنوعی | وابسته به Provider | سند `Non_Functional_Requirements_And_SLA` |
| **نرخ موفقیت اجرای Tool** | درصد اجرای موفق Toolها | ≥ ۹۵٪ | تعریف داخلی |
| **عمق صف** | تعداد پیام‌های در انتظار در صف‌ها | < ۱۰۰۰ | تعریف داخلی |
| **هزینه به‌ازای هر درخواست** | هزینه متوسط هر درخواست (مدل + زیرساخت) | قابل پایش | سند `Architecture_Overview_Enterprise_AI_Platform` |

## ۷. مشاهده‌پذیری سرویس‌های هوش مصنوعی (AI Observability)

با توجه به ماهیت خاص مدل‌های هوش مصنوعی و Agentها، مشاهده‌پذیری این بخش نیازمند اطلاعات ویژه‌ای است:

**اطلاعات قابل ثبت برای هر درخواست AI:**

| فیلد | توضیح |
| :--- | :--- |
| **Prompt** | ورودی کاربر یا سیستم به مدل (با رعایت امنیت و پنهان‌سازی اطلاعات حساس) |
| **Context** | دانش و Context ارسال‌شده به مدل (شامل منابع و Metadata) |
| **Model Selected** | مدل استفاده‌شده (نام، Provider، نسخه) |
| **Model Configuration** | پارامترهای مدل (دما، حداکثر توکن، Top‑P و غیره) |
| **Tokens Used** | تعداد توکن ورودی و خروجی |
| **Response** | خروجی مدل |
| **Tools Executed** | فهرست Toolهای فراخوانی‌شده و نتایج آن‌ها |
| **Duration** | زمان کل پردازش |
| **Cost** | هزینه تخمینی بر اساس مصرف توکن و نرخ Provider |
| **Success/Failure** | وضعیت نهایی |
| **Error Details** | در صورت خطا، جزئیات کامل |
| **Agent Chain** | در صورت چند‑Agent، زنجیره Agentهای درگیر و تصمیمات آن‌ها |

**نکته امنیتی:** اطلاعات حساس (اطلاعات شخصی قابل شناسایی، اسرار، داده‌های محرمانه) قبل از ثبت در لاگ‌ها پنهان یا حذف می‌شوند — مطابق با سند `Security_and_Privacy_Architecture`.

## ۸. مدیریت هشدارها و پاسخ به حوادث (Incident Response)

فرآیند مدیریت هشدارها و پاسخ به حوادث بر اساس سطوح شدت تعریف‌شده در بخش ۵.۵ انجام می‌شود:

| مرحله | توضیح |
| :--- | :--- |
| **تشخیص** | شناسایی هشدار از طریق سیستم Monitoring و Alerting. |
| **تحلیل اولیه** | بررسی هشدار، تعیین شدت واقعی، جمع‌آوری اطلاعات زمینه‌ای (لاگ‌ها، Traceها، Metrics). |
| **اعلام** | اطلاع‌رسانی به تیم‌های مربوطه از طریق کانال‌های تعریف‌شده. |
| **بررسی و تشخیص علت** | تحلیل عمیق‌تر برای یافتن علت ریشه‌ای با استفاده از ابزارهای مشاهده‌پذیری. |
| **اقدام و بازیابی** | اجرای اقدامات اصلاحی (مانند مقیاس‌دهی، راه‌اندازی مجدد، تغییر پیکربندی، بازگشت به نسخه قبلی). |
| **ثبت و مستندسازی** | ثبت جزئیات حادثه، زمان‌بندی، اقدامات انجام‌شده و درس‌آموخته‌ها. |
| **پیگیری** | اطمینان از رفع کامل مشکل و اجرای اقدامات پیشگیرانه برای جلوگیری از تکرار. |

**زمان پاسخ:** مطابق با SLA تعریف‌شده در سند `Non_Functional_Requirements_And_SLA` (حادثه بحرانی < ۱۵ دقیقه، حادثه با اولویت بالا < ۱ ساعت).

## ۹. نگهداری داده‌های پایش (Data Retention)

برای هر نوع داده پایش، سیاست نگهداری زیر اعمال می‌شود:

| نوع داده | مدت نگهداری | دسترسی | نحوه آرشیو |
| :--- | :--- | :--- | :--- |
| **لاگ‌های عملیاتی (INFO، DEBUG)** | ۳۰ روز | تیم‌های توسعه و عملیات | حذف خودکار پس از ۳۰ روز |
| **لاگ‌های خطا (ERROR، WARN)** | ۹۰ روز | تیم‌های توسعه و عملیات | انتقال به ذخیره‌سازی سرد پس از ۳۰ روز |
| **لاگ‌های امنیتی و ممیزی** | ۱ سال (یا بیشتر بر اساس نیاز قانونی) | تیم امنیت، ممیزی | آرشیو در ذخیره‌سازی غیرقابل‌تغییر |
| **شاخص‌ها (Metrics)** | ۳۰ روز (جزئی) / ۱ سال (خلاصه) | تمام تیم‌ها | کاهش دقت (Downsampling) پس از ۳۰ روز |
| **ردیابی‌ها (Traceها)** | ۷ روز | تیم‌های توسعه و عملیات | حذف خودکار پس از ۷ روز |
| **هشدارها و حوادث** | ۱ سال | مدیریت، تیم عملیات | نگهداری کامل برای تحلیل روند |

## ۱۰. ابزارها و فناوری‌های پیشنهادی (پیشنهادی، قابل تغییر بر اساس نیاز سازمان)

| حوزه | ابزارهای پیشنهادی |
| :--- | :--- |
| **جمع‌آوری شاخص‌ها** | Prometheus، OpenTelemetry Collector |
| **ذخیره‌سازی و پرس‌وجوی شاخص‌ها** | Prometheus (با Thanos یا Cortex برای ذخیره‌سازی طولانی‌مدت) |
| **داشبورد** | Grafana |
| **جمع‌آوری و ذخیره‌سازی لاگ** | Elasticsearch، Loki |
| **تحلیل لاگ** | Kibana، Grafana Explore |
| **ردیابی توزیع‌شده** | Jaeger، Tempo، OpenTelemetry Collector |
| **هشدار** | Alertmanager، Grafana Alerting |
| **نظارت زیرساخت** | Kubernetes Metrics Server، Node Exporter، cAdvisor |

**توجه:** انتخاب ابزارها با توجه به زیرساخت موجود سازمان و نیازهای خاص قابل تنظیم است. معماری باید امکان جایگزینی ابزارها را بدون تغییر در منطق اصلی (Core Logic) فراهم کند.

## ۱۲. نتیجه‌گیری

معماری نظارت و مشاهده‌پذیری یکی از ارکان اصلی بهره‌برداری پایدار، مطمئن و مقیاس‌پذیر از پلتفرم است. این سند چارچوبی جامع برای جمع‌آوری، تحلیل و نمایش داده‌های عملیاتی فراهم می‌کند تا کیفیت سرویس، عملکرد سامانه و قابلیت اطمینان پلتفرم به‌صورت مستمر ارزیابی و بهبود یابد.

پیاده‌سازی مؤثر این معماری مستلزم همکاری نزدیک تیم‌های توسعه، عملیات، SRE و امنیت است. تمام Componentها باید از ابتدا با قابلیت‌های مشاهده‌پذیری طراحی شوند و داده‌های تولیدی آن‌ها به‌صورت استاندارد و متمرکز جمع‌آوری و تحلیل شوند. با تکیه بر این زیرساخت، تیم‌ها قادر خواهند بود مشکلات را سریع‌تر شناسایی و رفع کنند، ظرفیت را دقیق‌تر برنامه‌ریزی کنند و کیفیت سرویس را به‌طور مستمر ارتقا دهند.

**مسئولیت به‌روزرسانی:** تیم عملیات و SRE به همراه معماران ارشد مسئول بازبینی دوره‌ای این سند، به‌روزرسانی شاخص‌ها و هشدارها بر اساس تغییرات سیستم و نیازهای جدید، و ارزیابی اثربخشی زیرساخت مشاهده‌پذیری هستند.

**ثبات سند:** این سند باید با تغییرات در معماری، Componentها و نیازهای عملیاتی هم‌گام باشد. هر تغییر در ساختار پلتفرم باید از منظر مشاهده‌پذیری بررسی شده و در صورت نیاز این سند به‌روزرسانی شود.
