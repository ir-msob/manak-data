# معماری دامنه دانش و زمینه (Knowledge & Context Domain Architecture)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.0

**وضعیت:** پیش‌نویس

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف معماری دامنه **دانش و زمینه** (Knowledge & Context Domain) تدوین شده است. این دامنه مسئول مدیریت چرخه عمر دانش سازمانی، تولید نمایش‌های عددی (Embedding)، جستجوی معنایی (Semantic Search)، بازیابی اطلاعات (Retrieval) و مونتاژ زمینه (Context Assembly) برای استفاده در فرآیندهای استدلال و تصمیم‌گیری هوش مصنوعی است.

هدف این سند ایجاد چارچوبی استاندارد، مقیاس‌پذیر، کارآمد و قابل اعتماد برای تبدیل داده‌های خام سازمانی به دانش قابل استفاده و زمینه‌های دقیق و مرتبط برای مدل‌های هوش مصنوعی است. این سند به‌عنوان مرجع اصلی برای تیم‌های توسعه، معماری، مهندسی داده و هوش مصنوعی در زمینه طراحی و پیاده‌سازی زیرساخت دانش و زمینه پلتفرم عمل می‌کند.

---

## ۲. دامنه سند

این سند تمام جنبه‌های مرتبط با دامنه دانش و زمینه را پوشش می‌دهد و شامل موارد زیر است:

- **Data Ingestion:** دریافت و پردازش داده از منابع مختلف سازمانی
- **Document Processing:** پردازش اسناد (PDF، Word، Excel، HTML، Markdown و غیره)
- **Chunking:** تقسیم متون به بخش‌های کوچک‌تر و معنادار
- **Metadata Extraction:** استخراج فراداده از محتوا و منابع
- **Embedding Generation:** تولید نمایش‌های عددی (Vector) از متن
- **Indexing:** نمایه‌سازی دانش در پایگاه‌های داده برداری و جستجو
- **مصرف گراف دانش:** استفاده از گراف دانش (که در دامنه مدیریت دانش تعریف و نگهداری می‌شود) برای غنی‌سازی بازیابی و Context Assembly
- **Semantic Search:** جستجوی مبتنی بر معنا و مفهوم
- **Hybrid Search:** ترکیب جستجوی برداری و کلیدواژه‌ای
- **Context Assembly:** مونتاژ زمینه مناسب برای مدل‌های هوش مصنوعی
- **RAG (Retrieval-Augmented Generation):** بازیابی دانش برای تولید پاسخ
- **Data Versioning:** نسخه‌بندی و رهگیری تغییرات دانش
- **Knowledge Lifecycle Management:** مدیریت چرخه عمر دانش (ایجاد، به‌روزرسانی، انقضا، حذف)

جزئیات پیاده‌سازی فنی و کدنویسی در اسناد سطح پایین‌تر تدوین می‌شوند. این سند صرفاً **معماری سطح بالا و اصول طراحی** دامنه را تعریف می‌کند.

## ۳. اصول طراحی دامنه

| اصل | توضیح |
| :--- | :--- |
| **Knowledge First (دانش محور)** | داده خام ارزش مستقیم ندارد؛ هدف نهایی تبدیل آن به دانش قابل استفاده برای استدلال و تصمیم‌گیری است. |
| **Context Quality (کیفیت زمینه)** | کیفیت خروجی مدل‌های هوش مصنوعی به کیفیت زمینه دریافتی وابسته است. سرمایه‌گذاری بر کیفیت بازیابی و مونتاژ زمینه در اولویت است. |
| **Traceability (قابلیت ردیابی)** | هر دانش و هر زمینه باید تا منبع اصلی خود (Source) قابل ردیابی باشد تا شفافیت و اعتمادپذیری تضمین شود. |
| **Metadata Driven (فراداده‌محور)** | رفتار سیستم (دسترسی، بازیابی، اعتماد) بر اساس فراداده هر شیء تعیین می‌شود، نه نوع فایل یا منبع آن. |
| **Multi-Source (چندمنبعی)** | یک موجودیت دانش می‌تواند از چند منبع مختلف تغذیه شود؛ مدل باید این ترکیب را پشتیبانی کند. |
| **Semantic Enrichment (غنی‌سازی معنایی)** | دانش باید با اطلاعات معنایی (موجودیت‌ها، روابط، مفاهیم) غنی‌سازی شود تا جستجو و بازیابی دقیق‌تر انجام شود. |
| **Scalability (مقیاس‌پذیری)** | زیرساخت دانش باید توانایی مدیریت میلیون‌ها سند و میلیاردها بردار عددی را داشته باشد. |
| **Real-Time Readiness (آمادگی بلادرنگ)** | دانش باید در کوتاه‌ترین زمان ممکن از زمان دریافت، قابل بازیابی و استفاده باشد (Near Real-Time). |
| **Knowledge Freshness (تازگی دانش)** | دانش باید متناسب با نوع منبع و SLA تعریف‌شده در کوتاه‌ترین زمان ممکن به‌روزرسانی شود تا پاسخ‌های تولیدشده بر اساس جدیدترین اطلاعات باشند. |
| **Source Trust (اعتماد به منبع)** | هر منبع دانش باید دارای سطح اعتماد (Trust Level) باشد تا در رتبه‌بندی نتایج و مونتاژ Context مورد استفاده قرار گیرد. |
| **Knowledge Reusability (قابلیت استفاده مجدد)** | دانش استخراج‌شده باید مستقل از سناریوی استفاده ذخیره شود تا در کاربردهای مختلف مجدداً قابل استفاده باشد. |
| **Explainable Retrieval (بازیابی قابل تبیین)** | دلیل انتخاب هر بخش از دانش باید قابل نمایش باشد تا امکان بررسی و اعتماد به پاسخ فراهم شود. |
| **Model Agnostic Knowledge (استقلال از مدل)** | ساختار دانش و Context نباید وابسته به یک مدل زبانی خاص باشد و باید برای مدل‌های مختلف قابل استفاده باشد. |

## ۴. مؤلفه‌های اصلی دامنه

### ۴.۱. Data Ingestion (دریافت داده)

**مسئولیت:** دریافت داده از منابع مختلف سازمانی و آماده‌سازی آن برای پردازش.

**وظایف کلیدی:**

- **اتصال به منابع:** اتصال به منابع داده از طریق Connectorها
- **دریافت داده:** دریافت داده به‌صورت Batch، Streaming یا Event-Driven
- **اعتبارسنجی اولیه:** بررسی فرمت،完整性 و صحت داده
- **نرمال‌سازی:** تبدیل داده به فرمت استاندارد داخلی
- **ثبت منبع:** ثبت اطلاعات منبع برای ردیابی

**منابع داده پشتیبانی‌شده:**

| منبع | توضیح |
| :--- | :--- |
| **فایل‌ها و اسناد** | PDF، Word، Excel، PPT، HTML، Markdown، متن ساده |
| **پایگاه‌های داده** | SQL و NoSQL (PostgreSQL، MongoDB، Elasticsearch) |
| **Wiki و Knowledge Base** | Confluence، Notion، MediaWiki |
| **مخزن کد** | GitHub، GitLab، Bitbucket |
| **APIها** | REST API، GraphQL، SOAP |
| **سیستم‌های سازمانی** | ERP، CRM، Jira، ServiceNow |

---

### ۴.۲. Document Processing (پردازش اسناد)

**مسئولیت:** پردازش و استخراج محتوای متنی از اسناد با فرمت‌های مختلف.

**وظایف کلیدی:**

- **استخراج متن:** استخراج متن از فایل‌های PDF، Word، Excel و غیره
- **تشخیص ساختار:** تشخیص بخش‌ها، پاراگراف‌ها، جداول، تصاویر و عناوین
- **استخراج فراداده:** استخراج Metadata (عنوان، نویسنده، تاریخ، کلیدواژه‌ها)
- **تبدیل فرمت:** تبدیل فرمت‌های مختلف به فرمت استاندارد متنی
- **پاک‌سازی داده:** حذف نویز، کاراکترهای اضافی و فرمت‌های غیرضروری

**ابزارهای پیشنهادی:**

| ابزار | کاربرد |
| :--- | :--- |
| **Apache Tika** | استخراج متن و Metadata از انواع فایل‌ها |
| **PDFPlumber / PyPDF2** | استخراج متن از فایل‌های PDF |
| **python-docx** | استخراج متن از فایل‌های Word |
| **openpyxl** | استخراج متن از فایل‌های Excel |
| **BeautifulSoup** | استخراج متن از فایل‌های HTML |

---

### ۴.۳. Chunking (تقسیم‌بندی متن)

**مسئولیت:** تقسیم اسناد بزرگ به بخش‌های کوچک‌تر، معنادار و قابل پردازش.

**وظایف کلیدی:**

- **تقسیم بر اساس ساختار:** تقسیم بر اساس پاراگراف‌ها، عناوین، بخش‌ها
- **تقسیم بر اساس اندازه:** تقسیم به Chunkهای با اندازه مشخص (Token یا کاراکتر)
- **تقسیم بر اساس معنا:** تقسیم بر اساس مرزهای معنایی (جملات کامل، مفاهیم)
- **Overlap:** ایجاد همپوشانی بین Chunkها برای حفظ پیوستگی معنایی
- **تعیین اندازه بهینه:** انتخاب اندازه Chunk بر اساس نوع محتوا و مدل

**راهبردهای Chunking:**

| راهبرد | توضیح | کاربرد |
| :--- | :--- | :--- |
| **Fixed‑Size** | تقسیم بر اساس تعداد Token یا کاراکتر ثابت | محتوای ساده و بدون ساختار |
| **Semantic** | تقسیم بر اساس مرزهای معنایی (جمله، پاراگراف) | محتوای ساختاریافته و معنادار |
| **Hierarchical** | تقسیم سلسله‌مراتبی با بخش‌های بزرگ و کوچک | اسناد با ساختار درختی |
| **Document‑Aware** | تقسیم با آگاهی از ساختار سند (عنوان، بخش‌ها) | اسناد با ساختار مشخص |

---

#### ۴.۳.۱. راهبرد انتخاب Chunk (Chunk Selection Strategy)

انتخاب اندازه و روش تقسیم‌بندی متن باید بر اساس نوع محتوا انجام شود.

| نوع محتوا | راهبرد پیشنهادی |
| :--- | :--- |
| مستندات فنی | Document-Aware همراه با Overlap |
| کد منبع | تقسیم بر اساس ساختار فایل، کلاس، تابع یا ماژول |
| اسناد حقوقی | تقسیم بر اساس ماده، بند و تبصره |
| صفحات Wiki | تقسیم بر اساس Headingها |
| مستندات API | تقسیم بر اساس Endpoint یا Resource |
| ایمیل و مکاتبات | تقسیم بر اساس Thread یا پیام مستقل |

در تمام حالت‌ها باید پیوستگی معنایی اطلاعات حفظ شود.

### ۴.۴. Embedding Generation (تولید نمایش عددی)

**مسئولیت:** تبدیل متن به نمایش‌های عددی (Vectors) برای جستجوی معنایی.

**وظایف کلیدی:**

- **انتخاب مدل:** انتخاب مدل Embedding مناسب بر اساس نیاز
- **تولید Embedding:** تولید بردار عددی برای هر Chunk
- **اعتبارسنجی:** بررسی کیفیت Embedding تولیدشده
- **ذخیره‌سازی:** ذخیره Embedding در Vector Database
- **به‌روزرسانی:** بازتولید Embedding در صورت تغییر محتوا

**الزامات مدیریت Embedding**

- نسخه‌بندی مدل‌های Embedding
- ثبت نسخه مدل برای هر Vector
- پشتیبانی از بازتولید Embeddingها
- امکان استفاده هم‌زمان از چند مدل
- اعتبارسنجی کیفیت Embedding
- ثبت زمان تولید Embedding

**مدل‌های Embedding پیشنهادی:**

| مدل | کاربرد | ابعاد | ویژگی‌ها |
| :--- | :--- | :--- | :--- |
| **text‑embedding‑3‑small** | جستجوی عمومی | ۱۵۳۶ | دقت بالا، سرعت خوب |
| **text‑embedding‑3‑large** | جستجوی دقیق | ۳۰۷۲ | دقت بسیار بالا |
| **BAAI/bge‑large** | جستجوی چندزبانه | ۱۰۲۴ | پشتیبانی از فارسی |
| **sentence‑transformers/all‑MiniLM‑L6‑v2** | جستجوی سبک | ۳۸۴ | سرعت بالا، حجم کم |
| **Cohere/embed‑english‑v3.0** | جستجوی سازمانی | ۱۰۲۴ | کیفیت بالا، سفارشی‌سازی |

### ۴.۵. Indexing (نمایه‌سازی)

**مسئولیت:** ذخیره و سازماندهی دانش و Embedding‌ها برای بازیابی سریع.

**وظایف کلیدی:**

- **ذخیره‌سازی در Vector Database:** ذخیره Embedding‌ها با Metadata مرتبط
- **ایجاد Index:** ایجاد Indexهای کارآمد برای جستجوی سریع
- **مدیریت Metadata:** ذخیره Metadata برای فیلتر کردن و جستجوی ترکیبی
- **نسخه‌بندی:** نگهداری نسخه‌های مختلف Knowledge
- **به‌روزرسانی:** بروزرسانی Index در صورت تغییر محتوا

**الزامات نمایه‌سازی**

- پشتیبانی از چند Index برای یک دانش
- Reindex بدون توقف سرویس
- حذف تدریجی Indexهای قدیمی
- مدیریت Fragmentation
- بهینه‌سازی خودکار Index
- نگهداری آمار استفاده از Indexها

**پایگاه‌های داده پیشنهادی:**

| پایگاه داده | کاربرد | ویژگی‌ها |
| :--- | :--- | :--- |
| **Milvus** | جستجوی برداری در مقیاس بزرگ | مقیاس‌پذیری بالا، Indexهای پیشرفته |
| **Qdrant** | جستجوی برداری با فیلتر | فیلتر پیشرفته، API آسان |
| **Elasticsearch** | جستجوی ترکیبی (برداری + کلیدواژه) | Hybrid Search، قابلیت‌های غنی |
| **Pinecone** | جستجوی برداری مدیریت‌شده | سادگی، مقیاس‌پذیری خودکار |
| **Weaviate** | جستجوی برداری با GraphQL | سرعت بالا، انعطاف‌پذیری |

#### ۴.۵.۱. مدیریت نسخه دانش (Knowledge Version Management)

> **ارجاع:** تعریف پایه Semantic Versioning و Deprecation در `Versioning_And_Compatibility_Strategy` آمده است. جدول زیر فیلدهای خاص نسخه‌بندی دانش را مشخص می‌کند.

هر واحد دانش باید مستقل از نسخه‌های قبلی نگهداری شود.

برای هر نسخه اطلاعات زیر ثبت می‌شود:

- شناسه نسخه
- زمان ایجاد
- منبع تغییر
- دلیل تغییر
- نسخه Schema
- نسخه Embedding
- وضعیت انتشار
- نسخه فعال
- نسخه جایگزین‌شده

این اطلاعات امکان بازگشت به نسخه‌های قبلی و رهگیری تغییرات دانش را فراهم می‌کند.

### ۴.۶. مصرف گراف دانش (Knowledge Graph Consumption)

**مسئولیت:** این دامنه مالک گراف دانش نیست. مدل هستان‌شناسی (Ontology)، انواع موجودیت (Person، Organization، Document، Service، Process، Rule)، انواع رابطه (references، depends_on، owns، generated_by، related_to) و پیاده‌سازی موتور ذخیره‌سازی/پرس‌وجوی گراف، به‌طور کامل در دامنه مدیریت دانش (`Knowledge_Management_Domain_Architecture`) تعریف و نگهداری می‌شوند. این مدل، **Shared Kernel رسمی** بین دو دامنه است و طرحواره مرجع آن در سند `Data_Model_And_Knowledge_Schema_Overview` (بخش ۶) ثبت شده است.

**وظایف این دامنه در ارتباط با گراف دانش:**

- **درخواست پرس‌وجو:** ارسال پرس‌وجوهای گراف (بر اساس نیاز Retrieval) به `Graph Query Service` تعریف‌شده در دامنه مدیریت دانش
- **دریافت نتیجه:** دریافت موجودیت‌ها و روابط مرتبط برای استفاده در Hybrid Retrieval و Context Assembly (بخش ۴.۹)
- **ارسال محتوای خام برای استخراج:** در صورتی که Chunking یک سند موجودیت/رابطه جدیدی تولید کند، محتوای خام (نه موجودیت نهایی) برای استخراج به `Entity Extractor` و `Relation Extractor` در دامنه مدیریت دانش ارسال می‌شود؛ استخراج، اعتبارسنجی و ثبت نهایی در گراف همواره در همان دامنه انجام می‌شود.

**مرز مسئولیت:** این دامنه هیچ Entity Type یا Relation Type مستقلی تعریف نمی‌کند، هیچ پایگاه داده گرافی مستقل ندارد و منطق استخراج موجودیت/رابطه از متن را در خود پیاده‌سازی نمی‌کند.

> **ارجاع:** برای جزئیات کامل Ontology Manager، Knowledge Graph Engine، Entity/Relation Extractor و Graph Query Service، به سند `Knowledge_Management_Domain_Architecture` مراجعه کنید.

### ۴.۷. Retrieval (بازیابی دانش)

**مسئولیت:** بازیابی دانش مرتبط با درخواست از منابع مختلف.

**وظایف کلیدی:**

- **Semantic Search:** جستجوی مبتنی بر معنا با استفاده از Embedding
- **Keyword Search:** جستجوی مبتنی بر کلیدواژه (برای Hybrid Search)
- **Hybrid Search:** ترکیب جستجوی معنایی و کلیدواژه‌ای
- **Graph Query:** پرس‌وجوی گراف دانش برای بازیابی مبتنی بر رابطه
- **Filtering:** فیلتر کردن نتایج بر اساس Metadata (زمان، نوع، منبع، دسترسی)
- **Reranking:** مرتب‌سازی مجدد نتایج بر اساس کیفیت و ارتباط

**الگوریتم‌های بازیابی:**

| الگوریتم | توضیح | کاربرد |
| :--- | :--- | :--- |
| **Cosine Similarity** | شباهت کسینوسی بین بردارها | جستجوی معنایی پایه |
| **HNSW** | جستجوی تقریبی نزدیک‌ترین همسایه | سرعت بالا در مقیاس بزرگ |
| **BM25** | جستجوی کلیدواژه‌ای مبتنی بر TF‑IDF | جستجوی متنی |
| **RRF (Reciprocal Rank Fusion)** | ترکیب نتایج چند روش جستجو | Hybrid Search |
| **Query Expansion** | گسترش پرس‌وجو با مترادف‌ها | بهبود Recall |

---

#### ۴.۷.۱. راهبرد رتبه‌بندی نتایج (Retrieval Ranking Strategy)

نتایج بازیابی بر اساس مجموعه‌ای از معیارها امتیازدهی و رتبه‌بندی می‌شوند.

معیارهای رتبه‌بندی شامل:

- شباهت معنایی
- امتیاز BM25
- سطح اعتماد منبع
- تازگی دانش
- کیفیت سند
- سطح دسترسی کاربر
- ارتباط با موضوع
- امتیاز Reranker
- میزان استفاده گذشته

### ۴.۸. RAG (Retrieval-Augmented Generation)

**مسئولیت:** تولید پاسخ با استفاده از دانش بازیابی‌شده و مدل‌های زبانی.

**وظایف کلیدی:**

- **بازیابی:** بازیابی دانش مرتبط با پرس‌وجو
- **مونتاژ Context:** ترکیب دانش بازیابی‌شده در Context
- **تولید پاسخ:** ارسال Context به مدل برای تولید پاسخ
- **اعتبارسنجی:** اعتبارسنجی پاسخ با استفاده از منابع
- **منبع‌یابی:** نمایش منابع استفاده‌شده در پاسخ

**جریان RAG:**

```text
User Query
        │
        ▼
Retriever (Semantic + Keyword + Graph)
        │
        ▼
Knowledge (Documents, Chunks, Entities)
        │
        ▼
Context Assembly
        │
        ├── Add Knowledge (Chunks, Metadata)
        │
        ├── Add Memory (Session, Long-Term)
        │
        ├── Add Policies (Security, Governance)
        │
        ▼
Model (LLM)
        │
        ▼
Response Generation
        │
        ▼
Source Attribution (Show Sources)
```

---

### ۴.۹. Context Assembly (مونتاژ زمینه)

**مسئولیت:** ترکیب اطلاعات مختلف برای تولید زمینه مناسب برای مدل‌های هوش مصنوعی.

**وظایف کلیدی:**

- **جمع‌آوری منابع:** جمع‌آوری دانش از منابع مختلف (Knowledge، Memory، Policies، Tools)
- **ترکیب هوشمند:** ترکیب اطلاعات بر اساس اولویت، ارتباط و زمان
- **مدیریت اندازه:** مدیریت اندازه Context برای جلوگیری از پر شدن پنجره Context
- **پاک‌سازی:** حذف اطلاعات تکراری یا غیرمرتبط
- **ساختاردهی:** سازماندهی Context در قالب قابل فهم برای مدل

**الزامات مونتاژ Context**

- حذف اطلاعات متناقض
- حذف اطلاعات تکراری
- اولویت‌بندی اطلاعات جدیدتر
- رعایت محدودیت Token
- رعایت سیاست‌های امنیتی
- رعایت سطح دسترسی کاربر
- حفظ ترتیب منطقی اطلاعات

**منابع Context:**

| منبع | توضیح |
| :--- | :--- |
| **Relevant Knowledge** | دانش بازیابی‌شده از Knowledge & Context Engine |
| **Memory** | تاریخچه و تجربیات مرتبط از Memory Management Engine |
| **Policies** | محدودیت‌های Governance روی داده قابل استفاده |
| **Tools** | فهرست Toolهای در دسترس برای Task |
| **User Information** | اطلاعات کاربر (نقش، دسترسی، ترجیحات) |
| **System Instructions** | دستورالعمل‌های سیستمی برای هدایت مدل |

## ۵. جریان پردازش دانش (Knowledge Processing Flow)

جریان کامل پردازش دانش از دریافت تا بازیابی:

```text
Source Data
        │
        ▼
Data Ingestion
        │
        ├── Receive from Connector
        │
        ├── Validate & Normalize
        │
        ▼
Document Processing
        │
        ├── Extract Text & Metadata
        │
        ├── Clean & Prepare
        │
        ▼
Chunking
        │
        ├── Split into Meaningful Chunks
        │
        ├── Add Overlap
        │
        ▼
Metadata Extraction
        │
        ├── Extract Entities & Relations
        │
        ├── Add Classification & Tags
        │
        ▼
Embedding Generation
        │
        ├── Select Model
        │
        ├── Generate Vector
        │
        ▼
Indexing
        │
        ├── Store in Vector DB
        │
        ├── Store Metadata
        │
        ├── Update Knowledge Graph
        │
        ▼
Available for Retrieval
        │
        ├── Semantic Search
        │
        ├── Hybrid Search
        │
        ├── Graph Query
        │
        ▼
Context Assembly → Model
```

## ۱۰. نتیجه‌گیری

دامنه **دانش و زمینه** به‌عنوان **قلب دانشی پلتفرم**، نقش حیاتی در تبدیل داده‌های خام سازمانی به دانش قابل استفاده و زمینه‌های دقیق برای مدل‌های هوش مصنوعی ایفا می‌کند. معماری تعریف‌شده در این سند، چارچوبی استاندارد، مقیاس‌پذیر، کارآمد و قابل اعتماد برای مدیریت چرخه عمر دانش، تولید Embedding، جستجوی معنایی و مونتاژ Context فراهم می‌آورد.

رعایت اصول طراحی (Knowledge First، Context Quality، Traceability، Metadata Driven، Semantic Enrichment) و پیاده‌سازی مؤلفه‌های کلیدی (Ingestion، Processing، Chunking، Embedding، Indexing، Retrieval، RAG، Context Assembly) تضمین می‌کند که پلتفرم بتواند دانش سازمانی را به‌صورت مؤثر مدیریت کرده و زمینه‌های دقیق و قابل اعتمادی برای مدل‌های هوش مصنوعی تولید کند.

**مسئولیت به‌روزرسانی:** تیم معماری به همراه تیم‌های توسعه، مهندسی داده و هوش مصنوعی مسئول بازبینی دوره‌ای این سند، به‌روزرسانی آن بر اساس تغییرات نیازمندی‌های دانش، الگوریتم‌های جدید جستجو و بازخورد تیم‌های پیاده‌سازی هستند.

**ثبات سند:** این سند باید با تغییرات در معماری کلان، فناوری‌های دانش و نیازمندی‌های هوش مصنوعی هم‌گام باشد. هر تغییر در فرآیندهای دانش و زمینه باید در این سند منعکس شود تا سایر اسناد معماری و طراحی نیز به‌روزرسانی شوند.
