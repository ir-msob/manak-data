# حاکمیت داده و انطباق (Data Governance and Compliance)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.1

**وضعیت:** پیش‌نویس بازبینی‌شده

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف چارچوب حاکمیت داده (Data Governance) و انطباق (Compliance) پلتفرم تدوین شده است. هدف آن اطمینان از مدیریت صحیح داده‌ها در کل چرخه عمر، حفظ کیفیت، امنیت، قابلیت اعتماد، دسترس‌پذیری و رعایت الزامات قانونی و سازمانی است.

حاکمیت داده مجموعه‌ای از سیاست‌ها، فرآیندها، نقش‌ها و استانداردهایی است که نحوه ایجاد، نگهداری، استفاده، اشتراک‌گذاری و حذف داده‌ها را کنترل می‌کند. این سند به‌عنوان مرجع اصلی برای تمام تیم‌های محصول، توسعه، عملیات، امنیت و حاکمیت داده در زمینه مدیریت صحیح داده‌ها عمل می‌کند.

## ۲. دامنه سند

این سند تمام داده‌های تولید، دریافت، پردازش و ذخیره‌شده در پلتفرم را پوشش می‌دهد:

| نوع داده | نمونه‌ها |
| :--- | :--- |
| **داده‌های ساخت‌یافته (Structured Data)** | جداول پایگاه داده، فراداده (Metadata)، پیکربندی‌ها، وضعیت جلسات (Session State) |
| **داده‌های نیمه‌ساخت‌یافته (Semi-Structured Data)** | فایل‌های JSON، XML، لاگ‌های ساخت‌یافته |
| **داده‌های غیرساخت‌یافته (Unstructured Data)** | اسناد (PDF، Word، Excel، HTML)، ایمیل‌ها، ویکی‌ها، مخزن‌های کد |
| **داده‌های برداری (Embedding Vectors)** | بردارهای عددی تولیدشده از محتوا برای جستجوی معنایی (Semantic Search) |
| **حافظه گفتگو (Conversation Memory)** | تاریخچه مکالمات، حافظه جلسه (Session Memory)، حافظه بلندمدت (Long-Term Memory)، حافظه رویدادمحور (Episodic Memory) |
| **لاگ‌ها و داده‌های ممیزی (Logs & Audit Data)** | لاگ‌های سیستمی، مسیر حسابرسی (Audit Trail)، ردیابی‌ها (Traces) |
| **داده‌های هوش مصنوعی (AI Data)** | پرامپت‌ها (Prompts)، زمینه‌ها (Contexts)، خروجی مدل‌ها، توکن مصرفی، هزینه‌ها |
| **داده‌های حساس و شخصی (Sensitive & Personal Data)** | اطلاعات شناسایی‌کننده کاربران (PII)، اعتبارنامه‌ها، اسرار سازمانی |

## ۳. اهداف حاکمیت داده

| هدف | توضیح |
| :--- | :--- |
| **ایجاد مرجع واحد برای مدیریت داده** | تعریف استانداردها، سیاست‌ها و فرآیندهای یکسان برای تمام داده‌های پلتفرم |
| **تضمین کیفیت داده (Data Quality)** | اطمینان از صحت، کامل بودن، سازگاری و به‌روز بودن داده‌ها در تمام مراحل چرخه عمر |
| **حفاظت از داده‌های حساس** | اعمال کنترل‌های امنیتی و حریم خصوصی برای جلوگیری از دسترسی غیرمجاز و نشت داده |
| **تعریف مسئولیت‌ها** | شفاف‌سازی نقش‌ها و مسئولیت‌های افراد و تیم‌ها در مدیریت داده |
| **استانداردسازی مدیریت داده** | ایجاد فرآیندهای یکسان برای ایجاد، نگهداری، اشتراک‌گذاری و حذف داده |
| **رعایت الزامات قانونی** | انطباق با قوانین و مقررات مرتبط با داده (مانند GDPR، HIPAA، قوانین داخلی) |
| **افزایش اعتماد به داده‌ها** | ایجاد اطمینان در کاربران و سرویس‌ها نسبت به صحت، امنیت و قابلیت استفاده از داده‌ها |

## ۴. اصول حاکمیت داده

| اصل | توضیح |
| :--- | :--- |
| **داده به‌عنوان دارایی سازمان (Data as an Asset)** | داده‌ها یک دارایی ارزشمند سازمان هستند و باید با همان دقت و توجهی مدیریت شوند که سایر دارایی‌های حیاتی |
| **مرجع واحد حقیقت (Single Source of Truth)** | هر داده باید در یک مکان مشخص و معتبر نگهداری شود تا از تناقض و ابهام جلوگیری شود |
| **حداقل سطح دسترسی (Least Privilege)** | هر کاربر، سرویس یا Agent فقط به حداقل داده‌های لازم برای انجام وظیفه خود دسترسی دارد |
| **مالکیت مشخص داده (Data Ownership)** | هر مجموعه داده دارای مالک مشخص (Data Owner) است که مسئولیت ارزش، کیفیت و سیاست‌های آن را بر عهده دارد |
| **مدیریت چرخه عمر داده (Data Lifecycle Management)** | داده‌ها از لحظه ایجاد تا حذف، در تمام مراحل با سیاست‌های مشخص مدیریت می‌شوند |
| **حریم خصوصی از ابتدای طراحی (Privacy by Design)** | ملاحظات حریم خصوصی در طراحی معماری و پیاده‌سازی تمام Componentها لحاظ می‌شود |
| **کیفیت به‌عنوان اصل پایه (Quality by Default)** | کیفیت داده در تمام مراحل (ایجاد، پردازش، ذخیره‌سازی) تضمین می‌شود و اقدامات اصلاحی در صورت کاهش کیفیت انجام می‌شود |

## ۵. نقش‌ها و مسئولیت‌ها

| نقش | مسئولیت‌ها |
| :--- | :--- |
| **مالک داده (Data Owner)** | • تعیین ارزش کسب‌وکاری داده<br>• تصویب سیاست‌های دسترسی و استفاده<br>• تأیید طبقه‌بندی داده<br>• تعیین دوره نگهداری و حذف<br>• پاسخگویی در مورد کیفیت و انطباق |
| **متولی داده (Data Steward)** | • اجرای سیاست‌های حاکمیت داده<br>• نظارت بر کیفیت داده و رفع مشکلات<br>• استانداردسازی و طبقه‌بندی داده‌ها<br>• هماهنگی بین تیم‌های مختلف در مورد داده<br>• گزارش شاخص‌های کیفیت |
| **نگهدارنده داده (Data Custodian)** | • مدیریت زیرساخت فنی ذخیره‌سازی داده<br>• اجرای پشتیبان‌گیری و بازیابی<br>• پیاده‌سازی کنترل‌های امنیتی فنی<br>• مدیریت رمزنگاری و دسترسی فنی<br>• نگهداری و به‌روزرسانی سیستم‌های داده |
| **مصرف‌کننده داده (Data Consumer)** | • استفاده از داده مطابق با سیاست‌های دسترسی<br>• گزارش مشکلات کیفیت داده به Data Steward<br>• رعایت امنیت و حریم خصوصی در استفاده<br>• عدم ذخیره‌سازی غیرمجاز داده |

## ۶. چرخه عمر داده (Data Lifecycle)

هر داده در پلتفرم از مراحل زیر عبور می‌کند و برای هر مرحله سیاست‌ها و کنترل‌های مشخصی تعریف می‌شود:

```text
ایجاد/دریافت → اعتبارسنجی → طبقه‌بندی → ذخیره‌سازی → پردازش → اشتراک‌گذاری → آرشیو → حذف امن
```

| مرحله | توضیح | کنترل‌ها |
| :--- | :--- | :--- |
| **ایجاد/دریافت (Create/Ingest)** | داده از طریق اتصال‌دهنده‌ها (Connectors)، APIها، یا ورودی کاربر ایجاد یا دریافت می‌شود | اعتبارسنجی منبع، ثبت منبع، بررسی فرمت |
| **اعتبارسنجی (Validation)** | بررسی صحت، کامل بودن و سازگاری داده | قوانین اعتبارسنجی، بررسی طرحواره (Schema)، تشخیص ناهنجاری |
| **طبقه‌بندی (Classification)** | تعیین سطح حساسیت و دسته‌بندی داده | بر اساس محتوا، منبع و قوانین کسب‌وکار |
| **ذخیره‌سازی (Storage)** | نگهداری داده در مخازن مناسب با رعایت امنیت | رمزنگاری، کنترل دسترسی، پشتیبان‌گیری |
| **پردازش (Processing)** | تبدیل، تحلیل، نمایه‌سازی (Indexing)، تولید زمینه (Context) | ثبت تغییرات، حفظ قابلیت ردیابی (Traceability) |
| **اشتراک‌گذاری (Sharing)** | ارائه داده به کاربران، سرویس‌ها یا Agentهای مجاز | کنترل دسترسی، پنهان‌سازی داده (Masking)، ثبت حسابرسی (Audit Log) |
| **آرشیو (Archive)** | انتقال داده‌های کم‌استفاده به ذخیره‌سازی بلندمدت | رمزنگاری، دوره نگهداری، قابلیت بازیابی |
| **حذف امن (Secure Deletion)** | حذف دائمی داده با روش‌های امن | پاک‌سازی امن، تأیید حذف، ثبت در حسابرسی |

## ۷. طبقه‌بندی داده (Data Classification)

داده‌ها بر اساس حساسیت و الزامات امنیتی به چهار سطح طبقه‌بندی می‌شوند. این طبقه‌بندی تعیین‌کننده روش رمزنگاری، نگهداری، اشتراک‌گذاری و مدت نگهداری داده است.

| سطح | توضیح | نمونه | سیاست‌های کلیدی |
| :--- | :--- | :--- | :--- |
| **عمومی (Public)** | داده‌ای که می‌تواند بدون محدودیت در اختیار عموم قرار گیرد | مستندات عمومی، دانشنامه سازمانی، اطلاعیه‌ها | بدون نیاز به رمزنگاری خاص، دسترسی عمومی |
| **داخلی (Internal)** | داده‌ای که فقط برای کاربران داخلی سازمان قابل دسترسی است | دستورالعمل‌های داخلی، اخبار سازمانی، فرآیندهای غیرحساس | رمزنگاری در ذخیره و انتقال، دسترسی محدود به کاربران داخلی |
| **محرمانه (Confidential)** | داده‌ای که باید با دقت زیاد محافظت شود و دسترسی محدود دارد | اطلاعات مالی، استراتژی سازمان، کد منبع اختصاصی، داده‌های مشتریان | رمزنگاری قوی، کنترل دسترسی دقیق، ثبت کامل دسترسی |
| **بسیار محرمانه (Highly Confidential)** | داده‌ای با بالاترین سطح حساسیت که افشای آن می‌تواند زیان جبران‌ناپذیری داشته باشد | اطلاعات شخصی کاربران (PII)، کلیدهای رمزنگاری، اسرار تجاری، داده‌های پزشکی | رمزنگاری پیشرفته، دسترسی بسیار محدود، تأیید چندمرحله‌ای، پایش مستمر |

---

## ۸. کیفیت داده (Data Quality)

ابعاد کیفیت داده که باید به‌صورت مستمر پایش و گزارش شوند:

| بعد | توضیح | روش اندازه‌گیری |
| :--- | :--- | :--- |
| **صحت (Accuracy)** | داده‌ها باید با واقعیت مطابقت داشته باشند | مقایسه با منبع معتبر، بررسی تناقض‌ها |
| **کامل بودن (Completeness)** | تمام فیلدهای موردنیاز باید پر شده باشند | درصد فیلدهای خالی یا ناقص |
| **سازگاری (Consistency)** | داده‌ها در سیستم‌های مختلف باید با یکدیگر سازگار باشند | بررسی تناقض بین منابع مختلف |
| **یکتایی (Uniqueness)** | هر موجودیت باید یک بار و بدون تکرار ذخیره شود | شناسایی رکوردهای تکراری |
| **به‌نگام بودن (Timeliness)** | داده‌ها باید به‌موقع به‌روزرسانی شوند | زمان تأخیر بین ایجاد و در دسترس بودن |
| **اعتبار (Validity)** | داده‌ها باید با قوانین و محدودیت‌های تعریف‌شده مطابقت داشته باشند | اعتبارسنجی بر اساس طرحواره و قوانین |

**فرآیند مدیریت کیفیت:**
- اندازه‌گیری دوره‌ای شاخص‌های کیفیت
- گزارش به Data Steward و Data Owner
- شناسایی ریشه مشکلات و اقدام اصلاحی
- بازبینی دوره‌ای و بهبود فرآیندها

## ۹. مدیریت فراداده (Metadata Management)

برای هر مجموعه داده، حداقل اطلاعات فراداده‌ای زیر نگهداری می‌شود تا قابلیت جستجو، ردیابی و مدیریت داده تسهیل شود:

| فیلد فراداده | توضیح |
| :--- | :--- |
| **شناسه داده (Data ID)** | شناسه یکتای هر مجموعه داده |
| **مالک (Owner)** | Data Owner مسئول داده |
| **منبع (Source)** | منشاء داده (Connector، سیستم خارجی، کاربر) |
| **تاریخ ایجاد (Created Date)** | زمان ایجاد یا اولین دریافت |
| **تاریخ آخرین به‌روزرسانی (Last Updated)** | زمان آخرین تغییر |
| **نسخه (Version)** | نسخه فعلی داده |
| **سطح محرمانگی (Classification)** | یکی از چهار سطح طبقه‌بندی |
| **دوره نگهداری (Retention Period)** | مدت زمانی که داده باید نگهداری شود |
| **قوانین استفاده (Usage Policies)** | محدودیت‌ها و شرایط استفاده |
| **فرمت (Format)** | فرمت داده (JSON، PDF، CSV و غیره) |
| **حجم (Size)** | اندازه داده |
| **وابستگی‌ها (Dependencies)** | سایر داده‌هایی که به این داده وابسته هستند |

**پیاده‌سازی:** فراداده در سیستم مدیریت فراداده یا به‌عنوان بخشی از فراداده استاندارد هر موجودیت (تعریف‌شده در سند `Data_Model_And_Knowledge_Schema_Overview`) نگهداری می‌شود.

## ۱۰. سیاست‌های دسترسی (Access Policies)

دسترسی به داده‌ها باید بر اساس اصول زیر مدیریت شود:

| اصل | توضیح |
| :--- | :--- |
| **بر اساس نقش (Role-Based)** | دسترسی بر اساس نقش‌های سازمانی (مانند Admin، Analyst، Developer، Viewer) |
| **بر اساس ویژگی (Attribute-Based)** | دسترسی بر اساس ویژگی‌های پویا مانند واحد سازمانی، طبقه‌بندی داده، زمان، مکان |
| **حداقل دسترسی (Least Privilege)** | هر کاربر فقط به حداقل داده‌های لازم برای انجام وظیفه خود دسترسی دارد |
| **دسترسی موقت (Temporary Access)** | دسترسی‌های موقت با تاریخ انقضا برای موارد خاص |
| **دسترسی اضطراری (Break-Glass)** | دسترسی اضطراری با ثبت کامل و تأیید بعدی برای شرایط بحرانی |

**کنترل‌های پیاده‌سازی:**
- تمام درخواست‌های دسترسی از طریق سرویس‌های حاکمیت و پلتفرم (سرویس امنیت و هویت — Security & Identity Service) اعمال می‌شوند
- دسترسی‌ها به‌صورت دوره‌ای (حداقل هر ۳ ماه) بازبینی و تأیید می‌شوند
- دسترسی‌های غیرفعال یا اضافی حذف می‌شوند
- تمام تلاش‌های دسترسی (موفق و ناموفق) ثبت و قابل ممیزی هستند

## ۱۱. حفظ حریم خصوصی (Privacy Protection)

پلتفرم با رعایت اصول حفظ حریم خصوصی از بدو طراحی، حریم خصوصی کاربران و داده‌های شخصی را تضمین می‌کند:

| اصل | پیاده‌سازی |
| :--- | :--- |
| **حداقل‌سازی داده (Data Minimization)** | پلتفرم فقط داده‌های ضروری برای انجام Task را جمع‌آوری و پردازش می‌کند. داده‌های غیرضروری در اولین فرصت حذف می‌شوند. |
| **شفافیت (Transparency)** | کاربران از نحوه جمع‌آوری، پردازش و نگهداری داده‌های خود مطلع هستند. تمام عملیات روی داده‌های شخصی قابل ردیابی است. |
| **هدف‌مندی (Purpose Limitation)** | داده‌های شخصی فقط برای اهداف مشخص و قانونی پردازش می‌شوند و برای اهداف دیگر استفاده نمی‌شوند. |
| **رضایت (Consent)** | برای پردازش داده‌های حساس، رضایت صریح کاربر اخذ می‌شود و قابل لغو است. |
| **حق حذف و اصلاح (Right to Erasure & Correction)** | کاربران می‌توانند درخواست حذف یا اصلاح داده‌های شخصی خود را ارائه دهند. پلتفرم مکانیزمی برای پاسخ به این درخواست‌ها دارد. |
| **قابلیت حمل داده (Data Portability)** | در صورت نیاز، کاربران می‌توانند داده‌های شخصی خود را در قالبی استاندارد دریافت کنند. |
| **پنهان‌سازی و ناشناس‌سازی (Masking & Anonymization)** | در صورت استفاده از داده‌های شخصی برای تحلیل یا آموزش، داده‌ها ناشناس یا پنهان می‌شوند تا هویت افراد قابل تشخیص نباشد. |

**انطباق با قوانین:** معماری به‌گونه‌ای طراحی شده که با الزامات GDPR، CCPA، HIPAA و قوانین داخلی حریم خصوصی قابل انطباق باشد. فرآیندهای مربوط به ثبت پردازش (Records of Processing)، ارزیابی تأثیر حریم خصوصی (DPIA) و اطلاع‌رسانی نقض داده نیز پشتیبانی می‌شوند.

---

## ۱۲. انطباق با استانداردها و قوانین (Compliance)

پلتفرم باید امکان انطباق با استانداردها و چارچوب‌های زیر را فراهم کند:

| استاندارد/قانون | حوزه | الزامات کلیدی مرتبط با پلتفرم |
| :--- | :--- | :--- |
| **GDPR** | حریم خصوصی داده در اتحادیه اروپا | حق حذف، اصلاح، حمل داده، رضایت، ثبت پردازش، ارزیابی تأثیر |
| **CCPA/CPRA** | حریم خصوصی داده در کالیفرنیا | حق اطلاع، حذف، عدم فروش داده، اصلاح |
| **HIPAA** | حریم خصوصی داده‌های سلامت در آمریکا | کنترل دسترسی، رمزنگاری، ثبت حسابرسی، توافق‌نامه‌های همکار تجاری |
| **ISO 27001** | سیستم مدیریت امنیت اطلاعات | مدیریت ریسک، کنترل‌های امنیتی، ممیزی، بهبود مستمر |
| **SOC 2** | کنترل‌های خدمات سازمانی | امنیت، در دسترس‌پذیری، محرمانگی، حریم خصوصی، یکپارچگی پردازش |
| **NIST Cybersecurity Framework** | چارچوب امنیت سایبری | شناسایی، حفاظت، تشخیص، پاسخ، بازیابی |
| **قوانین داخلی سازمان** | سیاست‌ها و الزامات اختصاصی سازمان | طبقه‌بندی داده، دوره نگهداری، کنترل دسترسی، گزارش‌دهی |

**مسئولیت انطباق:** تیم حاکمیت داده به همراه تیم امنیت و تیم حقوقی سازمان مسئول ارزیابی دوره‌ای انطباق، شناسایی شکاف‌ها و اجرای اقدامات اصلاحی هستند.

| حوزه | الزامات |

## ۱۶. نتیجه‌گیری

حاکمیت داده یکی از پایه‌های اصلی موفقیت پایدار پلتفرم است. داده‌ها به‌عنوان یک دارایی ارزشمند سازمان، باید با بالاترین استانداردهای کیفیت، امنیت و انطباق مدیریت شوند تا اعتماد کاربران، سرویس‌ها و Agentهای هوشمند به داده‌ها حفظ شود.

این سند چارچوب مدیریت داده، مسئولیت‌ها، سیاست‌ها، فرآیندها و الزامات انطباق را تعریف می‌کند تا داده‌ها در کل چرخه عمر خود، از ایجاد تا حذف، با کیفیت، ایمن و منطبق با قوانین در اختیار مصرف‌کنندگان قرار گیرند.

**مسئولیت به‌روزرسانی:** تیم حاکمیت داده به همراه تیم امنیت، تیم حقوقی و معماران ارشد مسئول بازبینی دوره‌ای (حداقل سالانه) این سند، به‌روزرسانی سیاست‌ها بر اساس تغییرات قوانین و نیازهای سازمان، و ارزیابی اثربخشی کنترل‌های حاکمیت داده هستند.

**ثبات سند:** این سند باید با تغییرات در قوانین، مقررات، نیازهای کسب‌وکار و معماری پلتفرم هم‌گام باشد. هر تغییر در ساختار داده یا فرآیندهای پردازش داده باید از منظر حاکمیت داده بررسی شده و در صورت نیاز این سند به‌روزرسانی شود.
