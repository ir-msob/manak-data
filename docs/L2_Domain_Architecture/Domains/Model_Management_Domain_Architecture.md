# معماری دامنه مدیریت مدل‌ها (Model Management Domain Architecture)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.0

**وضعیت:** پیش‌نویس

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف معماری دامنه **مدیریت مدل‌ها** (Model Management Domain) تدوین شده است. این دامنه مسئول مدیریت اتصال، انتخاب، مسیریابی، ثبت و پایش مدل‌های هوش مصنوعی از انواع مختلف (مدل‌های زبانی بزرگ — LLM، مدل‌های نمایش عددی — Embedding، مدل‌های بازمرتب‌سازی — Reranking و سایر مدل‌های تخصصی) است. هدف آن ایجاد لایه‌ای مستقل از ارائه‌دهنده (Provider‑Agnostic) است که به پلتفرم امکان می‌دهد بدون وابستگی به یک مدل یا سرویس خاص، از بهترین مدل متناسب با هر Task استفاده کند.

این سند به‌عنوان مرجع اصلی برای تیم‌های توسعه، معماری، هوش مصنوعی و عملیات در زمینه طراحی و پیاده‌سازی زیرساخت مدیریت مدل‌های هوش مصنوعی پلتفرم عمل می‌کند.

---

## ۲. دامنه سند

این سند تمام جنبه‌های مرتبط با دامنه مدیریت مدل‌ها را پوشش می‌دهد و شامل موارد زیر است:

- **Model Registry:** ثبت، نگهداری و مدیریت فراداده و نسخه‌های مدل‌های در دسترس
- **Model Router:** انتخاب و مسیریابی هوشمند درخواست‌ها به مدل مناسب بر اساس معیارهای مختلف
- **Provider Adapter:** لایه انتزاع برای اتصال یکپارچه به ارائه‌دهندگان مختلف (Cloud، Local، Open Source)
- **Model Selection Strategy:** راهبردهای انتخاب مدل بر اساس نوع Task، کیفیت، هزینه، سرعت و محدودیت‌ها
- **Fallback Strategy:** مکانیزم جایگزینی خودکار مدل در صورت خرابی، کندی یا محدودیت
- **Model Configuration:** تنظیمات اجرایی هر مدل (Timeout، محدودیت مصرف، پارامترهای استنتاج)
- **Model Observability:** پایش عملکرد، هزینه، کیفیت و مصرف مدل‌ها
- **Model Lifecycle Management:** مدیریت چرخه عمر مدل‌ها از ثبت تا بازنشستگی
- **Model Versioning:** نسخه‌بندی و مدیریت تغییرات مدل‌ها
- **Cost & Performance Optimization:** بهینه‌سازی هزینه و عملکرد با انتخاب هوشمند مدل

جزئیات پیاده‌سازی فنی و کدنویسی در اسناد سطح پایین‌تر تدوین می‌شوند. این سند صرفاً **معماری سطح بالا و اصول طراحی** دامنه را تعریف می‌کند.

## ۳. اصول طراحی دامنه

| اصل | توضیح |
| :--- | :--- |
| **مستقل از ارائه‌دهنده (Provider‑Agnostic)** | پلتفرم نباید به هیچ مدل، ارائه‌دهنده یا زیرساخت هوش مصنوعی خاصی وابسته باشد. تغییر ارائه‌دهنده نباید نیاز به تغییر در منطق اصلی سیستم داشته باشد. |
| **انتخاب هوشمند مدل (Intelligent Selection)** | انتخاب مدل باید بر اساس ترکیبی از معیارها شامل نوع Task، کیفیت موردنیاز، سرعت، هزینه، محدودیت Context Window و سطح امنیت داده انجام شود. |
| **جایگزینی خودکار (Automatic Fallback)** | در صورت عدم دسترس‌پذیری، افزایش زمان پاسخ، محدودیت مصرف یا تغییر Policy امنیتی، سیستم باید به‌طور خودکار به مدل جایگزین سوئیچ کند. |
| **شفافیت هزینه (Cost Transparency)** | مصرف و هزینه هر مدل باید به‌صورت شفاف قابل مشاهده و رهگیری باشد تا تیم‌ها بتوانند هزینه‌ها را مدیریت و بهینه‌سازی کنند. |
| **مشاهده‌پذیری کامل (Full Observability)** | تمام تعاملات با مدل‌ها (زمان پاسخ، مصرف توکن، هزینه، نرخ خطا، کیفیت) باید قابل پایش و تحلیل باشند. |
| **امنیت و حاکمیت داده (Data Security & Governance)** | قبل از ارسال اطلاعات به مدل‌های خارجی، سیاست‌های امنیتی (Data Masking، PII Detection، Filtering) اعمال می‌شوند تا از نشت داده‌های حساس جلوگیری شود. |
| **مقیاس‌پذیری (Scalability)** | زیرساخت مدیریت مدل باید توانایی مدیریت هزاران درخواست همزمان به چندین ارائه‌دهنده را داشته باشد. |
| **توسعه‌پذیری (Extensibility)** | افزودن ارائه‌دهنده یا مدل جدید باید از طریق Adapterهای استاندارد و بدون تغییر در هسته سیستم امکان‌پذیر باشد. |
| **استقلال از قابلیت‌های مدل (Capability-Aware)** | انتخاب مدل باید علاوه بر نوع Task، بر اساس قابلیت‌های واقعی مدل (Function Calling، Structured Output، Vision، Streaming، Tool Calling، Reasoning و ...) انجام شود. |
| **آگاهی از توافق‌نامه سطح خدمت (SLA-Aware)** | انتخاب مدل باید بر اساس SLA شامل زمان پاسخ، دسترس‌پذیری و نرخ موفقیت نیز انجام شود. |
| **چندمستاجری (Multi-Tenant Isolation)** | سیاست‌های انتخاب، محدودیت مصرف، بودجه و مدل‌های مجاز باید برای هر Tenant به‌صورت مستقل قابل تعریف باشند. |
| **بهینه‌سازی پویا (Adaptive Optimization)** | سیستم باید بتواند سیاست انتخاب مدل را بر اساس عملکرد واقعی، هزینه و بازخوردها به‌صورت پویا بهبود دهد. |
| **قابلیت ممیزی (Auditability)** | تمام تصمیمات مربوط به انتخاب مدل، Fallback و تغییر سیاست‌ها باید قابل رهگیری و ممیزی باشند. |

## ۴. مؤلفه‌های اصلی دامنه

### ۴.۱. Model Registry (ثبت مدل)

**مسئولیت:** ثبت، نگهداری و مدیریت فراداده و نسخه‌های مدل‌های در دسترس پلتفرم.

**وظایف کلیدی:**

- **ثبت مدل:** ثبت مدل جدید با فراداده کامل (نام، نوع، ارائه‌دهنده، نسخه، قابلیت‌ها، محدودیت‌ها)
- **مدیریت نسخه:** نگهداری نسخه‌های مختلف هر مدل و امکان ارتقا یا بازگشت
- **مدیریت چرخه حیات:** فعال/غیرفعال‌سازی، منسوخ‌سازی و بازنشستگی مدل‌ها
- **اعتبارسنجی:** اعتبارسنجی پیکربندی و قابلیت‌های مدل در زمان ثبت
- **مدیریت ظرفیت:** ثبت محدودیت‌های ظرفیت و توان عملیاتی هر مدل

**فیلدهای کلیدی Model Registry:**

| فیلد | توضیح |
| :--- | :--- |
| `model_id` | شناسه یکتای مدل |
| `name` | نام مدل (منحصربه‌فرد) |
| `type` | نوع مدل (LLM, Embedding, Reranking, Vision, Speech) |
| `provider` | ارائه‌دهنده (OpenAI, Anthropic, Google, Cohere, Local, ...) |
| `version` | نسخه فعلی مدل |
| `capabilities` | قابلیت‌ها (Chat, Completion, Embedding, Reranking, Vision, ...) |
| `context_window` | حداکثر اندازه Context Window (تعداد Token) |
| `cost_per_1k_input` | هزینه به ازای هر ۱۰۰۰ Token ورودی |
| `cost_per_1k_output` | هزینه به ازای هر ۱۰۰۰ Token خروجی |
| `avg_latency_ms` | میانگین زمان پاسخ (میلی‌ثانیه) |
| `quality_score` | امتیاز کیفیت (بر اساس ارزیابی‌های داخلی) |
| `data_privacy_level` | سطح حریم خصوصی داده (Public, Private, On‑Premise) |
| `status` | وضعیت (Active, Inactive, Deprecated, Retired) |
| `owner_team` | تیم مالک مدل |
| `created_at` | زمان ثبت |
| `updated_at` | زمان آخرین به‌روزرسانی |

#### ۴.۱.۱. مدیریت قابلیت‌های مدل (Model Capability Management)

علاوه بر ثبت اطلاعات پایه، قابلیت‌های هر مدل باید به‌صورت ساخت‌یافته نگهداری شوند تا انتخاب مدل صرفاً بر اساس نام یا نوع انجام نشود.

نمونه قابلیت‌ها:

| قابلیت | توضیح |
| :--- | :--- |
| Function Calling | پشتیبانی از فراخوانی ابزارها |
| Structured Output | تولید خروجی ساختاریافته |
| JSON Mode | تولید JSON معتبر |
| Vision | پردازش تصویر |
| Audio | پردازش صوت |
| Streaming | تولید پاسخ جریانی |
| Long Context | پشتیبانی از Contextهای بزرگ |
| Reasoning | توانایی استدلال چندمرحله‌ای |
| Multilingual | پشتیبانی از چند زبان |

### ۴.۲. Model Router (مسیریاب مدل)

**مسئولیت:** انتخاب و مسیریابی هوشمند درخواست‌ها به مدل مناسب بر اساس معیارهای مختلف.

**وظایف کلیدی:**

- **تحلیل درخواست:** تحلیل نوع Task، پیچیدگی، نیازهای کیفی و محدودیت‌ها
- **انتخاب مدل:** انتخاب بهترین مدل بر اساس ترکیبی از معیارها
- **مسیریابی:** ارسال درخواست به مدل انتخاب‌شده از طریق Adapter مناسب
- **مدیریت بار:** توزیع بار بین مدل‌های مشابه برای جلوگیری از اشباع
- **Fallback:** فعال‌سازی مکانیزم جایگزین در صورت خطا یا کندی

**معیارهای انتخاب مدل:**

| معیار | توضیح | وزن پیشنهادی |
| :--- | :--- | :--- |
| **Task Type** | نوع Task (Chat, Summarization, Code, Embedding, ...) | بالا |
| **Quality Requirement** | سطح کیفیت موردنیاز (High, Medium, Low) | بالا |
| **Latency Requirement** | حساسیت به تأخیر (Real‑Time, Interactive, Batch) | بالا |
| **Cost Constraint** | محدودیت هزینه | متوسط |
| **Context Window** | نیاز به Context Window بزرگ | بالا |
| **Data Privacy** | سطح حریم خصوصی داده (حساسیت اطلاعات) | بحرانی |
| **Language Support** | پشتیبانی از زبان (فارسی، انگلیسی، ...) | متوسط |
| **Availability** | در دسترس‌پذیری فعلی مدل | بالا |

**الگوریتم انتخاب مدل:**

```text
1. فیلتر مدل‌های مناسب بر اساس Type و Capabilities
2. حذف مدل‌های غیرفعال یا با ظرفیت کامل
3. اعمال فیلترهای امنیتی (Data Privacy, Compliance)
4. امتیازدهی بر اساس معیارها با وزن‌های پویا
5. انتخاب مدل با بالاترین امتیاز
6. در صورت خطا → Fallback به مدل بعدی
```

#### ۴.۲.۱. سیاست‌های مسیریابی (Routing Policies)

سامانه باید امکان تعریف سیاست‌های مختلف مسیریابی را داشته باشد.

نمونه سیاست‌ها:

- Lowest Cost
- Highest Quality
- Lowest Latency
- Best SLA
- Data Residency
- Tenant Preference
- Weighted Routing
- Canary Routing
- A/B Routing

### ۴.۳. Provider Adapter (آداپتور ارائه‌دهنده)

**مسئولیت:** لایه انتزاع برای اتصال یکپارچه به ارائه‌دهندگان مختلف مدل‌های هوش مصنوعی.

**وظایف کلیدی:**

- **یکسان‌سازی رابط (Interface Standardization):** ارائه یک رابط داخلی یکسان برای تمام ارائه‌دهندگان
- **تبدیل درخواست (Request Transformation):** تبدیل درخواست داخلی به فرمت مورد انتظار هر ارائه‌دهنده
- **تبدیل پاسخ (Response Transformation):** تبدیل پاسخ ارائه‌دهنده به فرمت استاندارد داخلی
- **مدیریت خطا (Error Handling):** مدیریت خطاهای خاص هر ارائه‌دهنده و تبدیل به خطاهای استاندارد
- **مدیریت احراز هویت (Authentication):** مدیریت کلیدها و توکن‌های دسترسی به ارائه‌دهندگان

**ارائه‌دهندگان پشتیبانی‌شده:**

| ارائه‌دهنده | نوع مدل‌ها | پروتکل | ویژگی‌ها |
| :--- | :--- | :--- | :--- |
| **OpenAI** | LLM, Embedding | REST API | GPT‑4, GPT‑3.5, text‑embedding‑3 |
| **Anthropic** | LLM | REST API | Claude 3, Claude 3.5 |
| **Google (Vertex AI)** | LLM, Embedding | REST API, gRPC | Gemini, PaLM, Gecko |
| **Cohere** | LLM, Embedding, Reranking | REST API | Command, Embed, Rerank |
| **Mistral (Local)** | LLM | REST API (Local) | Mistral, Mixtral |
| **Llama (Local)** | LLM | REST API (Local) | Llama 2, Llama 3 |
| **Hugging Face** | LLM, Embedding | Inference API | Open Source Models |
| **Azure OpenAI** | LLM, Embedding | REST API | همان OpenAI با زیرساخت Azure |
| **AWS Bedrock** | LLM, Embedding | REST API | Claude, Titan, Jurassic, ... |
| **Custom (On‑Premise)** | LLM, Embedding | REST API / gRPC | مدل‌های داخلی سازمان |

**الزامات Adapterها**

تمام Adapterها باید قابلیت‌های زیر را پیاده‌سازی کنند.

- مدیریت Retry
- مدیریت Timeout
- استانداردسازی خطاها
- پشتیبانی از Streaming
- پشتیبانی از Cancellation
- ثبت Metrics
- مدیریت Rate Limit
- مدیریت Authentication
- بررسی سلامت Provider

### ۴.۴. Fallback Strategy (راهبرد جایگزینی)

**مسئولیت:** مکانیزم جایگزینی خودکار مدل در صورت خرابی، کندی یا محدودیت.

**وظایف کلیدی:**

- **تشخیص خطا:** شناسایی خطاهای Timeout، ۵xx، Rate Limit و خطاهای احراز هویت
- **انتخاب جایگزین:** انتخاب مدل جایگزین با اولویت‌بندی از پیش تعریف‌شده
- **سوئیچ خودکار:** تغییر مسیر درخواست به مدل جایگزین بدون دخالت کاربر
- **بازیابی:** بازگشت به مدل اصلی پس از رفع مشکل
- **ثبت و پایش:** ثبت تمام رویدادهای Fallback برای تحلیل و بهبود

**سیاست‌های Fallback:**

Fallback می‌تواند بر اساس یکی از سیاست‌های زیر انجام شود.

- Provider جایگزین
- مدل هم‌رده
- مدل ارزان‌تر
- مدل محلی
- مدل با Context بزرگ‌تر
- مدل سریع‌تر
- Human Escalation

**شرایط فعال‌سازی Fallback:**

| شرایط | توضیح | اقدام |
| :--- | :--- | :--- |
| **Unavailable** | ارائه‌دهنده در دسترس نیست | Fallback فوری |
| **Timeout** | زمان پاسخ از آستانه مجاز عبور کرده | Fallback با Retry |
| **Rate Limited** | محدودیت مصرف ارائه‌دهنده | Fallback موقت |
| **High Latency** | افزایش زمان پاسخ (P95 > آستانه) | Fallback انتخابی |
| **Quality Degradation** | کاهش کیفیت پاسخ (زیر آستانه) | Fallback به مدل باکیفیت‌تر |
| **Security Policy Change** | تغییر Policy امنیتی (مثلاً داده حساس) | Fallback به On‑Premise |

**سلسله‌مراتب Fallback (نمونه):**

```text
Primary: gpt-4
    │
    ├── Fallback 1: claude-3-opus
    │       │
    │       └── Fallback 2: gemini-1.5-pro
    │               │
    │               └── Fallback 3: gpt-3.5-turbo
    │                       │
    │                       └── Fallback 4: mistral-large (Local)
    │                               │
    │                               └── Fallback 5: Error (Human Escalation)
```

### ۴.۵. Model Configuration (پیکربندی مدل)

**مسئولیت:** مدیریت تنظیمات اجرایی و پارامترهای استنتاج هر مدل.

**وظایف کلیدی:**

- **پارامترهای استنتاج:** مدیریت Temperature، Max Tokens، Top‑P، Frequency Penalty و سایر پارامترها
- **محدودیت‌های اجرایی:** مدیریت Timeout، Retry Policy، Rate Limit و Concurrent Limit
- **پیکربندی سفارشی:** امکان تنظیم پارامترهای خاص هر Task یا کاربر
- **نسخه‌بندی پیکربندی:** نگهداری نسخه‌های مختلف پیکربندی برای بازتولید

**پارامترهای کلیدی:**

| پارامتر | توضیح | محدوده پیشنهادی |
| :--- | :--- | :--- |
| **temperature** | خلاقیت پاسخ (۰ تا ۱) | ۰٫۰ (دقیق) تا ۰٫۹ (خلاق) |
| **max_tokens** | حداکثر تعداد Token خروجی | ۱۰۰ تا ۴۰۹۶ |
| **top_p** | نمونه‌برداری هسته‌ای (۰ تا ۱) | ۰٫۱ تا ۱٫۰ |
| **frequency_penalty** | جریمه تکرار (۰ تا ۲) | ۰٫۰ تا ۱٫۰ |
| **presence_penalty** | جریمه وجود (۰ تا ۲) | ۰٫۰ تا ۱٫۰ |
| **timeout_ms** | حداکثر زمان انتظار | ۵۰۰۰ تا ۱۲۰۰۰۰ |
| **retry_count** | تعداد تکرار مجدد | ۰ تا ۳ |
| **retry_delay_ms** | فاصله زمانی بین Retry | ۱۰۰۰ تا ۱۰۰۰۰ |

**سطوح پیکربندی**

پیکربندی مدل می‌تواند در سطوح زیر تعریف شود.

- Global
- Tenant
- Workspace
- Project
- Agent
- Workflow
- Task
- User

در زمان اجرا اولویت با نزدیک‌ترین سطح به درخواست است.

### ۴.۶. Model Observability (مشاهده‌پذیری مدل)

**مسئولیت:** پایش عملکرد، هزینه، کیفیت و مصرف مدل‌ها.

**متریک‌های کلیدی:**

| متریک | توضیح |
| :--- | :--- |
| **Request Count** | تعداد درخواست‌ها به هر مدل |
| **Latency (P50, P95, P99)** | زمان پاسخ مدل در صدک‌های مختلف |
| **Token Usage (Input/Output)** | تعداد توکن ورودی و خروجی مصرف‌شده |
| **Cost** | هزینه تخمینی بر اساس مصرف Token و نرخ هر ارائه‌دهنده |
| **Success Rate** | درصد درخواست‌های موفق |
| **Error Rate** | درصد درخواست‌های ناموفق با جزئیات نوع خطا |
| **Fallback Rate** | درصد درخواست‌هایی که به مدل جایگزین سوئیچ شده‌اند |
| **Quality Score** | امتیاز کیفیت پاسخ (بر اساس ارزیابی خودکار یا بازخورد) |

**لاگ‌گیری:**

- تمام درخواست‌ها و پاسخ‌های مدل با جزئیات کامل
- شامل: `request_id`, `model_id`, `provider`, `input_tokens`, `output_tokens`, `latency_ms`, `cost`, `status`, `error`, `timestamp`

## ۵. جریان پردازش درخواست مدل

جریان کامل از درخواست عامل تا دریافت پاسخ مدل:

```text
Agent Request (with Task, Parameters, Context)
        │
        ▼
Model Router دریافت درخواست
        │
        ├── ۱. تحلیل Task (نوع، پیچیدگی، نیازها)
        │
        ├── ۲. فیلتر مدل‌ها (بر اساس Capability, Status, Capacity)
        │
        ├── ۳. اعمال فیلترهای امنیتی (Data Privacy, Policy)
        │
        ├── ۴. امتیازدهی به مدل‌ها (کیفیت، هزینه، سرعت، Context Window)
        │
        ├── ۵. انتخاب مدل با بالاترین امتیاز
        │
        ├── ۶. دریافت پیکربندی مدل (Temperature, Max Tokens, ...)
        │
        ├── ۷. ارسال درخواست به Provider Adapter
        │
        ├── ۸. Adapter → ارسال به ارائه‌دهنده خارجی
        │
        ├── ۹. دریافت پاسخ → تبدیل به فرمت استاندارد
        │
        ├── ۱۰. اعتبارسنجی پاسخ (Quality Check, Hallucination Detection)
        │
        ├── ۱۱. ثبت Metrics و Logs
        │
        ▼
Return Response to Agent
```

## ۱۰. نتیجه‌گیری

دامنه **مدیریت مدل‌ها** به‌عنوان **دروازه دسترسی به هوش مصنوعی**، نقش حیاتی در انعطاف‌پذیری، مقیاس‌پذیری و بهینه‌سازی هزینه پلتفرم ایفا می‌کند. معماری تعریف‌شده در این سند، چارچوبی استاندارد، مستقل از ارائه‌دهنده، هوشمند و قابل اعتماد برای مدیریت اتصال، انتخاب، مسیریابی و پایش مدل‌های هوش مصنوعی فراهم می‌آورد.

رعایت اصول طراحی (Provider‑Agnostic، Intelligent Selection، Automatic Fallback، Cost Transparency، Security) و پیاده‌سازی مؤلفه‌های کلیدی (Model Registry، Model Router، Provider Adapter، Fallback Strategy، Model Observability) تضمین می‌کند که پلتفرم بتواند از بهترین مدل‌ها برای هر Task استفاده کند، هزینه‌ها را بهینه‌سازی کند، در برابر خطاهای ارائه‌دهنده مقاوم باشد و در عین حال امنیت و حریم خصوصی داده‌ها را حفظ کند.

**مسئولیت به‌روزرسانی:** تیم معماری به همراه تیم‌های توسعه، هوش مصنوعی و عملیات مسئول بازبینی دوره‌ای این سند، به‌روزرسانی آن بر اساس تغییرات مدل‌های جدید، ارائه‌دهندگان جدید و بازخورد تیم‌های پیاده‌سازی هستند.

**ثبات سند:** این سند باید با تغییرات در معماری کلان، مدل‌های هوش مصنوعی و نیازمندی‌های امنیتی هم‌گام باشد. هر تغییر در سیاست‌های انتخاب مدل یا ارائه‌دهندگان باید در این سند منعکس شود تا سایر اسناد معماری و طراحی نیز به‌روزرسانی شوند.
