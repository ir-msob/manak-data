# ۱. هدف و محدوده سند

این سند سناریوهای خرابی (Failure Scenarios)، راهکارهای کاهش ریسک (Risk Mitigation) و راهبردهای تنزل کنترل‌شده سرویس (Graceful Degradation) را در سطح سازمانی (Enterprise) تحلیل می‌کند. این سند فرض می‌کند خواننده با مرزبندی Componentها و اهداف کیفی آشنا است؛ تمرکز اینجا بر «چه اتفاقی می‌افتد اگر یکی از این Componentها خراب شود» است، نه شرح مسئولیت آن‌ها.

---

# ۲. دسته‌بندی ریسک‌ها (Risk Categories)

| دسته | نمونه ریسک |
| :--- | :--- |
| **زیرساخت (Infrastructure)** | خرابی سرور، Cluster یا منابع محاسباتی |
| **شبکه (Network)** | قطعی یا کندی ارتباط بین سرویس‌ها |
| **مدل‌های هوش مصنوعی (AI Models)** | خرابی، کندی یا رفتار نادرست مدل (جزئیات در بخش ریسک‌های اختصاصی هوش مصنوعی) |
| **داده (Data)** | از‌دست‌رفتن، خرابی یا ناهم‌خوانی داده |
| **امنیت (Security)** | نفوذ، دسترسی غیرمجاز، نشت داده |
| **یکپارچه‌سازی‌های شخص ثالث (Third-party Integrations)** | خرابی یا تغییر ناگهانی یک سیستم یا Provider خارجی |
| **خطای انسانی (Human Error)** | خطای پیکربندی یا عملیات دستی نادرست |
| **ظرفیت (Capacity)** | عبور بار واقعی از ظرفیت پیش‌بینی‌شده |

# ۳. سناریوهای خرابی (Failure Modes)

| Component | نوع خرابی | تأثیر | راهکار کاهش ریسک |
| :--- | :--- | :--- | :--- |
| **Interface & Integration Layer (API Gateway)** | از دسترس خارج شدن | بالا (High) | استقرار با دسترس‌پذیری بالا (High Availability — چند نمونه فعال-فعال) + انتقال خودکار به نمونه سالم (Automatic Failover) |
| **Model Management Engine (LLM Provider)** | زمان پاسخ بیش از حد مجاز (Timeout) | بالا (High) | تلاش مجدد (Retry) + استفاده از مدل جایگزین (Fallback Model) |
| **Vector Database** | Offline شدن | متوسط (Medium) | استفاده از Context ذخیره‌شده در Cache به‌جای بازیابی زنده |
| **Knowledge & Context Engine** | خرابی سرویس | متوسط (Medium) | ارائه Context ناقص (Partial Context) به‌جای توقف کامل |
| **Action & Tool Engine (Tool Execution)** | خطای اجرا | متوسط (Medium) | تلاش مجدد (Retry) یا عملیات جبرانی (Compensation) |
| **Message Broker** | از کار افتادن | بالا (High) | صف پایدار (Durable Queue) که پیام را تا بازیابی سرویس نگه می‌دارد |
| **لایه داده (Data Layer — Storage)** | خرابی | بالا (High) | تکرار داده (Replication) در چند نسخه |
| **Governance & Platform Services (Identity Service)** | از کار افتادن | بحرانی (Critical) | حالت محدود فقط‑خواندنی (Read-only Mode) تا بازیابی کامل سرویس هویت |

> ستون «تأثیر» بر اساس اثر خرابی روی کاربر نهایی تعیین شده: **بحرانی** یعنی توقف کامل قابلیت اصلی سیستم (مثلاً احراز هویت)، **بالا** یعنی اختلال گسترده در تجربه کاربر، **متوسط** یعنی افت کیفیت بدون توقف کامل سرویس.

# ۴. تنزل کنترل‌شده سرویس (Graceful Degradation)

## ۴.۱ اولویت حفظ قابلیت‌ها

در شرایط بحرانی، ترتیب زیر برای حفظ قابلیت‌ها رعایت می‌شود (بالاترین اولویت اول):

۱. **امنیت (Security)** — کنترل‌های امنیتی هرگز غیرفعال نمی‌شوند، حتی به قیمت کاهش سایر قابلیت‌ها
۲. **APIهای هسته (Core APIs)** — عملکرد پایه Interface & Integration Layer
۳. **بازیابی دانش (Knowledge Retrieval)** — بازیابی دانش، حتی اگر ناقص باشد
۴. **استدلال هوش مصنوعی (AI Reasoning)** — تصمیم‌گیری و اجرای Agent
۵. **قابلیت‌های اختیاری (Optional Features)** — قابلیت‌های غیرحیاتی، اولین موارد قابل تعطیلی موقت

## ۴.۲ راهبردهای اجرایی

- **غیرفعال‌سازی قابلیت (Feature Disablement):** غیرفعال‌سازی موقت قابلیت‌های غیرضروری
- **پاسخ از حافظه پنهان (Cached Responses):** ارائه پاسخ از حافظه پنهان به‌جای پردازش زنده
- **حالت فقط‑خواندنی (Read-only Mode):** محدود کردن سیستم به عملیات فقط‑خواندنی
- **کاهش حجم Context (Reduced Context Size):** کاهش حجم Context ارسالی به مدل برای کاهش فشار روی سیستم
- **مدل‌های جایگزین (Fallback Models):** استفاده از مدل جایگزین سبک‌تر یا در دسترس‌تر
- **صف‌بندی درخواست‌ها (Queue Requests):** صف کردن درخواست‌ها به‌جای رد کردن آن‌ها
- **ارجاع به انسان (Human Escalation):** ارجاع به تصمیم‌گیرنده انسانی

---

# ۵. ریسک‌های اختصاصی هوش مصنوعی (AI‑specific Risks)

| ریسک | تعریف |
| :--- | :--- |
| **توهم (Hallucination)** | تولید پاسخی توسط مدل که واقعیت ندارد اما با اطمینان بیان می‌شود |
| **تزریق دستور (Prompt Injection)** | تلاش برای دستکاری رفتار مدل از طریق ورودی مخرب |
| **آلودگی Context (Context Poisoning)** | آلوده‌شدن Context با داده نادرست یا مخرب که روی تصمیم مدل اثر می‌گذارد |
| **سوءاستفاده از ابزار (Tool Misuse)** | استفاده نادرست یا خارج از دامنه مجاز از یک Tool توسط Agent |
| **هزینه بیش‌ازحد (Excessive Cost)** | مصرف غیرمنتظره و بالای منابع محاسباتی یا Token |
| **پر شدن پنجره Context (Token Exhaustion)** | پر شدن پنجره Context مدل پیش از تکمیل Task |

| :--- | :--- |

| **تأیید انسانی (Human Approval)** | Human-in-the-Loop |

# ۶. بازیابی (Recovery)

- **تلاش مجدد خودکار (Automatic Retry):** تلاش مجدد خودکار برای خطای گذرا (Transient Error)
- **قطع‌کننده مدار (Circuit Breaker):** قطع موقت مسیر ناسالم برای جلوگیری از گسترش خطا
- **بررسی سلامت (Health Checks):** بررسی دوره‌ای سلامت سرویس‌ها
- **خوددرمانی (Self‑healing):** راه‌اندازی مجدد خودکار نمونه‌های ناسالم بدون مداخله دستی
- **بازراه‌اندازی تدریجی (Rolling Restart):** بازراه‌اندازی تدریجی نمونه‌ها بدون قطعی کامل سرویس

---

# ۷. بازیابی از حوادث (Disaster Recovery)

- **استقرار چند‑منطقه‌ای (Multi‑zone Deployment):** استقرار در چند منطقه در دسترسی (Availability Zone) برای تحمل خرابی محلی
- **پشتیبان‌گیری خودکار (Automated Backups):** پشتیبان‌گیری خودکار و دوره‌ای
- **تکرار داده بین‌منطقه‌ای (Cross‑region Replication):** تکرار داده بین مناطق جغرافیایی مختلف

> اهداف کمّی این بخش (RPO/RTO) و پیاده‌سازی زیرساختی آن پیش‌تر در سند `Non_Functional_Requirements_And_SLA` و `Deployment_Environment_Topology` تعریف شده‌اند؛ این سند صرفاً از منظر ریسک به آن‌ها اشاره می‌کند و مقدار جدیدی تعریف نمی‌کند.

# ۸. پایش (Monitoring)

معیارهای کلیدی پایش برای تشخیص زودهنگام ریسک عبارت‌اند از:

- **دسترس‌پذیری (Availability)**
- **نرخ خطا (Error Rate)**
- **زمان پاسخ (Latency)**
- **عمق صف (Queue Depth)**
- **مصرف توکن (Token Usage)**
- **هزینه (Cost)**
- **هشدارهای رویداد (Incident Alerts)**

> این معیارها زیرمجموعه‌ای هدفمند (برای تشخیص زودهنگام ریسک) از فهرست کامل متریک‌های تعریف‌شده در سند `Non_Functional_Requirements_And_SLA` هستند.

# ۱۰. نتیجه‌گیری

این سند ریسک‌ها و سناریوهای خرابی پلتفرم را به‌صورت سیستماتیک شناسایی و دسته‌بندی کرده و برای هرکدام راهکارهای کاهش ریسک، راهبردهای تنزل کنترل‌شده و مکانیزم‌های بازیابی ارائه می‌دهد. با اجرای این راهکارها، پلتفرم قادر خواهد بود در مواجهه با خطاهای مختلف، سطح قابل قبولی از سرویس را حفظ کرده و از تأثیرات گسترده بر کاربران نهایی جلوگیری کند. پایش مستمر معیارهای کلیدی و بازبینی دوره‌ای این سند با توجه به تغییرات سیستم و تهدیدات جدید، بخشی از فرایند عملیاتی مستمر خواهد بود.
