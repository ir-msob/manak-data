# معماری دامنه هویت و دسترسی (Identity & Access Domain Architecture)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.0

**وضعیت:** پیش‌نویس

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف معماری دامنه **هویت و دسترسی** (Identity & Access Domain) تدوین شده است. این دامنه مسئول مدیریت هویت دیجیتال (Identity)، احراز هویت (Authentication) و مجوزدهی (Authorization) برای تمام کاربران، سرویس‌ها، عامل‌ها (Agents) و مؤلفه‌های پلتفرم است. هدف آن ایجاد یک لایه امنیتی یکپارچه، استاندارد و مقیاس‌پذیر برای تضمین هویت و سطح دسترسی هر نهاد (Entity) در سیستم، بر اساس اصول Zero Trust و Least Privilege است.

این سند به‌عنوان مرجع اصلی برای تیم‌های توسعه، معماری، امنیت و عملیات در زمینه طراحی و پیاده‌سازی زیرساخت هویت و کنترل دسترسی پلتفرم عمل می‌کند.

---

## ۲. دامنه سند

این سند تمام جنبه‌های مرتبط با دامنه هویت و دسترسی را پوشش می‌دهد و شامل موارد زیر است:

- **مدیریت هویت (Identity Management):** ثبت، نگهداری و چرخه حیات هویت کاربران، سرویس‌ها، عامل‌ها و سایر نهادها
- **احراز هویت (Authentication):** احراز هویت چندعاملی (MFA)، Single Sign-On (SSO)، احراز هویت سرویس‌به‌سرویس (mTLS، JWT)
- **مجوزدهی (Authorization):** کنترل دسترسی مبتنی بر نقش (RBAC) و مبتنی بر ویژگی (ABAC)
- **مدیریت توکن (Token Management):** تولید، اعتبارسنجی، انقضا و چرخش توکن‌های JWT و API Key
- **مدیریت خط‌مشی‌ها (Policy Management):** تعریف و اعمال سیاست‌های دسترسی بر اساس نقش، ویژگی و زمینه (Context)
- **دایرکتوری کاربران و سرویس‌ها (User & Service Directory):** مخزن مرکزی هویت‌ها و فراداده‌های مرتبط
- **ثبت و ممیزی (Audit & Logging):** ثبت کامل تلاش‌های احراز هویت، مجوزدهی و تغییرات دسترسی
- **یکپارچگی با ارائه‌دهندگان هویت خارجی:** اتصال به Identity Providerهای سازمانی (Azure AD، Okta، Keycloak)

جزئیات پیاده‌سازی فنی و کدنویسی در اسناد سطح پایین‌تر تدوین می‌شوند. این سند صرفاً **معماری سطح بالا و اصول طراحی** دامنه را تعریف می‌کند.

## ۳. اصول طراحی دامنه

| اصل | توضیح |
| :--- | :--- |
| **صفر اعتماد (Zero Trust)** | هیچ کاربر، سرویس یا عاملی به‌صورت پیش‌فرض قابل اعتماد نیست. هر درخواست باید احراز هویت، مجوزدهی و اعتبارسنجی شود، حتی درخواست‌های داخلی بین مؤلفه‌ها. |
| **کمترین سطح دسترسی (Least Privilege)** | هر نهاد (کاربر، سرویس، عامل) فقط به حداقل منابع، داده‌ها و عملیات لازم برای انجام وظیفه خود دسترسی دارد. |
| **جداسازی داده‌ها بر اساس مستأجر (Tenant Isolation)** | دسترسی به داده‌ها و منابع باید در سطح مستأجر (Tenant) ایزوله شود تا از نشت داده بین سازمان‌های مختلف جلوگیری شود. |
| **مقیاس‌پذیری (Scalability)** | زیرساخت هویت و دسترسی باید توانایی مدیریت میلیون‌ها کاربر و هزاران درخواست همزمان را داشته باشد. |
| **قابلیت ممیزی (Auditability)** | تمام رویدادهای مرتبط با هویت و دسترسی (ورود، خروج، تغییر نقش، تلاش‌های ناموفق) باید ثبت و قابل ردیابی باشند. |
| **یکپارچگی با استانداردها (Standards Compliance)** | پشتیبانی از استانداردهای باز مانند OAuth2، OIDC، SAML 2.0، SCIM و JWT برای قابلیت حمل و یکپارچه‌پذیری. |
| **انعطاف‌پذیری در مدل‌های دسترسی** | پشتیبانی هم‌زمان از مدل‌های RBAC و ABAC برای پاسخگویی به سناریوهای مختلف کسب‌وکار. |
| **امنیت از ابتدای طراحی (Security by Design)** | تمام مؤلفه‌های هویت و دسترسی باید با رعایت امنیت از ابتدا طراحی و پیاده‌سازی شوند. |
| **دفاع در عمق (Defense in Depth)** | کنترل دسترسی نباید به یک مکانیزم محدود شود و باید از چندین لایه امنیتی شامل احراز هویت، مجوزدهی، رمزنگاری، ممیزی و پایش استفاده شود. |
| **احراز هویت تطبیقی (Adaptive Authentication)** | سطح احراز هویت باید بر اساس میزان ریسک، موقعیت جغرافیایی، نوع دستگاه، رفتار کاربر و حساسیت عملیات به‌صورت پویا تعیین شود. |
| **اعتماد به دستگاه (Device Trust)** | وضعیت امنیتی دستگاه درخواست‌کننده باید پیش از اعطای دسترسی ارزیابی شود. |
| **تفکیک وظایف (Separation of Duties - SoD)** | نقش‌ها و مجوزها باید به گونه‌ای طراحی شوند که از ایجاد تعارض وظایف و سوءاستفاده جلوگیری شود. |
| **قابلیت ردیابی تصمیمات (Decision Traceability)** | تمام تصمیمات مربوط به احراز هویت و مجوزدهی باید همراه با دلایل، سیاست اعمال‌شده و اطلاعات زمینه‌ای قابل ردیابی باشند. |

## ۴. مؤلفه‌های اصلی دامنه

### ۴.۱. Identity Provider Integration (یکپارچگی با ارائه‌دهنده هویت)

**مسئولیت:** اتصال و یکپارچه‌سازی با ارائه‌دهندگان هویت خارجی (External Identity Providers) برای احراز هویت کاربران و سرویس‌ها.

**وظایف کلیدی:**

- **پشتیبانی از استانداردها:** OAuth2، OpenID Connect (OIDC)، SAML 2.0، LDAP، SCIM
- **اتصال به Identity Providers:** Azure AD، Okta، Keycloak، Google Workspace، AWS IAM
- **همگام‌سازی کاربران:** همگام‌سازی خودکار کاربران و نقش‌ها از طریق SCIM یا APIs
- **فدراسیون هویت (Federation):** امکان ورود با هویت سازمانی (SSO)
- **مدیریت جلسه (Session Management):** مدیریت جلسات کاربران در سطح ارائه‌دهنده

**قابلیت‌های تکمیلی:**

- پشتیبانی از چند Identity Provider به‌صورت هم‌زمان
- مسیریابی هوشمند درخواست احراز هویت بر اساس Tenant
- همگام‌سازی گروه‌ها (Groups)
- همگام‌سازی نقش‌ها
- همگام‌سازی واحدهای سازمانی
- کش اطلاعات هویت برای کاهش تأخیر
- مدیریت وضعیت اتصال هر Identity Provider

---

### ۴.۲. Authentication Service (سرویس احراز هویت)

**مسئولیت:** احراز هویت کاربران، سرویس‌ها و عامل‌ها با استفاده از روش‌های مختلف.

**وظایف کلیدی:**

- **احراز هویت کاربران:** پشتیبانی از نام کاربری/رمز عبور، MFA (TOTP، SMS، ایمیل)، بیومتریک
- **احراز هویت سرویس‌ها:** پشتیبانی از Client Credentials، mTLS، API Key
- **احراز هویت عامل‌ها:** پشتیبانی از JWT با نقش‌های محدود برای عامل‌ها
- **Single Sign‑On (SSO):** یکپارچگی با Identity Provider برای ورود یکپارچه
- **مدیریت جلسه:** ایجاد، نگهداری و انقضای جلسات کاربران
- **ثبت تلاش‌های احراز هویت:** ثبت موفقیت، شکست و جزئیات مرتبط

**روش‌های احراز هویت:**

| روش | توضیح | کاربرد |
| :--- | :--- | :--- |
| **Username/Password** | احراز هویت با اعتبارنامه‌های سنتی | کاربران داخلی با هویت سازمانی |
| **OAuth2 / OIDC** | احراز هویت مبتنی بر توکن با ارائه‌دهنده خارجی | ورود با حساب سازمانی (SSO) |
| **MFA** | احراز هویت چندعاملی (TOTP، SMS، ایمیل) | کاربران با دسترسی حساس |
| **Client Credentials** | احراز هویت سرویس‌به‌سرویس با Client ID/Secret | سرویس‌های داخلی و یکپارچه‌سازی |
| **mTLS** | احراز هویت متقابل با گواهی‌های SSL | ارتباطات داخلی با امنیت بالا |
| **API Key** | کلیدهای API با محدودیت دسترسی | توسعه‌دهندگان و برنامه‌های خارجی |

---

#### ۴.۲.۱ ارزیابی ریسک احراز هویت (Authentication Risk Assessment)

پیش از صدور توکن، سطح ریسک هر درخواست احراز هویت ارزیابی می‌شود.

معیارهای ارزیابی شامل:

- موقعیت جغرافیایی
- نوع دستگاه
- آدرس IP
- سابقه ورود کاربر
- ساعت درخواست
- الگوی رفتاری
- اعتبار دستگاه
- سطح حساسیت سرویس مقصد

بر اساس امتیاز ریسک، سامانه می‌تواند MFA را الزامی کند، درخواست را رد کند یا نیاز به تأیید بیشتر داشته باشد.

### ۴.۳. Authorization Engine (موتور مجوزدهی)

**مسئولیت:** تعیین سطح دسترسی هر نهاد به منابع، داده‌ها و عملیات بر اساس نقش‌ها، ویژگی‌ها و سیاست‌ها.

**وظایف کلیدی:**

- **ارزیابی دسترسی:** بررسی درخواست دسترسی بر اساس RBAC و ABAC
- **مدیریت نقش‌ها (Roles):** تعریف، نگهداری و تخصیص نقش‌ها به کاربران و سرویس‌ها
- **مدیریت ویژگی‌ها (Attributes):** مدیریت ویژگی‌های پویا (واحد سازمانی، طبقه‌بندی داده، موقعیت مکانی، زمان)
- **مدیریت سیاست‌ها (Policies):** تعریف و اعمال سیاست‌های دسترسی به‌صورت متمرکز
- **ارزیابی زمینه (Context‑Aware):** در نظر گرفتن زمینه درخواست (موقعیت، زمان، دستگاه، سطح ریسک)
- **کش (Cache):** کش‌کردن نتایج مجوزدهی برای کاهش تأخیر

**بهینه‌سازی‌های مجوزدهی:**

- کش تصمیمات مجوزدهی
- ارزیابی موازی Policyها
- اولویت‌بندی Policyها
- مدیریت تعارض Policyها
- پشتیبانی از Default Deny
- ثبت زمان ارزیابی
- ثبت Policy اعمال‌شده

**مدل‌های مجوزدهی:**

| مدل | توضیح | کاربرد |
| :--- | :--- | :--- |
| **RBAC** | دسترسی بر اساس نقش‌های از پیش تعریف‌شده | کنترل دسترسی عمومی و ساختاری |
| **ABAC** | دسترسی بر اساس ویژگی‌های پویا | کنترل دسترسی دقیق و زمینه‌محور |
| **Policy‑Based** | دسترسی بر اساس قوانین و سیاست‌های پیچیده | سناریوهای کسب‌وکار ویژه |
| **Hybrid (RBAC + ABAC)** | ترکیب نقش‌ها و ویژگی‌ها | انعطاف‌پذیری بالا برای سازمان‌های بزرگ |

---

### ۴.۴. Token Management (مدیریت توکن)

**مسئولیت:** تولید، اعتبارسنجی، انقضا و چرخش امن توکن‌های دسترسی.

**وظایف کلیدی:**

- **تولید توکن:** تولید JWT با امضای RSA/HS256 و包含 اطلاعات هویت و نقش‌ها
- **اعتبارسنجی توکن:** بررسی صحت، انقضا و امضای توکن در هر درخواست
- **مدیریت چرخش (Rotation):** چرخش دوره‌ای کلیدهای امضا و توکن‌ها
- **انقضا (Expiration):** تعیین مدت اعتبار توکن‌ها (Access Token کوتاه‌مدت، Refresh Token بلندمدت)
- **لغو (Revocation):** امکان لغو توکن‌ها در صورت نقض امنیت یا تغییر نقش
- **یکپارچگی با Refresh Token:** امکان تمدید جلسه بدون احراز هویت مجدد

**کنترل‌های امنیتی توکن:**

- چرخش خودکار کلیدهای امضا
- نسخه‌بندی کلیدها (Key Versioning)
- استفاده از JWKS برای انتشار کلید عمومی
- جلوگیری از Replay Attack
- امکان ابطال گروهی توکن‌ها
- محدودسازی تعداد Refresh Tokenهای فعال

**انواع توکن‌ها:**

| نوع توکن | توضیح | مدت اعتبار پیشنهادی |
| :--- | :--- | :--- |
| **Access Token** | توکن دسترسی به منابع (JWT) | ۱ تا ۲۴ ساعت |
| **Refresh Token** | توکن تمدید جلسه | ۷ تا ۳۰ روز |
| **ID Token** | توکن هویت کاربر (OIDC) | ۱ تا ۲۴ ساعت |
| **API Key** | کلید دسترسی برای سرویس‌ها و توسعه‌دهندگان | بدون انقضا (با امکان لغو دستی) |

---

### ۴.۵. User & Service Directory (دایرکتوری کاربران و سرویس‌ها)

**مسئولیت:** مخزن مرکزی و امن برای نگهداری هویت‌ها، نقش‌ها، ویژگی‌ها و فراداده‌های مرتبط.

**وظایف کلیدی:**

- **ثبت کاربران:** ثبت کاربران با فراداده کامل (نام، ایمیل، نقش، واحد سازمانی)
- **ثبت سرویس‌ها:** ثبت سرویس‌های داخلی و خارجی با Client ID/Secret
- **ثبت عامل‌ها:** ثبت عامل‌های هوشمند با هویت و نقش‌های محدود
- **مدیریت نقش‌ها:** تعریف و تخصیص نقش‌ها به کاربران، سرویس‌ها و عامل‌ها
- **مدیریت ویژگی‌ها:** نگهداری ویژگی‌های پویا (واحد سازمانی، طبقه‌بندی داده، مکان)
- **همگام‌سازی:** همگام‌سازی با Identity Provider خارجی از طریق SCIM یا APIs

**فیلدهای کلیدی دایرکتوری:**

| فیلد | توضیح |
| :--- | :--- |
| `entity_id` | شناسه یکتای نهاد (User/Service/Agent) |
| `entity_type` | نوع نهاد (User, Service, Agent) |
| `username` | نام کاربری (یکتا) |
| `email` | ایمیل |
| `roles` | لیست نقش‌های تخصیص‌یافته |
| `attributes` | ویژگی‌های پویا (JSON) |
| `tenant_id` | شناسه مستأجر |
| `status` | وضعیت (Active, Inactive, Locked, Expired) |
| `created_at` | زمان ایجاد |
| `updated_at` | زمان آخرین به‌روزرسانی |

**اطلاعات تکمیلی هر هویت:**

- آخرین زمان ورود
- آخرین تغییر رمز عبور
- وضعیت MFA
- وضعیت قفل حساب
- تعداد ورود ناموفق
- وضعیت تأیید ایمیل
- وضعیت تأیید شماره تلفن
- سطح ریسک هویت

---

### ۴.۶. Policy Management Engine (موتور مدیریت سیاست‌ها)

**مسئولیت:** تعریف، نگهداری و اعمال سیاست‌های دسترسی و امنیتی به‌صورت متمرکز.

**وظایف کلیدی:**

- **تعریف سیاست‌ها:** تعریف قوانین دسترسی بر اساس نقش، ویژگی، زمان، مکان و سایر معیارها
- **نسخه‌بندی سیاست‌ها:** نگهداری نسخه‌های مختلف سیاست‌ها برای بازتولید و بازگشت
- **اعتبارسنجی سیاست‌ها:** بررسی سازگاری و عدم تناقض سیاست‌ها
- **اعمال سیاست‌ها:** اعمال سیاست‌ها در زمان اجرا بر روی درخواست‌های دسترسی
- **تغییرات پویا:** امکان تغییر سیاست‌ها در زمان اجرا بدون نیاز به استقرار مجدد

**قابلیت‌های تکمیلی مدیریت سیاست:**

- شبیه‌سازی Policy
- اعتبارسنجی خودکار Policy
- انتشار مرحله‌ای Policy
- زمان‌بندی فعال‌سازی
- زمان‌بندی انقضا
- Rollback به نسخه قبلی
- بررسی تعارض بین Policyها

**نمونه سیاست‌ها:**

| سیاست | توضیح |
| :--- | :--- |
| **فقط مدیران می‌توانند کاربران را حذف کنند** | نقش `Admin` مجاز به حذف کاربران |
| **کاربران فقط به داده‌های واحد خود دسترسی دارند** | فیلتر بر اساس ویژگی `department` |
| **دسترسی به داده‌های محرمانه فقط از شبکه داخلی** | محدودیت IP برای داده‌های Confidential |
| **عامل‌ها فقط به Toolهای مجاز دسترسی دارند** | محدودیت Tool بر اساس نقش Agent |

---

### ۴.۷. Audit & Logging Service (سرویس ثبت و ممیزی)

**مسئولیت:** ثبت کامل و غیرقابل‌تغییر تمام رویدادهای مرتبط با هویت و دسترسی.

**وظایف کلیدی:**

- **ثبت رویدادهای احراز هویت:** ثبت تمام تلاش‌های ورود (موفق و ناموفق)
- **ثبت رویدادهای مجوزدهی:** ثبت تمام تلاش‌های دسترسی (موفق و ناموفق)
- **ثبت تغییرات دسترسی:** ثبت تغییرات در نقش‌ها، ویژگی‌ها و سیاست‌ها
- **ثبت تغییرات هویت:** ثبت ایجاد، به‌روزرسانی و حذف کاربران و سرویس‌ها
- **نگهداری بلندمدت:** نگهداری لاگ‌ها برای مدت زمان تعیین‌شده (حداقل ۱ سال)
- **یکپارچگی با سیستم‌های نظارتی:** ارسال لاگ‌ها به سیستم مشاهده‌پذیری

**فیلدهای کلیدی لاگ:**

| فیلد | توضیح |
| :--- | :--- |
| `event_id` | شناسه یکتای رویداد |
| `event_type` | نوع رویداد (Login, Logout, Access, RoleChange, ...) |

## ۵. جریان احراز هویت و مجوزدهی (Authentication & Authorization Flow)

جریان کامل از درخواست تا تأیید دسترسی:

```text
User/Service/Agent Request
        │
        ▼
Authentication (مدارک را ارائه می‌دهد)
        │
        ├── Validate Credentials (Username/Password, Client Credentials, mTLS)
        │
        ├── MFA (در صورت نیاز)
        │
        ├── Issue JWT/Token
        │
        ▼
Request with Token (درخواست به همراه توکن)
        │
        ▼
Token Validation (اعتبارسنجی توکن)
        │
        ├── Check Signature (امضا)
        │
        ├── Check Expiration (انقضا)
        │
        ├── Check Revocation (لغو)
        │
        ▼
Authorization (مجوزدهی)
        │
        ├── Extract Roles & Attributes (استخراج نقش و ویژگی‌ها)
        │
        ├── Evaluate Policies (ارزیابی سیاست‌ها)
        │
        ├── Context-Aware Check (بررسی زمینه: زمان، مکان، دستگاه)
        │
        ├── Decision (Allow/Deny)
        │
        ▼
Decision (تصمیم نهایی)
        │
        ├── Allow → دسترسی به منبع
        │
        └── Deny → خطای 403 Forbidden با دلیل
        │
        ▼
Audit Logging (ثبت کامل)
```

## ۱۰. نتیجه‌گیری

دامنه **هویت و دسترسی** به‌عنوان **دروازه امنیتی پلتفرم**، نقش حیاتی در تضمین امنیت، انطباق و یکپارچگی سیستم ایفا می‌کند. معماری تعریف‌شده در این سند، چارچوبی استاندارد، امن، مقیاس‌پذیر و منعطف برای مدیریت هویت، احراز هویت و مجوزدهی بر اساس اصول Zero Trust و Least Privilege فراهم می‌آورد.

رعایت اصول طراحی (Zero Trust، Least Privilege، Tenant Isolation، Auditability) و پیاده‌سازی مؤلفه‌های کلیدی (Identity Provider Integration، Authentication Service، Authorization Engine، Token Management، User & Service Directory، Policy Management، Audit & Logging) تضمین می‌کند که پلتفرم بتواند هویت و دسترسی تمام نهادها را به‌صورت امن، شفاف و قابل اطمینان مدیریت کند و در عین حال با ارائه‌دهندگان هویت سازمانی یکپارچه شود.

**مسئولیت به‌روزرسانی:** تیم امنیت و معماری به همراه تیم‌های توسعه و عملیات مسئول بازبینی دوره‌ای این سند، به‌روزرسانی آن بر اساس تغییرات نیازمندی‌های امنیتی، استانداردهای جدید و بازخورد تیم‌های پیاده‌سازی هستند.

**ثبات سند:** این سند باید با تغییرات در معماری کلان، استانداردهای امنیتی و نیازمندی‌های سازمانی هم‌گام باشد. هر تغییر در سیاست‌های هویت و دسترسی باید در این سند منعکس شود تا سایر اسناد معماری و طراحی نیز به‌روزرسانی شوند.
