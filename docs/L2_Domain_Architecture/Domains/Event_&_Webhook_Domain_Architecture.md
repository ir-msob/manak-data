# معماری دامنه رویداد و Webhook (Event & Webhook Domain Architecture)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.0

**وضعیت:** پیش‌نویس

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف معماری دامنه **رویداد و Webhook** (Event & Webhook Domain) تدوین شده است. این دامنه مسئول مدیریت اعلان‌ها، Webhookها و ارتباطات رویدادمحور (Event-Driven) با سیستم‌های خارجی است. هدف آن ایجاد بستری استاندارد، امن و قابل اعتماد برای انتشار رویدادهای مهم پلتفرم به مصرف‌کنندگان خارجی و دریافت رویدادهای خارجی جهت پردازش در پلتفرم است.

این سند به‌عنوان مرجع اصلی برای تیم‌های توسعه، معماری، یکپارچه‌سازی و محصول در زمینه طراحی و پیاده‌سازی ارتباطات رویدادمحور و مدیریت Webhookها عمل می‌کند.

---

## ۲. دامنه سند

این سند تمام جنبه‌های مرتبط با دامنه رویداد و Webhook را پوشش می‌دهد و شامل موارد زیر است:

- **Webhook Registry:** ثبت، مدیریت و نگهداری Webhookهای ثبت‌شده
- **Event Publisher:** انتشار رویدادها به مصرف‌کنندگان خارجی و داخلی
- **Webhook Delivery:** ارسال امن و قابل اعتماد Webhookها با مکانیزم Retry و نظارت
- **Webhook Security:** احراز هویت، امضای درخواست‌ها و محافظت در برابر حملات
- **Event Subscription:** مدیریت اشتراک‌های رویداد و فیلترهای مرتبط
- **Webhook Monitoring:** پایش موفقیت، خطاها و تأخیر در تحویل Webhookها
- **Schema Management:** مدیریت ساختار و نسخه‌بندی رویدادهای منتشرشده
- **Rate Limiting و Throttling:** کنترل نرخ ارسال Webhookها به مصرف‌کنندگان

جزئیات پیاده‌سازی فنی و کدنویسی در اسناد سطح پایین‌تر تدوین می‌شوند. این سند صرفاً **معماری سطح بالا و اصول طراحی** دامنه را تعریف می‌کند.

## ۳. اصول طراحی دامنه

| اصل | توضیح |
| :--- | :--- |
| **Event-Driven First (اولویت با رویدادمحوری)** | ارتباط با سیستم‌های خارجی تا حد امکان از طریق رویدادهای غیرهمزمان انجام می‌شود تا وابستگی زمانی و مستقیم کاهش یابد. |
| **قابلیت اطمینان در تحویل (Reliable Delivery)** | Webhookها باید با مکانیزم‌های Retry، Exponential Backoff و Dead Letter Queue تحویل داده شوند تا از دست‌رفتن رویدادها جلوگیری شود. |
| **امنیت پیش‌فرض (Security by Default)** | تمام Webhookها با امضای درخواست (Request Signing)، احراز هویت و رمزنگاری محافظت می‌شوند. |
| **مقیاس‌پذیری (Scalability)** | زیرساخت رویداد باید توانایی مدیریت میلیون‌ها رویداد در روز و هزاران Webhook همزمان را داشته باشد. |
| **جداسازی (Decoupling)** | تولیدکننده رویداد و مصرف‌کننده (Webhook) از طریق واسط‌های استاندارد (Message Broker، HTTP) از یکدیگر جدا هستند. |
| **نسخه‌بندی رویدادها (Event Versioning)** | ساختار رویدادها نسخه‌بندی می‌شود تا تغییرات بدون شکستن مصرف‌کنندگان موجود امکان‌پذیر باشد. |
| **مشاهده‌پذیری کامل (Full Observability)** | تمام تحویل‌های Webhook، موفقیت‌ها، خطاها و تأخیرها باید قابل پایش و لاگ‌گیری باشند. |
| **حداقل تأثیر بر عملکرد اصلی (Minimal Performance Impact)** | انتشار رویدادها نباید تأخیر قابل‌توجهی به جریان اصلی پردازش پلتفرم تحمیل کند. |
| **حداقل یک‌بار تحویل (At-Least-Once Delivery)** | معماری تحویل رویدادها باید به‌گونه‌ای طراحی شود که هیچ رویدادی از بین نرود، حتی اگر در برخی شرایط تحویل بیش از یک بار انجام شود. |
| **Idempotency (تکرارپذیری ایمن)** | مصرف‌کنندگان باید بتوانند دریافت مجدد یک رویداد را بدون ایجاد اثر جانبی پردازش کنند. |
| **ترتیب رویدادها (Event Ordering)** | در صورت نیاز کسب‌وکار، ترتیب انتشار و تحویل رویدادها برای هر موجودیت حفظ می‌شود. |
| **استقلال از Message Broker** | معماری دامنه نباید وابسته به یک Message Broker خاص باشد و امکان جایگزینی فناوری وجود داشته باشد. |
| **جداسازی مستأجران (Tenant Isolation)** | رویدادها، صف‌ها، اشتراک‌ها و Webhookهای هر مستأجر باید کاملاً از سایر مستأجران ایزوله شوند. |

## ۴. مؤلفه‌های اصلی دامنه

### ۴.۱. Webhook Registry (ثبت Webhook)

**مسئولیت:** ثبت، نگهداری و مدیریت Webhookهای ثبت‌شده توسط مصرف‌کنندگان خارجی.

**وظایف کلیدی:**

- **ثبت Webhook:** ثبت URL، روش احراز هویت، رویدادهای مشترک، نسخه رویداد
- **مدیریت چرخه حیات:** فعال/غیرفعال‌سازی، به‌روزرسانی، حذف Webhook
- **اعتبارسنجی:** بررسی معتبر بودن URL، روش احراز هویت و ساختار رویدادها
- **مدیریت نسخه:** نگهداری نسخه‌های مختلف رویدادهای مشترک
- **مدیریت محدودیت‌ها:** اعمال محدودیت نرخ، سقف درخواست و زمان‌بندی

**فیلدهای کلیدی Webhook Registry:**

| فیلد | توضیح |
| :--- | :--- |
| `webhook_id` | شناسه یکتای Webhook |
| `tenant_id` | شناسه مستأجر |
| `url` | آدرس Endpoint مصرف‌کننده |
| `event_types` | لیست رویدادهای مشترک |
| `event_versions` | نسخه‌های رویدادهای مشترک |
| `auth_method` | روش احراز هویت (API Key, JWT, HMAC) |
| `headers` | هدرهای سفارشی برای ارسال |
| `status` | فعال، غیرفعال، معلق |
| `retry_config` | تنظیمات Retry (تعداد، فاصله زمانی) |
| `rate_limit` | محدودیت نرخ ارسال |
| `created_at` | زمان ثبت |
| `updated_at` | زمان آخرین به‌روزرسانی |

**اطلاعات تکمیلی Webhook**

- نسخه قرارداد Webhook
- وضعیت سلامت Endpoint
- آخرین ارسال موفق
- آخرین ارسال ناموفق
- تعداد تحویل موفق
- تعداد خطا
- آخرین Status Code
- Timeout اختصاصی
- سیاست Circuit Breaker

---

### ۴.۲. Event Publisher (انتشاردهنده رویداد)

**مسئولیت:** انتشار رویدادهای دامنه به سیستم‌های خارجی از طریق Webhook و به سیستم‌های داخلی از طریق Message Broker.

**وظایف کلیدی:**

- **انتشار رویداد:** دریافت رویداد از دامنه‌های داخلی و انتشار آن به مصرف‌کنندگان
- **فیلتر کردن:** ارسال فقط به Webhookهایی که رویداد را مشترک شده‌اند
- **تبدیل (Transformation):** تبدیل رویداد به فرمت مورد انتظار مصرف‌کننده (JSON، XML)
- **نسخه‌بندی:** ارائه نسخه‌های مختلف رویداد بر اساس تنظیمات Webhook
- **تولید Payload:** تولید محموله رویداد با Metadata و اطلاعات کامل

**قابلیت‌های تکمیلی انتشار**

- انتشار همزمان برای چند مصرف‌کننده
- انتشار دسته‌ای (Batch Publishing)
- غنی‌سازی Metadata
- تعیین Priority رویداد
- زمان‌بندی انتشار
- جلوگیری از انتشار رویدادهای تکراری
- اعتبارسنجی Schema قبل از انتشار

**جریان انتشار:**

```text
Domain Event (Internal)
        │
        ▼
Event Publisher
        │
        ├── Filter Subscribers (by event_type, version)
        │
        ├── Transform Payload (to target format)
        │
        ├── Enrich with Metadata (timestamp, correlation_id, tenant_id)
        │
        ▼
Delivery Queue (Asynchronous)
        │
        ▼
Webhook Dispatcher
```

#### ۴.۲.۱ ساختار استاندارد رویداد (Standard Event Envelope)

تمام رویدادهای منتشرشده باید دارای یک ساختار استاندارد باشند تا امکان پردازش، ردیابی و نسخه‌بندی یکپارچه فراهم شود.

فیلدهای اصلی Envelope عبارت‌اند از:

| فیلد | توضیح |
| :--- | :--- |
| `event_id` | شناسه یکتای رویداد |
| `event_type` | نوع رویداد |
| `event_version` | نسخه قرارداد رویداد |
| `timestamp` | زمان ایجاد رویداد |
| `tenant_id` | شناسه مستأجر |
| `correlation_id` | شناسه ردیابی بین سرویس‌ها |
| `source` | دامنه یا سرویس تولیدکننده |
| `payload` | محتوای اصلی رویداد |
| `metadata` | اطلاعات تکمیلی مورد نیاز |

### ۴.۳. Webhook Dispatcher و Delivery (توزیع‌کننده و تحویل Webhook)

**مسئولیت:** ارسال امن، قابل اعتماد و مقیاس‌پذیر Webhookها به مصرف‌کنندگان خارجی.

**وظایف کلیدی:**

- **ارسال HTTP:** ارسال درخواست‌های HTTP با روش POST به URL ثبت‌شده
- **Retry و Exponential Backoff:** تلاش مجدد با فاصله زمانی افزایشی در صورت خطا یا Timeout
- **Dead Letter Queue:** ذخیره‌سازی رویدادهای شکست‌خورده برای بررسی دستی
- **مدیریت Timeout:** تعیین حداکثر زمان انتظار برای پاسخ مصرف‌کننده
- **امضای درخواست:** امضای درخواست‌ها با HMAC یا JWT برای احراز هویت
- **کنترل نرخ (Rate Limiting):** اعمال محدودیت نرخ ارسال به هر Webhook
- **ثبت و پایش:** ثبت موفقیت، خطا و تأخیر هر تحویل

**الگوریتم Retry پیشنهادی:**

| تلاش | زمان انتظار | توضیح |
| :--- | :--- | :--- |
| ۱ | ۰ ثانیه | ارسال اولیه |
| ۲ | ۵ ثانیه | پس از خطا |
| ۳ | ۳۰ ثانیه | پس از خطای دوم |
| ۴ | ۲ دقیقه | پس از خطای سوم |
| ۵ | ۱۰ دقیقه | پس از خطای چهارم |
| ۶ | ۱ ساعت | پس از خطای پنجم |
| ۷ (آخر) | ۶ ساعت | آخرین تلاش |
| **Dead Letter** | — | ارسال به صف خطاها برای بررسی دستی |

**سیاست‌های تحویل**

- At-Least-Once Delivery
- Idempotent Delivery
- Circuit Breaker برای Endpointهای ناپایدار
- Bulkhead Isolation
- Timeout اختصاصی هر Endpoint
- Retry قابل تنظیم برای هر Webhook
- حداکثر تعداد درخواست همزمان

---

### ۴.۴. Webhook Security (امنیت Webhook)

**مسئولیت:** محافظت از Webhookها در برابر حملات، دسترسی غیرمجاز و نشت داده.

**کنترل‌های امنیتی:**

| کنترل | توضیح |
| :--- | :--- |
| **امضای درخواست (Request Signing)** | هر درخواست با یک امضای HMAC یا JWT امضا می‌شود تا مصرف‌کننده بتواند اصالت آن را تأیید کند. |
| **احراز هویت (Authentication)** | پشتیبانی از روش‌های مختلف احراز هویت (API Key، JWT، OAuth2، Basic Auth) |
| **Validation URL** | اعتبارسنجی URL در زمان ثبت برای جلوگیری از حملات SSRF |
| **IP Whitelist** | محدود کردن ارسال Webhook به IPهای مجاز مصرف‌کننده |
| **رمزنگاری (Encryption)** | تمام ارتباطات با TLS 1.3 رمزنگاری می‌شوند. |
| **محدودیت نرخ (Rate Limiting)** | جلوگیری از ارسال بیش از حد به یک Endpoint |
| **ثبت ممیزی (Audit Logging)** | ثبت تمام درخواست‌ها و تلاش‌های ناموفق برای تحلیل امنیتی |
| **Replay Protection** | جلوگیری از اجرای مجدد یک درخواست امضاشده با استفاده از Timestamp و Nonce |
| **Secret Rotation** | تعویض دوره‌ای Secretهای مورد استفاده برای امضای درخواست |
| **Payload Encryption** | رمزنگاری Payload در صورت نیاز مصرف‌کننده |
| **Certificate Pinning** | اعتبارسنجی گواهی مقصد برای ارتباطات حساس |

### ۴.۵. مدیریت اشتراک (Subscription Management)

**مسئولیت:** مدیریت اشتراک‌های رویداد و فیلترهای مرتبط برای مصرف‌کنندگان.

**وظایف کلیدی:**

- **تعریف رویدادهای قابل اشتراک:** ارائه لیست رویدادهای موجود به مصرف‌کنندگان
- **ثبت اشتراک:** ثبت رویدادهای مورد نظر مصرف‌کننده و فیلترهای آن
- **فیلترهای پیشرفته:** امکان فیلتر بر اساس Metadata، Tenant، Priority، Severity
- **نسخه‌بندی:** پشتیبانی از نسخه‌های مختلف رویداد
- **لغو اشتراک:** لغو یا غیرفعال‌سازی اشتراک

**نمونه ساختار اشتراک:**

```json
{
  "subscription_id": "sub-123",
  "webhook_id": "whk-456",
  "event_type": "agent.task.completed",
  "event_version": "v1",
  "filters": {
    "tenant_id": ["tenant-1", "tenant-2"],
    "priority": ["high", "critical"],
    "agent_type": "planner"
  },
  "status": "active",
  "created_at": "2026-07-24T10:00:00Z"
}
```

#### ۴.۵.۱ مدیریت قرارداد رویداد (Event Contract Management)

برای هر نوع رویداد یک قرارداد مشخص تعریف می‌شود.

هر قرارداد شامل موارد زیر است:

- شناسه رویداد
- نسخه
- Schema
- نوع Payload
- Metadata
- قوانین اعتبارسنجی
- وضعیت انتشار
- سیاست سازگاری با نسخه‌های قبلی

---

### ۴.۶. مشاهده‌پذیری Webhook (Observability)

**مسئولیت:** پایش، لاگ‌گیری و هشداردهی برای تحویل Webhookها.

**متریک‌های کلیدی:**

| متریک | توضیح |
| :--- | :--- |
| **Delivery Success Rate** | درصد تحویل‌های موفق |
| **Delivery Failure Rate** | درصد تحویل‌های ناموفق |
| **Average Latency** | میانگین زمان بین انتشار و دریافت پاسخ |
| **Retry Count** | تعداد تلاش‌های مجدد برای هر Webhook |
| **Dead Letter Count** | تعداد رویدادهای ارسال‌شده به Dead Letter Queue |
| **Rate Limit Hits** | تعداد تلاش‌های ارسال محدودشده |

**لاگ‌گیری:**

- تمام تلاش‌های ارسال Webhook (موفق و ناموفق) با جزئیات کامل
- شامل: `webhook_id`, `event_type`, `correlation_id`, `attempt`, `status_code`, `duration_ms`, `error_message`

**هشداردهی (Alerting):**

- هشدار در صورت کاهش نرخ موفقیت (Success Rate) زیر آستانه
- هشدار در صورت افزایش تأخیر (Latency)
- هشدار در صورت پر شدن Dead Letter Queue

---

#### ۴.۶.۱ سلامت Endpointها (Endpoint Health Management)

سامانه به‌صورت مستمر وضعیت Endpointهای ثبت‌شده را پایش می‌کند.

اطلاعات نگهداری‌شده:

- آخرین پاسخ موفق
- میانگین Latency
- نرخ خطا
- تعداد Timeout
- وضعیت Circuit Breaker
- وضعیت فعال یا معلق

## ۵. جریان رویداد (Event Flow)

جریان انتشار و تحویل یک رویداد به‌صورت زیر است:

```text
Domain Event 발생 (در یک دامنه داخلی)
        │
        ▼
Event Publisher دریافت رویداد
        │
        ├── تولید Payload استاندارد
        │
        ├── جستجوی Webhookهای مشترک (بر اساس event_type و version)
        │
        ├── اعمال فیلترهای اشتراک (tenant_id، priority، ...)
        │
        ▼
ارسال به Queue (برای پردازش غیرهمزمان)
        │
        ▼
Webhook Dispatcher
        │
        ├── دریافت رویداد از Queue
        │
        ├── تبدیل به فرمت مورد انتظار مصرف‌کننده
        │
        ├── اعمال احراز هویت (امضای درخواست، افزودن هدرها)
        │
        ├── ارسال HTTP POST به URL ثبت‌شده
        │
        ├── در صورت موفقیت: ثبت لاگ و به‌روزرسانی آمار
        │
        ├── در صورت شکست: Retry (با Exponential Backoff)
        │
        └── در صورت شکست پس از Retry: ارسال به Dead Letter Queue
        │
        ▼
ثبت و پایش (Metrics, Logs, Traces)
```

---

### ۵.۱ مدیریت شکست تحویل (Delivery Failure Management)

در صورت عدم موفقیت در تحویل Webhook، مراحل زیر انجام می‌شود:

1. Retry
2. Exponential Backoff
3. Circuit Breaker
4. Dead Letter Queue
5. ایجاد Alert
6. امکان ارسال مجدد دستی
7. ثبت کامل در Audit Log

## ۱۰. نتیجه‌گیری

دامنه **رویداد و Webhook** به‌عنوان **پل ارتباطی رویدادمحور بین پلتفرم و سیستم‌های خارجی**، نقش حیاتی در یکپارچه‌سازی، اطلاع‌رسانی و هماهنگی با اکوسیستم سازمانی ایفا می‌کند. معماری تعریف‌شده در این سند، چارچوبی استاندارد، امن، قابل اعتماد و مقیاس‌پذیر برای انتشار رویدادهای مهم پلتفرم به مصرف‌کنندگان خارجی و دریافت رویدادهای خارجی جهت پردازش فراهم می‌آورد.

رعایت اصول طراحی (Event-Driven First، Reliable Delivery، Security by Default، Observability) و پیاده‌سازی مؤلفه‌های کلیدی (Webhook Registry، Event Publisher، Webhook Dispatcher، Subscription Management) تضمین می‌کند که پلتفرم بتواند به‌صورت مؤثر با سیستم‌های خارجی یکپارچه شود، رویدادها را با قابلیت اطمینان بالا تحویل دهد و در عین حال امنیت، عملکرد و قابلیت نگهداری بلندمدت را حفظ کند.

**مسئولیت به‌روزرسانی:** تیم معماری به همراه تیم‌های توسعه و محصول مسئول بازبینی دوره‌ای این سند، به‌روزرسانی آن بر اساس تغییرات نیازمندی‌های یکپارچه‌سازی رویدادمحور، استانداردهای جدید Webhook و بازخورد مصرف‌کنندگان هستند.

**ثبات سند:** این سند باید با تغییرات در معماری کلان، استانداردهای رویدادمحور و نیازمندی‌های یکپارچه‌سازی هم‌گام باشد. هر تغییر در رویدادها یا سیاست‌های Webhook باید در این سند منعکس شود تا سایر اسناد معماری و طراحی نیز به‌روزرسانی شوند.
