# معماری دامنه مشاهده‌پذیری (Observability Domain Architecture)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.0

**وضعیت:** پیش‌نویس

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف معماری دامنه **مشاهده‌پذیری** (Observability Domain) تدوین شده است. این دامنه مسئول مدیریت پایش (Monitoring)، لاگ‌گیری (Logging)، ردیابی (Tracing) و هشداردهی (Alerting) در سراسر پلتفرم است. هدف آن ایجاد یک زیرساخت یکپارچه، استاندارد و مقیاس‌پذیر برای جمع‌آوری، ذخیره‌سازی، تحلیل و نمایش داده‌های عملیاتی از تمام مؤلفه‌ها، سرویس‌ها و دامنه‌ها است تا وضعیت سلامت، عملکرد، رفتار و کیفیت سرویس‌ها به‌صورت شفاف قابل مشاهده و اندازه‌گیری باشد.

این سند به‌عنوان مرجع اصلی برای تیم‌های توسعه، عملیات، SRE و DevOps در زمینه طراحی، پیاده‌سازی و بهره‌برداری از قابلیت‌های مشاهده‌پذیری پلتفرم عمل می‌کند.

---

## ۲. دامنه سند

این سند تمام جنبه‌های مرتبط با دامنه مشاهده‌پذیری را پوشش می‌دهد و شامل موارد زیر است:

- **شاخص‌ها (Metrics):** جمع‌آوری، ذخیره‌سازی و نمایش شاخص‌های کمی (نرخ درخواست، تأخیر، نرخ خطا، مصرف منابع) از تمام سرویس‌ها
- **لاگ‌ها (Logs):** جمع‌آوری، نمایه‌سازی و جستجوی لاگ‌های ساخت‌یافته از تمام مؤلفه‌ها با قابلیت رهگیری و تحلیل
- **ردیابی (Tracing):** ردیابی توزیع‌شده (Distributed Tracing) درخواست‌ها در مسیر عبور از سرویس‌های مختلف برای شناسایی گلوگاه‌ها و خطاها
- **همبستگی (Correlation):** ارتباط بین Metrics، Logs و Traces از طریق شناسه‌های مشترک (Correlation ID، Trace ID) برای مشاهده یکپارچه
- **هشداردهی (Alerting):** تعریف قوانین هشدار، تشخیص ناهنجاری‌ها و ارسال اعلان‌ها به تیم‌های مربوطه
- **داشبوردها (Dashboards):** ارائه نمایش‌های بصری و تعاملی از وضعیت سیستم برای مخاطبان مختلف
- **مدیریت چرخه عمر داده‌های مشاهده‌پذیری:** نگهداری، بایگانی و حذف داده‌های قدیمی بر اساس سیاست‌های تعیین‌شده
- **سنجش سلامت (Health Checks):** بررسی دوره‌ای وضعیت سرویس‌ها و مؤلفه‌ها

جزئیات پیاده‌سازی فنی و کدنویسی در اسناد سطح پایین‌تر تدوین می‌شوند. این سند صرفاً **معماری سطح بالا و اصول طراحی** دامنه را تعریف می‌کند.

## ۳. اصول طراحی دامنه

| اصل | توضیح |
| :--- | :--- |
| **Observability by Design** | تمام مؤلفه‌ها و سرویس‌ها باید از ابتدا با قابلیت تولید Metrics، Logs، Traces و Events طراحی شوند. مشاهده‌پذیری یک قابلیت ذاتی معماری است. |
| **Golden Signals** | تمام سرویس‌ها باید حداقل چهار شاخص Latency، Traffic، Errors و Saturation را تولید و پایش کنند. |
| **Standard Telemetry** | تمام داده‌های مشاهده‌پذیری باید مطابق استاندارد OpenTelemetry تولید شوند تا وابستگی به ابزارهای خاص از بین برود. |
| **End-to-End Correlation** | تمام درخواست‌ها باید دارای Trace ID و Correlation ID باشند و این شناسه‌ها در تمام سرویس‌ها، Eventها، Queueها و Workflowها حفظ شوند. |
| **Structured Logging** | تمام لاگ‌ها باید به صورت JSON و مطابق Schema استاندارد تولید شوند. |
| **Cost-aware Observability** | Sampling، Downsampling، Retention و Aggregation باید به گونه‌ای انجام شوند که هزینه ذخیره‌سازی کنترل شود. |
| **Reliability** | خرابی زیرساخت مشاهده‌پذیری نباید باعث اختلال در سرویس‌های عملیاتی شود. |
| **Security & Privacy** | داده‌های حساس نباید وارد Logs یا Traceها شوند و دسترسی به داده‌ها باید بر اساس RBAC و ABAC کنترل گردد. |

## ۴. مؤلفه‌های اصلی دامنه

### ۴.۱. Metrics Collection & Storage (جمع‌آوری و ذخیره‌سازی شاخص‌ها)

**مسئولیت:** جمع‌آوری، ذخیره‌سازی و مدیریت شاخص‌های کمی از تمام سرویس‌ها و زیرساخت.

**وظایف کلیدی:**

- **جمع‌آوری شاخص‌ها:** دریافت Metrics از سرویس‌ها از طریق Pull (Prometheus) یا Push (OpenTelemetry)
- **ذخیره‌سازی:** ذخیره‌سازی Metrics در پایگاه‌های داده سری‌زمانی (Time‑Series DB) با قابلیت Downsampling
- **مدیریت برچسب‌ها (Labels):** مدیریت برچسب‌های استاندارد (`service`, `endpoint`, `tenant_id`, `status_code`)
- **محاسبه نرخ‌ها و Aggregation:** محاسبه نرخ‌ها (Rate)، درصدها (Percentiles) و Aggregateهای سفارشی

**انواع Metrics:**

| نوع | توضیح | نمونه |
| :--- | :--- | :--- |
| **Counter** | مقدار افزایشی (هرگز کاهش نمی‌یابد) | تعداد درخواست‌ها، تعداد خطاها |
| **Gauge** | مقدار فعلی (افزایش و کاهش) | مصرف CPU، حافظه، تعداد Podهای فعال |
| **Histogram** | توزیع مقادیر (برای Percentileها) | زمان پاسخ (Latency) |
| **Summary** | مشابه Histogram با قابلیت محاسبه Percentile در سمت کلاینت | زمان پاسخ با Percentile مشخص |

**ابزارهای پیشنهادی:** Prometheus، VictoriaMetrics، Thanos، Cortex

**استانداردهای کلیدی Metrics:**

تمام سرویس‌ها باید حداقل مجموعه‌ای از متریک‌های استاندارد زیر را منتشر کنند:

| دسته | متریک |
| :--- | :--- |
| **Availability** | Request Count، Success Rate، Error Rate |
| **Latency** | P50، P90، P95، P99 |
| **Traffic** | Requests/sec، Throughput |
| **Resource Usage** | CPU، Memory، Disk، Network |
| **Business Metrics** | Token Usage، Agent Execution Count، Tool Invocation Count (در صورت نیاز) |

تمام متریک‌ها باید از استاندارد نام‌گذاری و Labelهای مشترک تعریف‌شده در سند `Metrics_Standards` پیروی کنند.

### ۴.۲. Logging Collection & Storage (جمع‌آوری و ذخیره‌سازی لاگ‌ها)

**مسئولیت:** جمع‌آوری، نمایه‌سازی، ذخیره‌سازی و جستجوی لاگ‌های تولیدشده توسط تمام سرویس‌ها.

**وظایف کلیدی:**

- **جمع‌آوری لاگ‌ها:** دریافت لاگ‌ها از سرویس‌ها از طریق Filebeat، Fluentd، یا OpenTelemetry
- **نمایه‌سازی (Indexing):** نمایه‌سازی خودکار فیلدهای لاگ برای جستجوی سریع
- **ذخیره‌سازی:** ذخیره‌سازی لاگ‌ها با دوره نگهداری مشخص (Hot/Warm/Cold Storage)
- **جستجو و تحلیل:** ارائه رابط جستجو و تحلیل (Kibana، Grafana Explore)
- **Parsing و غنی‌سازی:** استخراج فیلدهای کلیدی از لاگ‌های نیمه‌ساخت‌یافته

**فیلدهای استاندارد هر لاگ:**

| فیلد | توضیح | الزامی |
| :--- | :--- | :--- |
| `timestamp` | زمان ثبت | بله |
| `service` | نام سرویس | بله |
| `component` | نام Component | بله |
| `environment` | محیط اجرا | بله |
| `tenant_id` | شناسه Tenant | بله |
| `trace_id` | شناسه Trace | بله |
| `span_id` | شناسه Span | خیر |
| `correlation_id` | شناسه درخواست | بله |
| `request_id` | شناسه درخواست HTTP | خیر |
| `user_id` | شناسه کاربر | خیر |
| `operation` | عملیات در حال اجرا | بله |
| `level` | سطح لاگ | بله |
| `message` | متن لاگ | بله |
| `error_code` | کد خطا | خیر |
| `exception` | Exception | خیر |
| `data` | داده تکمیلی (JSON) | خیر |

**الزامات ثبت لاگ:**

- تمام لاگ‌ها باید به‌صورت JSON تولید شوند.
- ثبت Password، Secret، Access Token، API Key و سایر اطلاعات حساس ممنوع است.
- تمام لاگ‌ها باید در صورت وجود شامل `trace_id` و `correlation_id` باشند.
- سطح Log باید متناسب با اهمیت رویداد انتخاب شود و از ثبت بیش از حد Logهای Debug در محیط Production جلوگیری گردد.

**ابزارهای پیشنهادی:** Elasticsearch + Kibana، Loki + Grafana، Splunk، Datadog

### ۴.۳. Distributed Tracing (ردیابی توزیع‌شده)

**مسئولیت:** ردیابی کامل مسیر یک درخواست در میان سرویس‌های مختلف برای شناسایی گلوگاه‌ها، خطاها و تأخیرها.

**وظایف کلیدی:**

- **تولید Spanها:** هر سرویس باید Spanهای مربوط به عملیات خود را تولید کند (شروع، پایان، Duration، Metadata)
- **ارسال به Collector:** ارسال Spanها به Collector (Jaeger، Tempo) با استفاده از استاندارد OpenTelemetry
- **ذخیره‌سازی:** ذخیره‌سازی Traceها برای مدت مشخص (معمولاً ۷ روز)
- **جستجو و تحلیل:** جستجوی Traceها بر اساس Service، Operation، Duration، Error و Tags
- **بصری‌سازی:** نمایش گرافیکی مسیر درخواست و زمان‌بندی Spanها

**مفاهیم کلیدی Tracing:**

| مفهوم | توضیح |
| :--- | :--- |
| **Trace** | مسیر کامل یک درخواست از آغاز تا پایان |
| **Span** | یک عملیات واحد در یک سرویس (با زمان شروع و پایان) |
| **Parent‑Child** | رابطه بین Spanها (یک Span والد و چند Span فرزند) |
| **Tags** | برچسب‌های اضافی برای Spanها (HTTP Method، Status Code، Error) |
| **Baggage** | داده‌های متنی که در طول Trace حمل می‌شوند |

**ابزارهای پیشنهادی:** Jaeger، Tempo، Zipkin (با پروتکل OpenTelemetry)

**سیاست Sampling:**

به‌منظور کنترل هزینه و حجم داده‌ها، Traceها باید بر اساس سیاست‌های قابل تنظیم نمونه‌برداری شوند.

نمونه‌ای از سیاست پیشنهادی:

- Production: نمونه‌برداری تطبیقی (Adaptive Sampling)
- Development: ثبت کامل Traceها
- سرویس‌های بحرانی: امکان Override نرخ Sampling

### ۴.۴. Telemetry Gateway

**مسئولیت:** دریافت، اعتبارسنجی، استانداردسازی و مسیریابی تمام داده‌های مشاهده‌پذیری قبل از ذخیره‌سازی.

**وظایف کلیدی:**

- دریافت Metrics، Logs و Traces از تمام سرویس‌ها
- اعتبارسنجی Schema داده‌ها
- افزودن Metadata استاندارد
- حذف یا Mask کردن اطلاعات حساس
- Rate Limiting
- Sampling
- Routing داده‌ها به Backend مناسب
- اعمال سیاست‌های چندمستاجری (Multi-Tenant Isolation)

---

### ۴.۵. Correlation Engine (موتور همبستگی)

**مسئولیت:** ایجاد ارتباط میان تمام داده‌های عملیاتی برای تولید نمای واحد از رفتار سیستم.

**وظایف کلیدی:**

- همبستگی Metrics، Logs، Traces و Domain Events
- اتصال درخواست‌ها به Workflowها و Agent Executionها
- ارتباط میان Queue Messageها و Traceها
- ارائه Root Cause Analysis
- نمایش End-to-End Request Flow
- تولید Service Dependency Graph

**پیاده‌سازی:**

- استفاده از `trace_id` و `correlation_id` به‌عنوان کلیدهای مشترک در تمام داده‌ها
- استفاده از Grafana برای ترکیب داده‌های Prometheus (Metrics)، Loki (Logs) و Tempo (Traces) در یک داشبورد واحد (Grafana Explore با قابلیت Jump‑to‑Logs و Jump‑to‑Traces)
 
**استاندارد شناسه‌های همبستگی:**

تمام درخواست‌ها باید دارای `correlation_id` باشند.

در صورت ایجاد Trace جدید، `trace_id` نیز باید در تمام سرویس‌های Downstream منتقل شود.

تمام Metrics، Logs و Traces باید در صورت امکان این شناسه‌ها را حمل کنند تا امکان تحلیل End-to-End فراهم شود.

### ۴.۶. Alerting Engine (موتور هشداردهی)

**مسئولیت:** تعریف قوانین هشدار، تشخیص ناهنجاری‌ها و ارسال اعلان‌ها به تیم‌های مربوطه.

**وظایف کلیدی:**

- **تعریف قوانین:** تعریف قوانین هشدار بر اساس Metrics (مثلاً `latency > 500ms` یا `error_rate > 1%`)
- **تشخیص ناهنجاری:** تشخیص خودکار ناهنجاری‌ها با استفاده از الگوریتم‌های آماری و Machine Learning (اختیاری)
- **ارسال اعلان:** ارسال اعلان از طریق کانال‌های مختلف (Email، Slack، PagerDuty، Opsgenie، SMS)
- **مدیریت هشدارها:** Grouping، Deduplication، Silence و Ack هشدارها برای جلوگیری از Alert Fatigue
- **ثبت ممیزی:** ثبت تمام هشدارها و اقدامات انجام‌شده

**چرخه عمر هشدار (Alert Lifecycle):**

هر هشدار باید یکی از وضعیت‌های زیر را داشته باشد:

- Open
- Acknowledged
- In Progress
- Resolved
- Closed

تمام تغییر وضعیت‌ها باید ثبت و قابل ممیزی باشند.

**سطوح هشدار:**

| سطح | توضیح | زمان پاسخ |
| :--- | :--- | :--- |
| **Critical** | سرویس از کار افتاده یا داده‌ها در خطر هستند | ≤ ۱۵ دقیقه |
| **High** | اختلال جدی در عملکرد یا تجربه کاربر | ≤ ۱ ساعت |
| **Medium** | شرایط غیرعادی که ممکن است به مشکل تبدیل شود | ≤ ۴ ساعت |
| **Info** | رویدادهای مهم اما غیربحرانی | بدون نیاز به اقدام فوری |

**ابزارهای پیشنهادی:** Alertmanager (برای Prometheus)، Grafana Alerting، Opsgenie، PagerDuty

### ۴.۷. Dashboards & Visualization (داشبوردها و بصری‌سازی)

**مسئولیت:** ارائه نمایش‌های بصری و تعاملی از وضعیت سیستم برای مخاطبان مختلف.

**وظایف کلیدی:**

- **داشبوردهای عملیاتی:** نمایش وضعیت لحظه‌ای سرویس‌ها، خطاها و هشدارها (برای تیم SRE/عملیات)
- **داشبوردهای مدیریتی:** نمایش شاخص‌های کلیدی (KPI) مانند Availability، Latency P95، Cost (برای مدیریت)
- **داشبوردهای AI:** نمایش کیفیت مدل‌ها، مصرف Token، هزینه و عملکرد (برای تیم هوش مصنوعی)
- **داشبوردهای امنیتی:** نمایش رویدادهای امنیتی، تلاش‌های ناموفق و هشدارها (برای تیم امنیت)

**داشبوردهای پیشنهادی:**

| داشبورد | مخاطب | محتوای کلیدی |
| :--- | :--- | :--- |
| **سلامت کل پلتفرم** | مدیریت، عملیات | Availability، خطاهای فعال، هشدارهای بحرانی |
| **وضعیت Microserviceها** | تیم عملیات، SRE | Latency P95، Error Rate، Throughput، منابع |
| **وضعیت Agentها و مدل‌ها** | تیم AI، محصول | نرخ موفقیت، زمان پاسخ مدل، هزینه، Fallback |
| **وضعیت زیرساخت** | تیم زیرساخت | مصرف CPU، حافظه، دیسک، شبکه |
| **امنیت و ممیزی** | تیم امنیت | رویدادهای امنیتی، دسترسی‌های ناموفق |
| **SLO / SLA Dashboard** | عملیات، SRE، مدیریت | وضعیت SLIها، Error Budget، تحقق SLA و روند نقض SLOها |

**ابزارهای پیشنهادی:** Grafana، Kibana، Datadog Dashboards

### ۴.۸. Health Checks & Synthetic Monitoring (بررسی سلامت و پایش ترکیبی)

**مسئولیت:** بررسی دوره‌ای وضعیت سرویس‌ها و شبیه‌سازی سناریوهای کاربری برای تشخیص مشکلات قبل از کاربران واقعی.

**وظایف کلیدی:**

- **Liveness Probe:** بررسی اینکه آیا سرویس در حال اجرا است (در Kubernetes)
- **Readiness Probe:** بررسی اینکه آیا سرویس آماده دریافت ترافیک است (در Kubernetes)
- **Synthetic Monitoring:** شبیه‌سازی درخواست‌های کاربری (API Calls، گردش‌کارهای حیاتی) به‌صورت دوره‌ای
- **پایش نقاط ورود (End‑to‑End):** پایش مسیر کامل یک درخواست از API Gateway تا پاسخ نهایی

**انواع Health Check:**

| نوع | هدف |
| :--- | :--- |
| Liveness | بررسی زنده بودن سرویس |
| Readiness | بررسی آمادگی سرویس برای دریافت درخواست |
| Startup | بررسی تکمیل فرآیند Startup سرویس |
| Synthetic | شبیه‌سازی سناریوهای واقعی کاربران |

### ۴.۹. Telemetry Governance

**مسئولیت:** تعریف استانداردهای تولید داده‌های مشاهده‌پذیری در کل سازمان.

**وظایف کلیدی:**

- استاندارد نام‌گذاری Metrics
- استاندارد Labelها
- استاندارد Log Schema
- استاندارد Trace Naming
- مدیریت نسخه Telemetry Schema
- کنترل کیفیت داده‌های مشاهده‌پذیری
- جلوگیری از Cardinality Explosion
- مدیریت Metadata مشترک

| **Metrics (Aggregated)** | نامحدود (با کاهش دقت) | — | — |
| **Logs (ساخت‌یافته)** | ۷ روز | ۳ ماه (فشرده) | — |
| **Logs (خطا/امنیت)** | ۳۰ روز | ۱ سال | — |
| **Traces** | ۷ روز | ۳۰ روز (Sampled) | ۱۰٪ (برای حفظ هزینه) |
| **Alerts** | نامحدود | نامحدود | — |

**Tiering داده‌ها:**

- **Hot Storage:** داده‌های عملیاتی با دسترسی سریع
- **Warm Storage:** داده‌های کم‌استفاده با هزینه کمتر
- **Cold Archive:** داده‌های آرشیوی برای الزامات قانونی و ممیزی

## ۵. جریان داده مشاهده‌پذیری (Observability Data Flow)

جریان کامل از تولید داده تا نمایش و هشدار:

```text
Application Services (All Domains)
        │
        ├── Produce Metrics (Prometheus Client, OpenTelemetry)
        │
        ├── Produce Logs (Structured JSON → Stdout/File)
        │
        └── Produce Traces (OpenTelemetry SDK → Collector)
        │
        ▼
Collectors (OpenTelemetry Collector, Prometheus, Fluentd)
        │
        ├── Scrape/Push Metrics → Time‑Series DB (Prometheus/Thanos)
        │
        ├── Push Logs → Logging DB (Elasticsearch/Loki)
        │
        └── Push Traces → Tracing DB (Jaeger/Tempo)
        │
        ▼
Storage (Retention Policies, Downsampling, Archiving)
        │
        ▼
Analysis & Correlation
        │
        ├── Query via PromQL, LogQL, TraceQL
        │
        ├── Correlation via Trace‑ID / Correlation‑ID
        │
        ▼
Consumption
        │
        ├── Dashboards (Grafana, Kibana)
        │
        ├── Alerting (Alertmanager, Grafana Alerting)
        │
        └── Health Checks (Kubernetes Probes, Synthetic Monitoring)
        │
        ▼
Actions (On‑Call, Auto‑Scaling, Self‑Healing, Incident Response)
```

## ۱۰. نتیجه‌گیری

دامنه **مشاهده‌پذیری** به‌عنوان **چشم‌های سیستم**، نقش حیاتی در درک رفتار، عملکرد و سلامت پلتفرم ایفا می‌کند. معماری تعریف‌شده در این سند، چارچوبی استاندارد، یکپارچه، مقیاس‌پذیر و کارآمد برای جمع‌آوری، ذخیره‌سازی، تحلیل و نمایش داده‌های عملیاتی از تمام مؤلفه‌ها و سرویس‌ها فراهم می‌آورد.

رعایت اصول طراحی (Observability by Design، Golden Signals، Seamless Correlation، Structured Logging) و پیاده‌سازی مؤلفه‌های کلیدی (Metrics، Logs، Traces، Alerting، Dashboards، Correlation) تضمین می‌کند که تیم‌های توسعه، عملیات و کسب‌وکار بتوانند وضعیت سیستم را به‌صورت شفاف مشاهده کنند، مشکلات را سریعاً شناسایی و رفع کنند، عملکرد را بهینه‌سازی نمایند و تصمیمات آگاهانه‌تری اتخاذ کنند.

**مسئولیت به‌روزرسانی:** تیم عملیات و SRE به همراه معماران ارشد مسئول بازبینی دوره‌ای این سند، به‌روزرسانی شاخص‌ها و هشدارها بر اساس تغییرات سیستم و نیازهای جدید، و ارزیابی اثربخشی زیرساخت مشاهده‌پذیری هستند.

**ثبات سند:** این سند باید با تغییرات در معماری کلان، مؤلفه‌ها و نیازمندی‌های عملیاتی هم‌گام باشد. هر تغییر در ساختار پلتفرم باید از منظر مشاهده‌پذیری بررسی شده و در صورت نیاز این سند به‌روزرسانی شود.
