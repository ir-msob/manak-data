# معماری دامنه ابزارها (Tool Domain Architecture)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.1

**وضعیت:** بازبینی‌شده

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف معماری دامنه **ابزارها** (Tool Domain) تدوین شده است. این دامنه مسئول مدیریت، ثبت، کشف، اجرای امن و پایش ابزارهای قابل اجرا در سیستم‌های خارجی و گردش‌کارهای سازمانی است. ابزارها (Tools) نقطه‌ی اتصال عامل‌های هوشمند به دنیای واقعی هستند و به آن‌ها امکان می‌دهند عملیات‌هایی مانند فراخوانی API، اجرای اسکریپت، تغییر داده، ایجاد تیکت و سایر اقدامات عملیاتی را انجام دهند.

هدف این سند ایجاد چارچوبی استاندارد، امن، مقیاس‌پذیر و قابل اعتماد برای تعریف، مدیریت و اجرای ابزارها و گردش‌کارها (Workflowها) به‌گونه‌ای است که عامل‌ها بتوانند به‌صورت کنترل‌شده و با رعایت اصول امنیتی و حاکمیتی، عملیات واقعی را در سیستم‌های سازمانی انجام دهند. این سند به‌عنوان مرجع اصلی برای تیم‌های توسعه، معماری، امنیت و یکپارچه‌سازی در زمینه طراحی و پیاده‌سازی زیرساخت ابزارها و اقدامات عمل می‌کند.

---

## ۲. دامنه سند

این سند تمام جنبه‌های مرتبط با دامنه ابزارها را پوشش می‌دهد و شامل موارد زیر است:

- **Tool Registry:** ثبت، نگهداری و مدیریت فراداده و نسخه‌های ابزارها
- **Tool Catalog:** کشف و ارائه قابلیت‌های ابزارهای موجود به عامل‌ها
- **Execution Engine:** موتور اجرای ابزارها با پشتیبانی از همزمانی، زمان‌بندی و مدیریت خطا
- **Sandbox Environment:** محیط‌های ایزوله برای اجرای امن ابزارهای پرریسک
- **مصرف Workflow Engine:** ارائه Execution Engine به‌عنوان نقطه اجرای تک‌مرحله‌ای برای گردش‌کارهایی که در دامنه مدیریت جریان کار (`Workflow_Domain_Architecture`) تعریف و هماهنگ می‌شوند
- **Security & Authorization:** کنترل دسترسی، مجوزدهی و تأیید انسانی برای ابزارهای حساس
- **Observability:** پایش، لاگ‌گیری و ردیابی اجرای ابزارها
- **Transaction & Recovery Management:** مدیریت تراکنش‌ها، بازگشت به حالت قبل (Rollback) و اقدامات جبرانی (Compensation)
- **Tool Runtime Management:** مدیریت محیط‌های اجرای ابزارها و Runtimeهای مختلف
- **Tool Policy Enforcement:** اعمال سیاست‌های اجرایی، امنیتی و محدودیت‌ها قبل از اجرای ابزار
- **Tool Version Management:** مدیریت نسخه‌های ابزارها و سازگاری نسخه‌ها
- **Tool Lifecycle Management:** مدیریت چرخه حیات ابزار از ثبت تا منسوخ شدن

جزئیات پیاده‌سازی فنی و کدنویسی در اسناد سطح پایین‌تر تدوین می‌شوند. این سند صرفاً **معماری سطح بالا و اصول طراحی** دامنه را تعریف می‌کند.

## ۳. اصول طراحی دامنه

| اصل | توضیح |
| :--- | :--- |
| **ابزارمحوری (Tool‑Centric)** | تمام تعاملات عامل‌ها با سیستم‌های خارجی باید از طریق ابزارهای تعریف‌شده و کنترل‌شده انجام شود تا امنیت، شفافیت و قابلیت ممیزی حفظ شود. |
| **امنیت پیش‌فرض (Security by Default)** | هیچ ابزاری بدون احراز هویت، مجوزدهی و بررسی سیاست‌های امنیتی قابل اجرا نیست. ابزارهای پرریسک نیاز به تأیید انسانی دارند. |
| **جداسازی و ایزوله‌سازی (Isolation)** | اجرای ابزارها باید در محیط‌های ایزوله (Sandbox) با محدودیت دسترسی شبکه، منابع و زمان انجام شود تا از آسیب به سیستم جلوگیری شود. |
| **قابلیت کشف (Discoverability)** | عامل‌ها باید بتوانند ابزارهای موجود، قابلیت‌ها و محدودیت‌های آن‌ها را از طریق Tool Catalog کشف کنند. |
| **تحمل خطا (Fault Tolerance)** | ابزارها باید با مکانیزم‌های Retry، Exponential Backoff، Timeout و Dead Letter Queue در برابر خطاهای موقت مقاوم باشند. |
| **قابلیت رهگیری (Traceability)** | تمام اجراهای ابزار، پارامترها، نتایج و خطاها باید ثبت و قابل ردیابی باشند. |
| **مدیریت تراکنش (Transaction Management)** | برای گردش‌کارهای چندمرحله‌ای، مکانیزم‌های تراکنش و اقدامات جبرانی برای بازگردانی وضعیت در صورت شکست پیش‌بینی می‌شود. |
| **توسعه‌پذیری (Extensibility)** | افزودن ابزار جدید باید بدون تغییر در هسته سیستم و از طریق رابط‌های استاندارد امکان‌پذیر باشد. |
| **عدم اجرای تکراری (Idempotency)** | اجرای مجدد یک درخواست یا پیام نباید باعث اجرای چندباره یک ابزار یا ایجاد تغییرات تکراری شود. |
| **استقلال Runtime** | ابزارها نباید به نوع Runtime وابسته باشند و موتور اجرا باید انتخاب Runtime مناسب را به‌صورت شفاف انجام دهد. |
| **سازگاری نسخه‌ها (Version Compatibility)** | نسخه‌های مختلف ابزار باید تا پایان اجرای درخواست‌های جاری قابل استفاده باشند و تغییر نسخه نباید موجب اختلال در اجرا شود. تعریف پایه Semantic Versioning و سیاست Deprecation در سند `Versioning_And_Compatibility_Strategy` آمده است. |

## ۴. مؤلفه‌های اصلی دامنه

### ۴.۱. Tool Registry (ثبت ابزار)

**مسئولیت:** ثبت، نگهداری و مدیریت فراداده و نسخه‌های ابزارهای موجود در پلتفرم.

**وظایف کلیدی:**

- **ثبت ابزار:** ثبت ابزار جدید با فراداده کامل (نام، توضیحات، ورودی‌ها، خروجی‌ها، سطح ریسک، مالک)
- **مدیریت نسخه:** نگهداری نسخه‌های مختلف هر ابزار و امکان ارتقا یا بازگشت
- **مدیریت چرخه حیات:** فعال/غیرفعال‌سازی، منسوخ‌سازی و حذف ابزارها
- **اعتبارسنجی:** اعتبارسنجی ساختار و قرارداد ابزار در زمان ثبت
- **مدیریت مجوزها:** تعیین مجوزهای مورد نیاز برای هر ابزار
- **مدیریت چرخه انتشار:** مدیریت وضعیت Draft، Published، Deprecated و Archived
- **مدیریت وابستگی‌ها:** ثبت وابستگی ابزار به Runtimeها، سرویس‌ها و سیستم‌های خارجی
- **مدیریت قابلیت‌ها:** ثبت قابلیت‌های قابل ارائه هر ابزار برای استفاده در فرآیند کشف

**فیلدهای کلیدی Tool Registry:**

| فیلد | توضیح |
| :--- | :--- |
| `tool_id` | شناسه یکتای ابزار |
| `name` | نام ابزار (منحصربه‌فرد) |
| `description` | توضیحات کامل ابزار و کاربرد آن |
| `version` | نسخه فعلی ابزار |
| `capability` | قابلیت‌ها و عملیات قابل انجام |
| `input_schema` | طرحواره ورودی (JSON Schema) |
| `output_schema` | طرحواره خروجی (JSON Schema) |
| `risk_level` | سطح ریسک (Low, Medium, High, Critical) |
| `auth_required` | آیا به احراز هویت نیاز دارد؟ |
| `owner_team` | تیم مالک ابزار |
| `status` | وضعیت (Active, Inactive, Deprecated) |
| `execution_timeout` | حداکثر زمان اجرا (میلی‌ثانیه) |
| `retry_policy` | سیاست تکرار مجدد |
| `created_at` | زمان ثبت |
| `updated_at` | زمان آخرین به‌روزرسانی |
| `runtime_type` | نوع Runtime موردنیاز برای اجرای ابزار |
| `execution_mode` | نحوه اجرا (همزمان، غیرهمزمان، جریانی) |
| `category` | دسته‌بندی ابزار |
| `tags` | برچسب‌های جستجو و کشف |
| `permission_scope` | دامنه مجوزهای موردنیاز |
| `supports_streaming` | پشتیبانی از خروجی جریانی |
| `supports_async` | پشتیبانی از اجرای غیرهمزمان |
| `deprecated_at` | زمان منسوخ شدن ابزار |
| **`compensation_capability`** | **قابلیت جبران (COMPENSABLE \| NON_COMPENSABLE \| READ_ONLY)** |
| **`non_compensable_failure_policy`** | **سیاست در صورت شکست Tool غیرقابل جبران (ABORT_WORKFLOW \| CONTINUE_WITH_WARNING \| HUMAN_ESCALATION)** |
| **`compensation_retry_policy`** | **سیاست Retry برای عملیات جبرانی شامل `max_retries` (پیش‌فرض ۳) و `backoff_seconds` (پیش‌فرض ۳۰)** |
| **`compensable`** | **آیا ابزار قابلیت جبران (Compensation) دارد؟ (boolean)** |
| **`compensation_action`** | **نام عملیات جبرانی (مثلاً `tool_name.compensate`) - در صورت `compensable: true` اجباری است** |
| **`compensation_params_mapping`** | **نگاشت پارامترهای عملیات جبرانی از خروجی عملیات اصلی یا ورودی‌های اولیه (JSON object)** |
| **`is_compensation_idempotent`** | **آیا عملیات جبرانی Idempotent است؟ (پیش‌فرض: true)** |

### ۴.۲. Tool Catalog (کاتالوگ ابزار)

**مسئولیت:** ارائه قابلیت‌های ابزارهای موجود به عامل‌ها و سرویس‌های مصرف‌کننده.

**وظایف کلیدی:**

- **کشف ابزار:** امکان جستجو و فیلتر ابزارها بر اساس نام، قابلیت، سطح ریسک و دسته‌بندی
- **ارائه جزئیات:** نمایش فراداده کامل ابزار شامل ورودی/خروجی، محدودیت‌ها و نمونه‌ها
- **اعتبارسنجی دسترسی:** بررسی مجوزهای عامل درخواست‌کننده قبل از نمایش ابزار
- **نسخه‌بندی:** نمایش نسخه‌های مختلف یک ابزار و قابلیت‌های هر نسخه
- **کشف مبتنی بر قابلیت:** جستجوی ابزارها بر اساس قابلیت موردنیاز به‌جای نام ابزار
- **پیشنهاد ابزار:** ارائه ابزارهای مناسب بر اساس زمینه درخواست عامل
- **فیلتر بر اساس مجوز:** نمایش فقط ابزارهایی که عامل اجازه استفاده از آن‌ها را دارد

**رابط‌های دسترسی:**

- **API:** ارائه REST API برای جستجو و دریافت اطلاعات ابزارها
- **SDK:** کتابخانه‌های کلاینت برای کشف ابزار در زبان‌های مختلف
- **Event:** انتشار رویدادهای تغییر در کاتالوگ برای اطلاع‌رسانی به عامل‌ها

### ۴.۳. Execution Engine (موتور اجرای ابزار)

**مسئولیت:** اجرای امن، قابل اعتماد و کنترل‌شده ابزارها بر اساس درخواست‌های دریافتی از عامل‌ها، Workflowها یا سایر مؤلفه‌های مجاز.

Execution Engine تنها مسئول اجرای ابزار است و مسئولیت طراحی یا هماهنگی فرآیندهای چندمرحله‌ای را بر عهده ندارد. مدیریت توالی اجرا، تصمیم‌گیری، گردش‌کار و جبران خطاها در دامنه Workflow انجام می‌شود.

**وظایف کلیدی:**

- **دریافت درخواست اجرا:** دریافت درخواست اجرای Tool از Agent، Workflow Engine یا سایر سرویس‌های مجاز
- **اعتبارسنجی درخواست:** بررسی ساختار ورودی، نسخه Tool، مجوزها و Policyهای اجرایی
- **اعمال Policyها:** اعمال Rate Limit، Timeout (طبق `Non_Functional_Requirements_And_SLA`)، Quota، Concurrency Limit و سایر سیاست‌های اجرایی
- **اجرای Tool:** اجرای Tool از طریق Runtime مناسب (HTTP، gRPC، Script، Container، MCP و ...)
- **مدیریت خطاهای اجرایی:** مدیریت Retry (طبق سیاست یکپارچه در `Non_Functional_Requirements_And_SLA`)، Timeout، Circuit Breaker و ثبت Failure
- **بازگرداندن نتیجه:** تبدیل خروجی Tool به قالب استاندارد و ارسال نتیجه به درخواست‌کننده
- **ثبت رویدادها و Metrics:** انتشار رویدادهای اجرا و ثبت اطلاعات موردنیاز برای مشاهده‌پذیری و ممیزی
- **انتخاب Runtime:** انتخاب Runtime مناسب بر اساس نوع ابزار
- **اجرای غیرهمزمان:** پشتیبانی از اجرای Async و مدیریت Jobها
- **اجرای جریانی:** پشتیبانی از Streaming برای ابزارهایی که خروجی مرحله‌ای تولید می‌کنند
- **لغو اجرا:** امکان توقف یا لغو اجرای ابزارهای در حال اجرا
- **کنترل همزمانی:** جلوگیری از اجرای همزمان بیش از حد ابزارها

**نکته معماری:**

Execution Engine هیچ دانشی نسبت به منطق کسب‌وکار، ترتیب اجرای مراحل، تصمیم‌گیری یا Compensation ندارد و صرفاً مسئول اجرای یک درخواست Tool است. مدیریت فرآیندهای چندمرحله‌ای بر عهده Workflow Engine و تصمیم‌گیری بر عهده Agent یا Orchestrator است.

**پیکربندی Circuit Breaker:**

| پارامتر | مقدار پیش‌فرض | توضیح |
| :--- | :--- | :--- |
| **Failure Threshold** | ۵۰٪ | درصد خطا در ۱۰ ثانیه آخر که باعث باز شدن مدار می‌شود |
| **Circuit Open Timeout** | ۳۰ ثانیه | مدت زمانی که مدار در حالت باز (Open) باقی می‌ماند |
| **Half-Open Success Threshold** | ۱ درخواست موفق | تعداد درخواست‌های موفق در حالت Half-Open برای بسته شدن مجدد مدار |
| **Monitoring** | فعال | ثبت وضعیت مدار در Metrics و هشدار در صورت باز شدن |

**پیکربندی Timeout پیش‌فرض (طبق `Non_Functional_Requirements_And_SLA`):**

| نوع عملیات | Timeout پیش‌فرض |
| :--- | :--- |
| **فراخوانی Tool (همزمان)** | ۶۰ ثانیه |
| **اجرای Tool در Sandbox** | ۱۲۰ ثانیه |
| **اجرای Tool جریانی** | ۳۰۰ ثانیه |

**جریان اجرای Tool:**

```text
Execution Request
        │
        ▼
Request Validation
        │
        ▼
Authorization & Policy Check
        │
        ▼
Runtime Selection
        │
        ▼
Tool Execution
        │
        ├── Success
        │        │
        │        ▼
        │   Normalize Result
        │        │
        │        ▼
        │   Include compensation_status in response
        │        │
        │        ▼
        │   Publish Event
        │        │
        │        ▼
        │   Return Response
        │
        └── Failure
                 │
                 ▼
        Retry / Timeout / Circuit Breaker
                 │
                 ▼
        Failure Event with compensation_status
```

#### ۴.۳.۱. پشتیبانی از عملیات جبرانی (Compensation Execution)

Execution Engine مسئول اجرای عملیات جبرانی (`compensate`) درخواستی از سوی Workflow Engine است. این عملیات باید با رعایت اصول زیر انجام شود:

- **Idempotency:** عملیات جبرانی باید به‌گونه‌ای پیاده‌سازی شود که اجرای مجدد آن (در صورت Retry) عوارض جانبی جدیدی ایجاد نکند. این ویژگی در Tool Registry با فیلد `is_compensation_idempotent` مشخص می‌شود.
- **عدم وابستگی به وضعیت جلسه:** عملیات جبرانی نباید به Context یا Session Memory جاری وابسته باشد و باید صرفاً بر اساس پارامترهای ارسال‌شده (که از خروجی عملیات اصلی یا ورودی‌های اولیه استخراج می‌شوند) عمل کند.
- **ثبت کامل:** تمام فراخوانی‌های عملیات جبرانی (موفق و ناموفق) باید با جزئیات کامل در Audit Log ثبت شوند.

**جریان فراخوانی جبران:**

```text
Workflow Engine
        │
        ▼
Execution Engine دریافت درخواست compensate
        │
        ├── اعتبارسنجی Tool (وجود compensation_action)
        │
        ├── آماده‌سازی پارامترها بر اساس compensation_params_mapping
        │
        ├── اجرای عملیات جبرانی (با همان محدودیت‌های امنیتی و Sandbox)
        │
        ├── ثبت نتیجه در Audit Log (شامل شناسه گردش‌کار و گام مرتبط)
        │
        ▼
بازگرداندن نتیجه به Workflow Engine
```

---

#### ۴.۳.۲. الزامات پاسخ اجرای Tool

پاسخ هر درخواست اجرای Tool باید شامل فیلد `compensation_status` با یکی از مقادیر زیر باشد:

- `AVAILABLE`: عملیات جبرانی برای این Tool تعریف شده و قابل اجرا است.
- `NOT_SUPPORTED`: این Tool فاقد عملیات جبرانی است (NON_COMPENSABLE یا READ_ONLY).
- `FAILED`: عملیات جبرانی برای این Tool تعریف شده اما در زمان اجرا با شکست مواجه شده است.

### ۴.۴. Sandbox Environment (محیط ایزوله)

**مسئولیت:** فراهم‌سازی محیط‌های اجرای ایزوله و محدود برای ابزارهای پرریسک یا ناشناخته.

**وظایف کلیدی:**

- **ایزوله‌سازی شبکه:** محدودیت دسترسی شبکه به منابع داخلی و خارجی
- **محدودیت منابع:** محدودیت مصرف CPU، حافظه و زمان اجرا
- **محدودیت دسترسی فایل:** محدودیت دسترسی به فایل‌ها و دایرکتوری‌های سیستم
- **پاک‌سازی خودکار:** حذف خودکار محیط پس از پایان اجرا
- **ثبت و پایش:** ثبت کامل فعالیت‌های داخل Sandbox
- **اعمال سیاست‌های امنیتی:** اعمال محدودیت‌های دسترسی بر اساس Policyهای امنیتی
- **ثبت کامل فعالیت‌ها:** ثبت تمام عملیات انجام‌شده در محیط Sandbox
- **حذف اطلاعات موقت:** پاک‌سازی کامل داده‌های موقت پس از پایان اجرا

**سناریوهای استفاده از Sandbox:**

| سناریو | توضیح |
| :--- | :--- |
| **ابزارهای پرریسک** | ابزارهایی که امکان تغییر داده یا دسترسی به سیستم‌های حساس دارند |
| **ابزارهای ناشناخته** | ابزارهای جدید که هنوز به‌طور کامل اعتبارسنجی نشده‌اند |
| **اجرای کد دلخواه** | ابزارهایی که امکان اجرای اسکریپت یا کد سفارشی را فراهم می‌کنند |
| **تست و اعتبارسنجی** | اجرای ابزارها در محیط تست قبل از انتشار به تولید |

### ۴.۵. ارتباط با دامنه مدیریت جریان کار (Relationship with Workflow Domain)

**این دامنه هیچ موتور گردش‌کار (Workflow Engine) مستقلی ندارد و مالک هیچ منطق چندمرحله‌ای نیست.** اجرای گردش‌کارهایی که ترکیبی از چند Tool هستند، به‌طور کامل در مسئولیت دامنه مدیریت جریان کار (`Workflow_Domain_Architecture`) قرار دارد.

**مرز دقیق مسئولیت:**

| مسئولیت | مالک |
| :--- | :--- |
| تعریف گردش‌کار (Workflow Definition) | دامنه مدیریت جریان کار |
| توالی، شرط، اجرای موازی بین گام‌ها | دامنه مدیریت جریان کار |
| مدیریت وضعیت گردش‌کار (State Manager) | دامنه مدیریت جریان کار |
| Retry / Rollback / Compensation در سطح گردش‌کار | دامنه مدیریت جریان کار |
| اجرای واقعی هر گام منفرد (Tool Invocation) | این دامنه، از طریق Execution Engine (بخش ۴.۳) |
| اعتبارسنجی پارامتر، Sandbox، Policy هر Tool | این دامنه |

**نحوه تعامل:** Workflow Engine (در دامنه مدیریت جریان کار) برای هر گامی که نیاز به اجرای Tool دارد، یک درخواست مجزا و مستقل به Execution Engine همین دامنه ارسال می‌کند و منتظر نتیجه آن گام می‌ماند. Execution Engine هیچ دانشی از گام قبلی یا بعدی گردش‌کار ندارد و صرفاً یک درخواست Tool را پردازش می‌کند (مطابق با نکته معماری بخش ۴.۳).

> **ارجاع:** برای جزئیات کامل تعریف Workflow، State Manager، Human‑in‑the‑Loop و مدیریت خطای سطح گردش‌کار، به سند `Workflow_Domain_Architecture` مراجعه کنید.

### ۴.۶. Security & Authorization (امنیت و مجوزدهی)

**مسئولیت:** کنترل دسترسی، مجوزدهی و تأیید انسانی برای ابزارها.

**وظایف کلیدی:**

- **مجوزدهی بر اساس نقش:** بررسی نقش کاربر/Agent قبل از اجازه اجرا
- **مجوزدهی بر اساس Tool:** هر ابزار دارای سطح دسترسی مشخص است
- **تأیید انسانی (Human‑in‑the‑Loop):** برای ابزارهای با سطح ریسک بالا، نیاز به تأیید انسانی قبل از اجرا
- **محدودیت نرخ (Rate Limiting):** محدودیت تعداد اجرا در بازه زمانی مشخص
- **ثبت ممیزی:** ثبت تمام درخواست‌های اجرا، موفق و ناموفق
- **مجوزدهی مبتنی بر ویژگی (ABAC):** اعمال مجوزها بر اساس ویژگی‌های کاربر، عامل، ابزار و داده
- **تفویض هویت (Identity Delegation):** اجرای ابزار با هویت کاربر یا سرویس درخواست‌کننده
- **مدیریت اسرار (Secret Management):** استفاده ایمن از Tokenها، کلیدها و اطلاعات محرمانه

**سطوح ریسک و الزامات مجوز:**

| سطح ریسک | توضیح | مجوز مورد نیاز |
| :--- | :--- | :--- |
| **Low** | عملیات فقط‑خواندنی و بی‌خطر | مجوز عمومی |
| **Medium** | عملیات تغییر داده با تأثیر محدود | مجوز نقش خاص |
| **High** | عملیات تغییر داده با تأثیر گسترده | مجوز نقش + تأیید انسانی |
| **Critical** | عملیات حذف، تغییر زیرساخت یا مالی | مجوز نقش + تأیید انسانی + تأیید مدیر |

---

### ۴.۷. Observability (مشاهده‌پذیری)

**مسئولیت:** پایش، لاگ‌گیری و ردیابی اجرای ابزارها.

**متریک‌های کلیدی:**

| متریک | توضیح |
| :--- | :--- |
| **Execution Success Rate** | درصد اجراهای موفق |
| **Execution Failure Rate** | درصد اجراهای ناموفق |
| **Average Execution Time** | میانگین زمان اجرا |
| **Retry Count** | تعداد تلاش‌های مجدد |
| **Timeout Count** | تعداد Timeoutها |
| **Rate Limit Hits** | تعداد تلاش‌های محدودشده |
| **Sandbox Usage** | تعداد اجراهای Sandbox |
| **Execution Queue Size** | تعداد درخواست‌های در انتظار اجرا |
| **Concurrency Usage** | میزان استفاده از ظرفیت اجرای همزمان |
| **Circuit Breaker Activations** | تعداد فعال شدن Circuit Breaker |
| **Average Queue Time** | میانگین زمان انتظار قبل از اجرا |
| **Execution Throughput** | تعداد اجراهای موفق در واحد زمان |

**لاگ‌گیری:**

- تمام اجراهای Tool (موفق و ناموفق) با جزئیات کامل
- شامل: `execution_id`, `tool_id`, `agent_id`, `user_id`, `tenant_id`, `parameters`, `result`, `duration_ms`, `status`, `error_message`, `timestamp`

**ردیابی (Tracing):**

- Distributed Tracing با OpenTelemetry
- ارسال Traceها به Jaeger یا Tempo
- امکان ردیابی یک درخواست از Agent تا Tool و سیستم خارجی

### ۴.۸. Endpoint حذف تاریخچه کاربر (`tool.delete_user_history`)

**مسئولیت:** پیاده‌سازی Endpoint داخلی استاندارد برای حذف یا ناشناس‌سازی تاریخچه اجرای Toolهای مرتبط با یک کاربر مشخص، به‌عنوان یکی از گام‌های Workflow حذف سرتاسری داده (`wf-deletion` تعریف‌شده در `Workflow_Domain_Architecture` بخش ۴.۱.۲).

**وظایف کلیدی:**

- **شناسایی تاریخچه مرتبط:** یافتن تمام رکوردهای `ToolExecutionStarted`، `ToolExecutionSucceeded` و `ToolExecutionFailed` که به `user_id` درخواستی مرتبط هستند.
- **ناشناس‌سازی:** ناشناس‌سازی `user_id` و `agent_id` (در صورت وجود) در رکوردهای تاریخچه اجرا (به‌دلیل نیاز به نگهداری برای تحلیل و عیب‌یابی، حذف کامل مجاز نیست).
- **Idempotency:** تضمین این‌که اجرای مجدد درخواست حذف اثر جانبی جدید ایجاد نکند.
- **گزارش نتیجه:** بازگرداندن تعداد رکورد ناشناس‌شده به سرویس `Data Subject Request Service`.

**ورودی/خروجی:** مطابق قرارداد استاندارد Endpoint حذف تعریف‌شده در `Data_Governance_and_Compliance` (بخش ۱۲.۶).

## ۵. جریان کامل اجرای ابزار

جریان کامل از درخواست عامل تا دریافت نتیجه:

```text
Agent Request (with tool_id, parameters, context)
        │
        ▼
Execution Engine دریافت درخواست
        │
        ├── ۱. اعتبارسنجی ورودی (بر اساس input_schema)
        │
        ├── ۲. بررسی مجوزها (RBAC/ABAC)
        │
        ├── ۳. بررسی محدودیت نرخ (Rate Limiting)
        │
        ├── ۴. بررسی نیاز به تأیید انسانی (Human‑in‑the‑Loop)
        │       │
        │       └── اگر نیاز باشد → ارسال درخواست تأیید → انتظار برای پاسخ
        │
        ├── ۵. ایجاد محیط Sandbox (در صورت نیاز)
        │
        ├── ۶. اجرای Tool با Timeout
        │       │
        │       ├── موفق → دریافت نتیجه
        │       │
        │       └── ناموفق → Retry (تا سقف مجاز)
        │
        ├── ۷. اعتبارسنجی خروجی (بر اساس output_schema)
        │
        ├── ۸. ثبت نتیجه در Memory (Experience Store)
        │
        ├── ۹. انتشار رویداد (ToolCompleted / ToolFailed)
        │
        ├── ۱۰. ثبت لاگ و Metrics
        │
        ▼
Return Result to Agent
```

## ۱۰. نتیجه‌گیری

دامنه **ابزارها** به‌عنوان **بازوی اجرایی پلتفرم**، نقش حیاتی در تبدیل تصمیمات هوشمند عامل‌ها به عملیات واقعی در سیستم‌های سازمانی ایفا می‌کند. معماری تعریف‌شده در این سند، چارچوبی استاندارد، امن، مقیاس‌پذیر و قابل اعتماد برای تعریف، ثبت، کشف، اجرا و پایش ابزارها و گردش‌کارها فراهم می‌آورد.

رعایت اصول طراحی (Tool‑Centric، Security by Default، Isolation، Fault Tolerance، Transaction Management) و پیاده‌سازی مؤلفه‌های کلیدی (Tool Registry، Tool Catalog، Execution Engine، Sandbox، Security & Authorization) تضمین می‌کند که عامل‌های هوشمند بتوانند به‌صورت کنترل‌شده، امن و قابل اطمینان با سیستم‌های خارجی تعامل کرده و عملیات واقعی را در سازمان اجرا کنند.

**مسئولیت به‌روزرسانی:** تیم معماری به همراه تیم‌های توسعه، امنیت و یکپارچه‌سازی مسئول بازبینی دوره‌ای این سند، به‌روزرسانی آن بر اساس تغییرات نیازمندی‌های ابزارها، پروتکل‌های جدید و بازخورد تیم‌های پیاده‌سازی هستند.

**ثبات سند:** این سند باید با تغییرات در معماری کلان، پروتکل‌های یکپارچه‌سازی و نیازمندی‌های امنیتی هم‌گام باشد. هر تغییر در ابزارها یا سیاست‌های اجرایی باید در این سند منعکس شود تا سایر اسناد معماری و طراحی نیز به‌روزرسانی شوند.
