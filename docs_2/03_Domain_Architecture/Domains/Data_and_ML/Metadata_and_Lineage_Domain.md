# معماری دامنه مدیریت فراداده و دودمان داده (Metadata & Lineage Domain Architecture)

**نام پلتفرم:** Enterprise AI Context & Automation Platform

**نسخه:** 1.1

**وضعیت:** بازبینی‌شده

**سند مرجع نام‌گذاری:** `Naming_And_Terminology_Glossary`

---

## ۱. هدف سند

این سند با هدف تعریف معماری دامنه **مدیریت فراداده و دودمان داده** (Metadata & Lineage Management) تدوین شده است. این دامنه به‌عنوان مرجع واحد حقیقت برای تمام فراداده‌های پلتفرم (شامل Schemaها، دودمان داده، مالکیت، طبقه‌بندی و کیفیت) عمل می‌کند و سرویس‌های مختلف را از مدیریت پراکندهٔ Metadata بی‌نیاز می‌سازد.

هدف آن ایجاد یک لایهٔ متمرکز و استاندارد برای ثبت، نگهداری و پرس‌وجوی فراداده است تا تکامل‌پذیری، انطباق‌پذیری و شفافیت داده‌ها در سراسر پلتفرم تضمین شود. این سند به‌عنوان مرجع اصلی برای تیم‌های داده، معماری، حاکمیت و توسعه در زمینه مدیریت فراداده عمل می‌کند.

---

## ۲. دامنه سند

این سند تمام جنبه‌های مرتبط با دامنه مدیریت فراداده و دودمان داده را پوشش می‌دهد و شامل موارد زیر است:

- **Schema Registry:** ثبت، نسخه‌بندی و اعتبارسنجی Schemaهای داده (برای Kafka، APIها و پایگاه‌ها)
- **Data Catalog:** کشف داده، جستجوی فراداده و نمایش مالکیت/طبقه‌بندی داده‌ها
- **Data Lineage:** ثبت و نمایش دودمان داده (نحوهٔ تولید، تبدیل و مصرف داده‌ها در سراسر خطوط لوله)
- **Metadata Governance:** اعمال سیاست‌های نسخه‌بندی، کامپتیبیلیتی (Compatibility) و انطباق بر روی Schemaها

جزئیات پیاده‌سازی فنی و کدنویسی در اسناد سطح پایین‌تر تدوین می‌شوند. این سند صرفاً **معماری سطح بالا و اصول طراحی** دامنه را تعریف می‌کند.

---

## ۳. اصول طراحی دامنه

| اصل | توضیح |
| :--- | :--- |
| **مرجع واحد حقیقت (Single Source of Truth)** | تمام دامنه‌ها برای ثبت یا دریافت فراداده باید به این دامنه مراجعه کنند. هیچ دامنه‌ای نباید فراداده را به‌صورت محلی ذخیره کند. |
| **تکامل‌پذیری (Evolution)** | تغییرات Schema باید با حفظ سازگاری با نسخه‌های قبلی (Backward/Forward Compatibility) مدیریت شوند. |
| **غیرمتمرکز نبودن** | هیچ دامنه‌ای نباید Schema Registry یا Lineage خود را به‌صورت محلی پیاده‌سازی کند. |
| **تغییرناپذیری Lineage** | دودمان داده (Lineage) پس از ثبت، غیرقابل‌تغییر است و بیانگر یک حقیقت تاریخی است. |
| **قابلیت جستجو** | تمام فراداده‌ها باید از طریق رابط‌های جستجوی کارآمد قابل کشف باشند. |

## ۴. مؤلفه‌های اصلی دامنه

### ۴.۱. Schema Registry (ثبت طرحواره)

**مسئولیت:** ذخیره، نسخه‌بندی و اعتبارسنجی تمام Schemaهای پلتفرم.

**وظایف کلیدی:**

- **ثبت Schema:** ثبت Schema جدید با فراداده کامل (نام، نسخه، نوع، تاریخ ایجاد)
- **نسخه‌بندی:** نگهداری نسخه‌های مختلف هر Schema با قابلیت بازگشت. نسخه‌بندی بر اساس `Versioning_And_Compatibility_Strategy` انجام می‌شود.
- **اعتبارسنجی Compatibility:** اعمال سیاست‌های Compatibility (Backward, Forward, Full) برای جلوگیری از Breaking Changes. سیاست‌های Compatibility در زمان ثبت Schema تعیین می‌شوند.
- **کش (Cache):** کش‌کردن Schemaها برای کاهش تأخیر در زمان اعتبارسنجی با TTL قابل تنظیم (پیش‌فرض: ۵ دقیقه).
- **اعتبارسنجی خودکار:** بررسی سازگاری نسخه جدید با نسخه‌های قبلی بر اساس سیاست Compatibility.
- **ثبت تغییرات:** ثبت تاریخچه کامل تغییرات هر Schema برای ممیزی.

**فیلدهای کلیدی Schema Registry:**

| فیلد | توضیح |
| :--- | :--- |
| `schema_id` | شناسه یکتای Schema |
| `name` | نام Schema |
| `version` | نسخه فعلی (Semantic Versioning) |
| `type` | نوع Schema (Avro, Protobuf, JSON Schema) |
| `definition` | محتوای کامل Schema |
| `compatibility` | سیاست Compatibility (Backward, Forward, Full) |
| `owner_team` | تیم مالک Schema |
| `status` | وضعیت (Draft, Active, Deprecated, Archived) |
| `created_at` | زمان ثبت |
| `updated_at` | زمان آخرین به‌روزرسانی |
| `deprecated_at` | زمان منسوخ‌سازی (در صورت Deprecated) |
| `replaced_by_version` | نسخه جایگزین (در صورت Deprecated) |

**راهبرد کش Schema:**

| لایه | TTL | توضیح |
| :--- | :--- | :--- |
| **In-Memory Cache** | ۵ دقیقه | کش محلی در `metadata-lineage-service` |
| **Distributed Cache (Redis)** | ۱۵ دقیقه | کش توزیع‌شده برای کاهش بار روی پایگاه داده |
| **بازخوانی اجباری** | — | در صورت خطای Validation، کش به‌روزرسانی می‌شود |

**سیاست‌های Compatibility پشتیبانی‌شده:**

| سیاست | توضیح |
| :--- | :--- |
| **Backward** | نسخه جدید باید با مصرف‌کنندگان نسخه قبلی سازگار باشد (افزودن فیلد مجاز است، حذف یا تغییر نوع مجاز نیست). |
| **Forward** | نسخه جدید باید با مصرف‌کنندگان نسخه جدید سازگار باشد (افزودن فیلد در نسخه قدیمی مجاز است، حذف یا تغییر نوع مجاز نیست). |
| **Full** | هر دو حالت Backward و Forward پشتیبانی می‌شوند. |
| **None** | هیچ محدودیتی برای سازگاری اعمال نمی‌شود (فقط برای محیط Development). |

**روش تکامل Schema (Schema Evolution):**

| تغییر | مجاز | شرط |
| :--- | :--- | :--- |
| افزودن فیلد جدید | بله | فیلد باید اختیاری باشد یا مقدار پیش‌فرض داشته باشد |
| حذف فیلد | خیر (با Deprecation) | ابتدا Deprecated، سپس در نسخه Major بعدی حذف شود |
| تغییر نوع فیلد | خیر (با نسخه جدید) | نیاز به نسخه Major جدید با Schema جدید |
| تغییر نام فیلد | خیر (با Deprecation) | فیلد قدیمی Deprecated و فیلد جدید با نام جدید اضافه شود |
| افزودن Enum مقدار جدید | بله | باید با مصرف‌کنندگان موجود سازگار باشد |

### ۴.۲. Data Catalog (کاتالوگ داده)

**مسئولیت:** ارائه رابط برای کشف داده، جستجوی فراداده و نمایش اطلاعات مرتبط با داده‌ها.

**وظایف کلیدی:**

- **ثبت داده:** ثبت مجموعه‌داده‌ها با فراداده کامل (نام، توضیحات، مالک، طبقه‌بندی)
- **جستجو:** جستجوی داده‌ها بر اساس نام، توضیحات، برچسب‌ها و مالک
- **مدیریت طبقه‌بندی:** نمایش طبقه‌بندی امنیتی و قوانین دسترسی
- **مدیریت مالکیت:** ثبت و نمایش مالک و متولی هر مجموعه داده

**ابزارهای پیشنهادی:** Apache Atlas، Amundsen، DataHub

---

### ۴.۳. Lineage Service (سرویس دودمان داده)

**مسئولیت:** ثبت و پرس‌وجوی دودمان داده (نقشهٔ جریان داده از منبع تا مصرف‌کننده).

**وظایف کلیدی:**

- **ثبت Lineage:** ثبت رویدادهای تبدیل، انتقال و مصرف داده در خطوط لوله
- **پرس‌وجو:** پرس‌وجوی دودمان به‌صورت Upstream (منابع) و Downstream (مصرف‌کنندگان)
- **بصری‌سازی:** ارائه گراف دودمان برای عیب‌یابی و تحلیل تأثیر
- **یکپارچگی با Audit:** ثبت تغییرات و دسترسی‌ها برای اهداف انطباق

**زیرساخت پیشنهادی:** پایگاه داده گرافی (Neo4j، JanusGraph) + Kafka

---

### ۴.۴. Metadata Governance (حاکمیت فراداده)

**مسئولیت:** اعمال سیاست‌های نسخه‌بندی، کامپتیبیلیتی و انطباق بر روی Schemaها.

**وظایف کلیدی:**

- **سیاست‌های Compatibility:** تعیین و اعمال سیاست‌های Backward، Forward یا Full برای هر Schema
- **نگهداری نسخه‌ها:** مدیریت دوره نگهداری و انقضای نسخه‌های قدیمی
- **گزارش‌دهی:** تولید گزارش‌های دوره‌ای از وضعیت فراداده و انطباق

---

### ۴.۵. مدیریت خطا در زمان عدم دسترسی (Error Handling for Unavailability)

**مسئولیت:** مدیریت شرایطی که `metadata-lineage-service` در دسترس نیست یا با تأخیر پاسخ می‌دهد.

**وظایف کلیدی:**

- **Schema Registry Unavailability:** در صورت عدم دسترسی به Schema Registry، دامنه‌های مصرف‌کننده (مانند Event Publisher) باید از کش محلی (Cache) یا آخرین نسخه معتبر Schema استفاده کنند. در صورت عدم وجود کش معتبر، عملیات با خطای `SCHEMA_UNAVAILABLE` متوقف می‌شود.
- **Lineage Service Unavailability:** در صورت عدم دسترسی به Lineage Service، دامنه‌های تولیدکننده (مانند Data Engineering) باید رویدادهای Lineage را در یک صف محلی (Local Queue) ذخیره کنند و پس از بازیابی سرویس، ارسال کنند.
- **Retry Policy:** درخواست‌های ناموفق به `metadata-lineage-service` باید با سیاست Retry تعریف‌شده در `Non_Functional_Requirements_And_SLA` (حداکثر ۳ Retry، Exponential Backoff) تکرار شوند.
- **Fallback Behavior:** در صورت شکست تمام Retryها، عملیات باید با یکی از رفتارهای زیر ادامه یابد:
  - **Schema Registry:** درخواست با خطای `SCHEMA_UNAVAILABLE` رد شود (Fail Closed).
  - **Lineage Service:** رویداد در صف محلی نگهداری شود و عملیات اصلی ادامه یابد (Fail Open با Warning).
- **Alerting:** در صورت تکرار خطا یا عدم دسترسی طولانی‌مدت، هشدار به تیم عملیات ارسال شود.
- **Recovery:** پس از بازیابی سرویس، درخواست‌های ذخیره‌شده در صف محلی به‌صورت خودکار ارسال شوند.

## ۹. نتیجه‌گیری

دامنه **مدیریت فراداده و دودمان داده** به‌عنوان **مرجع واحد حقیقت** برای تمام فراداده‌های پلتفرم، نقش حیاتی در شفافیت، تکامل‌پذیری و انطباق‌پذیری سیستم ایفا می‌کند. معماری تعریف‌شده در این سند، چارچوبی استاندارد، متمرکز و قابل اعتماد برای مدیریت Schemaها، دودمان داده و کاتالوگ داده فراهم می‌آورد.

رعایت اصول طراحی (Single Source of Truth، Evolution، Immutability) و پیاده‌سازی مؤلفه‌های کلیدی (Schema Registry، Data Catalog، Lineage Service) تضمین می‌کند که تمام دامنه‌ها بتوانند به‌صورت یکپارچه و بدون وابستگی متقابل، از خدمات فراداده استفاده کنند و در عین حال الزامات انطباق و ممیزی به‌خوبی پوشش داده شود.

**مسئولیت به‌روزرسانی:** تیم معماری به همراه تیم‌های داده، حاکمیت و توسعه مسئول بازبینی دوره‌ای این سند، به‌روزرسانی آن بر اساس تغییرات نیازمندی‌های فراداده و بازخورد تیم‌های مصرف‌کننده هستند.

**ثبات سند:** این سند باید با تغییرات در معماری کلان، نیازمندی‌های انطباق و استانداردهای داده هم‌گام باشد. هر تغییر در فرآیندهای مدیریت فراداده باید در این سند منعکس شود تا سایر اسناد معماری و طراحی نیز به‌روزرسانی شوند.
